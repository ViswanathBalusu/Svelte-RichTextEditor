# ADR 0316: Lane U-PRO-120-131, decisions taken to close PRO-131 and PRO-130 criterion 4

Status: proposed. Owner decisions stay the owner's; these are the spec defaults or the kit's proposals, used so that a criterion can be proven.

Date: 2026-11-13. Lane: U-PRO-120-131, round 1.

## Context

PRO-131 (the `perm-read` profile) and PRO-130 (read restrictions in DEP) waited for a server that announces read restrictions. The reference service (`services/document-service`) had the projection machinery (ADR 0019; `control-plane/visibility.ts`, the data plane's view tokens) but did not wire a visibility function by default, so every reader saw the full document, and it announced no feature name. The leak oracle of `perm-read.leak` then found confidential text in REST content responses.

## Decisions

1. **Feature name.** The reference service announces `read-restrictions`. This is the kit's proposal (ADR 0042 item 4; `packages/tck/src/config.ts`), not a DEP decision. DEP still names no feature (PRO-130 criterion 4 is ticked on the kit's name). Owner or spec decision needed: the name, and whether `read-restrictions` belongs in the feature registry of `packages/protocol`.
2. **Default wiring.** The reference service wires read restrictions on by default (`restrictedViews` in `services/document-service/src/control-plane/visibility.ts`, used by `src/server.ts`). Owner decision 2026-11-06 says version 1 can hide regions; this ADR only makes the default match it. An operator may still pass `views` explicitly; `FULL_VIEWS` is unchanged.
3. **Test environment.** The PostgreSQL run creates a database named `docedit_u_pro_120_131_<hex>` with the admin role, runs it through the service role, and drops it afterwards. No other object is touched.

## Consequences

- Discovery of the reference service lists `read-restrictions` (`services/document-service/test/data-plane/session.test.ts` expectation updated).
- The `perm-read` profile runs against the reference service. `leak`, `converge` and `placeholder` pass in memory and on PostgreSQL. `leak` does not yet cover exports or asset URLs, because the reference service announces no `exports` feature in the run (PRO-131 criterion 1 stays open).
- A server that wires no visibility function still announces `read-restrictions` only if it takes `PROTOCOL_FEATURES` as its default; this is a known gap to close with the feature registry decision in point 1.

## Round 2 (2026-11-13): PRO-121, and why PRO-123 to PRO-126 were not closed

Status: proposed. Lane U-PRO-120-131, round 2.

### PRO-121 (webhooks)

- Done: `services/document-service/src/control-plane/webhook-deliveries-pg.ts` implements the `DeliveryStore` of the dispatcher on PostgreSQL, with the DDL of table `webhook_deliveries`. `services/document-service/test/postgres/u-pro-121-webhook-deliveries.pg.test.ts` runs it on a database the test creates in the Podman PostgreSQL (4 tests passed: round trip and order, refused duplicate, update, and a retry that keeps its `webhook-id` and ends delivered).
- Proposal 1 (delivery table): carry `WEBHOOK_DELIVERIES_DDL` in a new migration under `services/document-service/migrations/`. Not added here, because every other schema test reads the newest migration as the expected version, and about a hundred lanes share the tree. The main session should sequence it.
- Proposal 2 (kit receiver versus egress): the egress proxy refuses loopback and private addresses (10 §3.2; `egress-address.ts`). A kit receiver on the same host therefore cannot receive a delivery from the reference service, and PRO-121 criteria 1 to 3 cannot be run end to end. The spec default is to refuse. The proposal, for the owner to decide, is an exception that applies only in test mode (PRO-109), with an explicit allow-list entry for the kit's receiver address. Alternatives: a receiver on a public test name, or a receiver in a container on a non-private address.
- Proposal 3: the retry base delay and factor stay with the caller (the spec does not state them). No default is proposed.

### PRO-123, PRO-124, PRO-125, PRO-126 (not closed this round)

- PRO-123 criterion 2 needs an independent evaluator of the rules language in another language. The fixtures hold 426 cases (`packages/tck/fixtures/rules/rules-1.fixtures.json`: 226 expressions, 70 patterns, 68 rule sets, 62 values). The reference is `packages/rules/src/language.ts` (1,317 lines), `evaluate.ts` (521), `pattern.ts` (709) and `dates.ts`, `decimal.ts`. A second implementation is a separate piece of work and would not be a quick port. Left open.
- PRO-124 needs a server in relay mode. No service in `services/` implements relay mode; `packages/authority/src/room/relay.ts` is in-process logic, not a DEP server. Left open.
- PRO-125 needs a runner for the authority interface of 05 §10, which DEP does not reach. The kit has no such runner, and the reference-service run belongs to CI (root configuration). Left open.
- PRO-126 needs a server that exposes test hooks. The hook interface and the feature name `test-hooks` are not decided (ADR 0219). Left open until the owner or the main session decides them.

### Owner or main-session items

1. Sequence the migration for `webhook_deliveries` (Proposal 1), then compose `PgDeliveryStore` in place of the memory store.
2. Decide the test-mode egress exception for the kit receiver (Proposal 2).
3. Decide the test-hook interface (ADR 0219) before PRO-126.
4. Decide whether a relay-mode server is built (PRO-124), and whether the authority profile runs in-process (PRO-125).
