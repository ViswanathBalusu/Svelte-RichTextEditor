# ADR 0313: lane V-PRO-069-085, open questions met while closing blocked criteria

Status: proposed. Owner decisions stay the owner's; where the spec leaves a question open, this lane
used the spec default (as the story Notes say) and records it here.

Scope: stories PRO-083 and PRO-084 in `docs/stories/PRO-protocol.md`, the element methods they need
(`packages/element/src/host-api.ts`, `packages/element/src/doc-editor.ts`), and their tests.

## 1. Count in `flush` rejection (PRO-083 criterion 2)

05 §8.1 says the rejection reports "the number of unconfirmed commits". The engine (`flush` in
`packages/engine/src/core.ts`) reports the count of unconfirmed items it holds (in-flight commits plus
the queue, as the story Notes already say). Spec default used: keep the engine's count and say so in
the story. The browser test (`packages/element/e2e/pro-083-flush-timeout-journal.spec.ts`) checks only
that the count is at least 1 and that the typed text stays in the journal. The owner may want one
count per commit; that is not decided here.

## 2. Insert of a fragment that spans the whole document (PRO-084)

`insertContent` refuses a fragment that replaces the whole document with `refused`, `refusal:
structure` (engine guard). The element tests insert one block instead. The spec does not say this
case must succeed; the engine's answer is kept.

## 3. Reason for a refused `exec` (PRO-085 criterion 3, open)

`exec` returns a boolean. The spec wants the call to report why. Changing the return type changes the
published typings (PRO-091) and the engine's `run`, so it is not done in this lane. Proposed: return
the boolean as now and expose the reason through a later member such as `execResult`. Owner or main
session to decide. Not built.

## 4. Feature switches (PRO-081 criterion 4, open)

05 names feature switches as a category of `config` but gives no keys. The config type
(`packages/element/src/config.ts`) has none. A key would need the shell to hide the commands of that
feature (`packages/ui/src/commands/builtin.ts`) as well. Spec default: none is invented here. Owner or
main session to name the first switch. Not built.

## 5. Every built-in command reachable from the host (PRO-085 criterion 5, open)

The built-in toolbar commands (`packages/ui/src/commands/builtin.ts`, ids such as `edit.undo`) are not
the engine's `CommandName` set that `exec` takes. How the host reaches each command is not stated in 05
or 13. Not decided here; see docs/adr/0217-lane-PRO-085-098.md, question 3.

## Round 7 (2026-11-14), status: proposed

Decisions the spec leaves open, taken at the spec default or as the smallest reading, for the owner to confirm:

1. seq on every document, thread and comment event is the content head at the moment of the event (05 section 7; the schemas require it). For dep.document.deleted the head is read after the soft delete, because the data stays (BE-035 criterion 6).
2. dep.document.changed and the restore's dep.document.changed carry chainHead when the log store has a chain head (LogStore.state). The field name chainHead is the schema placeholder (gaps G83); no value is invented when the store has none, and the envelope then refuses the event.
3. A restore raises dep.version.restored with seq only, as its schema lists.
4. Thread events (dep.thread.deleted, dep.thread.resolved, dep.thread.reopened, dep.comment.created) carry seq read at the time of the change, the same way.

Not decided here: the throttle rate of dep.commit.rejected (open question), the debounce wiring (PRO-072 criterion 2), and whether dep.session.* events belong to the control plane.

## Round 8 (2026-11-14, lane V-PRO-069-085 developer), status: proposed

1. Debounce wiring (PRO-072 criterion 2). The spec table gives the window as ten seconds per document (05 section 7). createKit now sends dep.document.changed through DocumentChangeDebounce, so the first change of a window is raised at once and the last change of a burst is raised when the window ends. The trailing raise uses an unreferenced timer in the running service (the window is real time). Spec default: the debounce's design as written in event-throttle.ts. Test: test/control-plane/pro-072-v-pro-069-085-debounce.test.ts (memory and PostgreSQL, 2 passed).
2. Receiver statements (PRO-070 criterion 5). The integration guide (apps/reference-host/docs/integration-guide.md, UX-090) already says to check the signature and to drop a repeated webhook-id. This lane ticked the criterion on that text and added a test that reads the guide. The owner may prefer that UX-090 own the text; the test would then move with it.
3. Not decided here: whether the debounce's trailing event should keep the chain head of the latest commit (it does, because the latest change is the one stored); the shutdown behaviour of the trailing timer (it is unreferenced and raises into the sink if the process lives on).
4. Still open, unchanged: PRO-069 criterion 4 for every event type (only the four lifecycle types are reachable from the running handlers; workflow and task events have no emitter yet).
