# 0421. The relying party's verifier, updates of the sealed PDF and the signature appearances

**Status:** proposed, 2026-11-18. Written while building FRW-055, FRW-056 and FRW-057 (lane w4). It follows ADR 0420. The owner has decided none of these points (docs/owner-decisions-2026-11-15.md has nothing on them beyond decisions 221 to 223, which leave the production library, key store, certificate and authority open). Each item takes the smallest reading that works; the owner may change any of them.

1. **One command for a relying party (FRW-055).** `services/signing-service/scripts/verify-final.ts <bundle.json> <sealed.pdf> --root <root>... [--anchor <file>]` checks the bundle (`verifyWorkflowEvidenceBundle`), every signature and time-stamp of the PDF against the roots the reader names, and, with the anchor file of ADR 0420 item 6, that the signed head is the bundle's chain at that `seq`. It lives in the signing service's package because it needs `pkijs`; it imports the history package's source by a relative path, so no dependency was added to `pnpm-lock.yaml`. It trusts no root of its own. The chain head printed in the certificate pages is not read from the PDF (that needs a PDF text extractor and a compiled certificate); FRW-055 criterion 2 stays open for that one check.
2. **What "in the chain" means for evidence (FRW-055).** A signing, a completion and a decline are anchored by a control commit, so each of their commitments must be the `evidenceHash` of a control commit of the segment. A view and a consent are not anchored and are not asked of the chain. When a control payload is erased (tombstone), an anchored item that cannot be found is reported as unchecked, not as a failure. A control commit that anchors evidence the bundle does not hold is reported (`unmatchedAnchors`) and does not fail the bundle, because an erased participant leaves exactly that.
3. **Bytes after the last signature (FRW-055).** A B-LT seal appends its validation data after the signature, so a signature that does not reach the last byte is normal. The verifier accepts a tail that holds a `/DSS` and no signature contents, and reports any other tail. It does not analyse what a later update changes; Acrobat's incremental-update analysis does.
4. **Updates of the sealed PDF (FRW-056).** The signing service's `POST /v1/extend` appends fresh validation data (a new DSS naming every signature the file holds) and a further document time-stamp. A request carries an idempotency key; the service keeps the results of served keys in memory. The sealed object is never replaced: each update is a further object `<workflow>.u<n>.pdf` under the tenant, written with Object Lock, found by listing and by number, and it must begin with the latest stored bytes; a base that is not the latest is `stale`. `GET /workflow/final` returns the latest. There is no table row for an update: the object and its hash are the record. The new expiry is the `notAfter` of the time-stamp authority's certificate in the new token. Nothing schedules the validation job or the renewal job yet (FRW-056 criterion 2).
5. **Signature appearances (FRW-057).** For each `signature` and `initials` field of the document at `completedSeq` the signing service draws a stamp annotation with its own appearance stream at the field's rectangle in `layout.json`, before the seal's signature, so the signature covers it and the equal pair of compiles is of the bytes before. The rectangle is converted from twentieths of a point from the top-left to points from the lower-left of the page box. The text is `Electronically signed`, the participant by name (else identifier) and the UTC date of the signing, or `Not signed` for a field without a signing record. It claims no identity. Helvetica is not embedded; characters outside Latin-1 are drawn as `?`. Fields that get no appearance are returned as diagnostics and written to the audit entry `workflow.appearance_diagnostics`; the seal is not held back. `layout.json` entries have no `key` (the published schema refuses it), so the key is joined from the document by the identifier.
6. **Not built.** The whole-file validation of `layout.json` against `LAYOUT_SCHEMA` in the document service (the schema is the export worker's, and no schema file is published under `spec/`). Images the participant adopted in an appearance. A row for the evidence bundle in 07 section 12 (FRW-055 criterion 6).
