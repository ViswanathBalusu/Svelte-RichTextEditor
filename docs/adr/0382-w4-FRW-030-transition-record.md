# 0382. Recording a workflow transition: order of the writes, the audit entry, the commit read back

**Status:** proposed, 2026-11-17. Written while building FRW-030 (lane w4). 12 §6.2 says every transition is recorded as a control commit. It does not say how the workflow row and the log write relate, which audit entry a transition leaves, or how a webhook learns the `seq`. Each item takes the smallest reading that works; the owner may change any of them.

1. **One path.** Every transition goes through `recordTransition` (`services/document-service/src/workflow/transitions.ts`). A route calls it and does nothing else to the lock or the state.
2. **The lock comes from `lockFor`.** The new state's lock (document state and `workflowActive`, FRW-029) is stored as one grants change. That change raises the grants revision and writes its `grants.changed` audit entry in the same transaction, and the room records the revision as a control commit with no steps (07 §9). A state whose lock `lockFor` does not decide (`correcting`, `completed`, `finalised`, `expired`) is refused with a `RangeError`: nobody takes a default by accident.
3. **Lock first, then the state.** The grants and the workflow row are written by two stores, so they are not one database transaction. The lock is stored first. A process that stops between the two leaves a locked document whose workflow is still in the old state. The caller repeats the transition: the lock is already in force, so no second revision and no second control commit are made, and the state moves once (the write is conditional on the state and revision that were read). The control commit has a deterministic identifier per revision. This is recovery by repeating the request, not by a background repair. A single transaction over both tables would need the grant store to share its transaction with the workflow store; that is a change to storage (BE) and is left open. FRW-030 criterion 3 stays unticked for that reason.
4. **A `workflow.transition` audit entry.** `grants.changed` does not exist for a transition that changes no lock (`sent` to `in_progress`). Every transition therefore also writes `workflow.transition` with the actor, the document, the server time and `{ from, to, rev }`. The kind is a proposed name.
5. **The commit is read back, when a room is open.** The route cannot know the `seq` of the control commit before the room writes it. `recordTransition` waits up to `controlWaitMs` for the commit of the new revision and returns its `seq` and the chain head at that moment. If no room is open, the room writes the commit when it next opens (07 §9) and the result carries no control commit: the webhook then carries `sentSeq`, the head at the send, and says so in its audit. Opening a room from the service to write the commit at once is the data plane's and is not built.
