# 0382. Recording a workflow transition: order of the writes, the audit entry, the commit read back

**Status:** proposed, 2026-11-17. Written while building FRW-030 (lane w4). 12 §6.2 says every transition is recorded as a control commit. It does not say how the workflow row and the log write relate, which audit entry a transition leaves, or how a webhook learns the `seq`. Each item takes the smallest reading that works; the owner may change any of them.

1. **One path.** Every transition goes through `recordTransition` (`services/document-service/src/workflow/transitions.ts`). A route calls it and does nothing else to the lock or the state.
2. **The lock comes from `lockFor`.** The new state's lock (document state and `workflowActive`, FRW-029) is stored as one grants change. That change raises the grants revision and writes its `grants.changed` audit entry in the same transaction, and the room records the revision as a control commit with no steps (07 §9). A state whose lock `lockFor` does not decide (`correcting`, `completed`, `finalised`, `expired`) is refused with a `RangeError`: nobody takes a default by accident.
3. **Lock first, then the state.** The grants and the workflow row are written by two stores, so they are not one database transaction. The lock is stored first. A process that stops between the two leaves a locked document whose workflow is still in the old state. The caller repeats the transition: the lock is already in force, so no second revision and no second control commit are made, and the state moves once (the write is conditional on the state and revision that were read). The control commit has a deterministic identifier per revision. This is recovery by repeating the request, not by a background repair. A single transaction over both tables would need the grant store to share its transaction with the workflow store; that is a change to storage (BE) and is left open. FRW-030 criterion 3 stays unticked for that reason.
4. **A `workflow.transition` audit entry.** `grants.changed` does not exist for a transition that changes no lock (`sent` to `in_progress`). Every transition therefore also writes `workflow.transition` with the actor, the document, the server time and `{ from, to, rev }`. The kind is a proposed name.
5. **The commit is read back, when a room is open.** The route cannot know the `seq` of the control commit before the room writes it. `recordTransition` waits up to `controlWaitMs` for the commit of the new revision and returns its `seq` and the chain head at that moment. If no room is open, the room writes the commit when it next opens (07 §9) and the result carries no control commit: the webhook then carries `sentSeq`, the head at the send, and says so in its audit. Opening a room from the service to write the commit at once is the data plane's and is not built.
6. **A transition that keeps the lock still raises a grants revision (2026-11-18).** 12 §6.2 says every transition is a control commit, and the room writes a control commit only for a new grants revision. A transition that changes no lock (`sent` to `in_progress`, a completion that moves the order on, `completed` to `finalised`) therefore raises a revision with nothing changed (`recordTransition`, `keepsLock`). The cost is that the grants ETag moves at each of these, so an owner who read the grants before a participant opened the document is told to read them again. A repeat after a stop between the revision and the state write raises a second revision for such a transition (the lock is not there to find in force), so its control commit can be written twice, once for each revision; the state still moves once. For a transition that changes the lock the repeat is clean, as in point 3. Making the anchor idempotent needs a key that the grants revision stores (an audit field or a column) or one transaction over both tables; both are storage changes (BE) and are left open, so FRW-030 criterion 3 stays unticked.
7. **Before it writes anything, a transition checks that its source state is still the workflow's (2026-11-18).** A transition that raises a revision and then loses the conditional write of the state would leave a control commit for a transition that did not happen. ecordTransition therefore reads the workflow row first and returns conflict when its state or revision is not the caller's; a race that starts after that read can still leave one such commit. It also reads the grants revision again when another change took it between its read and its write (two participants opening the document together).

8. **The repeat of a transition that keeps the lock finds its revision (2026-11-26; FRW-030 criterion 3).** Point 6 left a repeat after a stop raising a second grants revision, and so a second control commit. The fix is the storage change that point named: the revision a transition raises carries a key, `<workflow revision>:<state it leaves>><state it enters>`, in the new column `grant_history.transition_key` (migration `0099_frw_030_transition_key.sql`, an expand step, with a unique index over the document and the key where the key is set). `GrantStore.change` takes the key as `ChangeOptions.transition`; when a revision with that key exists it returns that state and raises nothing (the memory store keeps the same map). `recordTransition` passes the key of every revision it raises. The repeat then reports the first attempt's revision and reads its control commit back, the state moves once, and the control commit, whose identifier is fixed by the revision, is written once. A transition that changes the lock needed no key: its repeat finds the lock in force. A key never recurs for a document, because the workflow revision it names has moved on once the state has moved. Proposed, not an owner decision. The grants ETag still moves at each such transition (point 6).
