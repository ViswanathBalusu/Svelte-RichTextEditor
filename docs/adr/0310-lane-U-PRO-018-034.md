# ADR 0310: Close the socket on pagehide and reconnect by backoff (lane U-PRO-018-034)

Status: proposed

## Context

PRO-019 criterion 5 asks that a page which fires `pagehide` closes its socket, so that the page can enter the back/forward cache. The spec (05 §4) does not say what the client does when the page is shown again, and PRO-019 Notes record that "reopening is assumed".

## Decision (spec default, not an owner decision)

- `platform.ts` exposes an optional `onPageHide`, backed by the global `pagehide` event when the environment has one.
- `backend.ts` subscribes in `connect()` and removes the subscription in `close()`. On `pagehide` with an online session, the socket closes with code 1001 and the close is reported as a lost connection with `reconnect: 'backoff'`.
- The session is not ended. The client reconnects by its own backoff if the page stays alive. A page that enters the back/forward cache has its timers paused, so it does not reconnect until it is shown again.

## Consequences

- A hidden page that is not cached reconnects after the backoff delay, not on `pageshow`. A `pageshow` listener, which would reconnect at once, is not built.
- The close frame's code and the reconnect are checked through `connection.status` in `packages/backend-dep/src/pagehide.universal.test.ts` (Chromium, Firefox, WebKit). Whether a page enters the back/forward cache is not measured.

## Open

- Whether the client should reconnect on `pageshow` instead of by backoff.
- Round 2 (PRO-024 criterion 6): the rolling restart is ticked on the data-plane test `services/document-service/test/data-plane/be-022-rolling-restart.pg.test.ts`, not on the kit profile PRO-126. The owner decides whether the criterion requires that profile to run it. Until then the criterion is read as met by the behaviour, and the location is recorded here.
- Round 2 (PRO-030 criterion 1): the reset reasons `restore`, `migration` and `repair` are tested at room level (`packages/authority/test/pro-030-snapshot-reasons.test.ts`). The data plane forwards the reset unchanged, but only `import` is tested through the whole plane.

## Round 4: PRO-032 criterion 5 (unknown member of `access`), spec default

Status: proposed. The decision below is the spec default (05 §1 rule 3, PRO-005: ignore what is not known), not an owner decision.

- `packages/protocol/src/client/channel.ts` adds `knownAccess`, which keeps only the eight members of the `access` object in 05 §5.5 (`rev`, `asOfSeq`, `docRole`, `caps`, `scopes`, `leases`, `fill`, `restrictions`). `onAccess` applies it to `ch.opened` and to `perm.changed`, so the host never receives an unknown top-level member.
- Consequence: an unknown member is ignored, as PRO-032 criterion 5 is written. The earlier record (PRO-032 Notes, lane PRO-029-042) noted that the object was handed on unchanged; that is no longer the case.
- Open for the owner: whether a later protocol version's member should be kept and passed to the host rather than dropped. If so, `knownAccess` changes and the test in `access-unknown-field.universal.test.ts` changes with it.
- Nested unknown members (inside `scopes` or `leases`) are not stripped; the criterion is about the `access` object's own fields.

## Round 4: PRO-032 criterion 4 (region not listed), not closed

Criterion 4 stays unticked in this round. The mock backend (`packages/backend-mock/src/document.ts`) dispatches `perm.changed` straight after the commit that creates a region, so the window the criterion describes (the commit received, no `access` yet) cannot be reached through the mock. The planned route is a test hook in `backend-mock` that holds access deliveries, and a Playwright spec under `packages/element/e2e` that types into the region through the element. Until that exists the criterion has no browser evidence.
