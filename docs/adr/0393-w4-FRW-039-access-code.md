# 0393. The access code of a participant: registration, attempts, what verification changes

**Status:** proposed, 2026-11-18. Written while building FRW-039 (lane w4). 12 §6.1 and §7 say that an access code is verified by the document service and stored only as a hash, and give `auth.require` as the only example. They leave open how the code is registered, how many attempts are allowed and what "verified" changes. Each item takes the smallest reading that works; the owner may change any of them. The numbers in item 3 are design values, not measurements.

1. **Registration.** The host registers the code: `POST /documents/{id}/workflow/participants/{pid}/access-code` with `{ "code": text }` (method and path assumed, G95), needing `manage`, answered `204` with no body. Only a salt and the SHA-256 hash are stored (`registerAccessCode` of the authority; table `workflow_access_codes`, migration 0077). The host sends the code to the person in its own voice (12 §6.3). A participant whose `auth.require` does not list `access_code` is `conflict`. A new registration replaces the old and starts the count of wrong attempts again. It is allowed while the workflow is a draft, `sent`, `in_progress` or `correcting`.
2. **Verification.** `POST .../participants/{pid}/verify` with the code. The caller is a user whose token binds to `pid` (`wfp` and `sub`, FRW-038). The host's service credential and the owner are refused (`forbidden`): the point of the code is that the person knows it, and a credential that could prove it for them would defeat it. A correct code stores `verifiedAt` for the participant in a transition of the workflow (so the room gives them fill and tells them with `perm.changed` and `wf.changed`) and clears the count. Verification is once for the workflow: a later correct submission changes nothing. A wrong code is `forbidden`, raises `auth_failed` (with the participant, never the code) and writes a failed attempt to the evidence. A workflow that is not `sent` or `in_progress` is `conflict`.
3. **The limit.** 5 attempts in a window of 15 minutes for each participant, the correct one counted. Each attempt is counted before the code is compared, in one statement, so concurrent attempts cannot exceed the limit. The sixth is `rate_limited` whatever the code, with `retryAfterMs` (the time left in the window) in the problem and `Retry-After` in whole seconds; a refused attempt is not recorded as a wrong one and raises nothing. The window runs from the first attempt, and a correct code or a new registration clears it. 12 states no limit and no lockout policy.
4. **Until the code is given.** A participant who requires a code and has not verified is not active for fill (`fillActive` is false, so `access.fill.active` is false and their commits are refused with `read_only`), and `ch.opened.workflow.participant.state` is the word `unverified` (new, beside `active`, `waiting` and the rest). The component can show the code input from that word; the input itself (criterion 6) is the editor's. The signing ceremony is not built yet (FRW-044 to FRW-047), so its gate is the same `fillActive`.
5. **Evidence.** An attempt is one ledger row, item `access_code`, holding `{ ok, atMs }`, the `amr` of the token when it has one, and the address and `User-Agent` of the request under the tenant's capture setting. The code never appears in it. A `cc` has no code and no such item.
6. **`auth.require`.** Only `access_code` is accepted when a workflow is saved (`checkAuthRequire`); any other entry, a non-list, or another member of `auth` is `validation_failed`.
