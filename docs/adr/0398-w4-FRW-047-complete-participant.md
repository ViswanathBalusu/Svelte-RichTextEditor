# 0398. Completing a participant's part

**Status:** proposed, 2026-11-18. Written while building FRW-047 (lane w4). 12 §5.3, §6.2 and §8.1 step 4 name the check, the `rules` commit and the transition and leave the details below open. The owner has not seen this record.

1. **Route and caller.** `POST /documents/{id}/workflow/participants/{pid}/complete` (the operation `participantComplete` was already registered). The body is empty or `{}`; any member is `validation_failed`. The caller is a user token bound to `pid` (`wfp` and `sub`, FRW-038). The host's service credential does not complete for a person (`forbidden`), as for consent and signing. The answer is the workflow resource with its `ETag`, as for `decline`.
2. **What is checked.** The workflow is `in_progress` (a `sent` workflow is `conflict`: the first view moves it on, and the route does not invent one), and the participant is active (`fillActive`: not completed, not a `cc`, in the lowest open order, past an access code). Then `completionCheck` runs over the fields assigned to the participant's roles that are visible and enabled: static `required`, static limits and patterns, and the `require` and `validate` effects. 12 §5.3 says only "required fields and validations"; the participant's own fields are read, because later participants' fields are still empty. A participant of kind `approver` has no check: they own no fields.
3. **The refusal.** `validation_failed` (400). 12 names no code; the registry has `validation_failed`. Each failing field is one violation `{ path: "/fields/<key>", rule: "<code>" }`, where the code is `required`, a static code such as `pattern`, or `rule (<rule id>)` for a `validate` effect. A rule set that cannot be evaluated, or a spent budget, refuses with one violation at `/`, `rules_unavailable` (fail closed). The participant stays active and nothing is written.
4. **The `rules` commit.** One server-authored commit with origin `rules`, attributed to the participant, through the outbox. It writes the result of each formula field whose stored value differs and null for each hidden field that holds a value (`completionWrites`, `packages/authority/src/workflow/completion.ts`). Hidden and formula are decided under the completing participant's roles, with the server clock and the workflow's time zone. A hidden formula field is cleared, not computed. When nothing differs no commit is written. The commit identifier is derived from the participant, the send, the head the checks read and the steps, so a repeat of the same request holds one outbox item.
5. **A change in the room's outcome check.** P7 refuses a value change in a hidden field, which is what clearing is. `outcomeCheck` now lets a server-authored commit with origin `rules` set a field's value to null when it held one, without the fill rule (`packages/authority/src/permissions/outcome.ts`, tested by `packages/authority/test/frw-047.clear-hidden.test.ts`). A client commit, another origin and a non-null value get no such pass. P8 (server-set kinds) and the checks of readable values and of concurrent fills are unchanged. Known limit: the commit is attributed to the participant, so a sensitive hidden field the participant may not read (ADR 0019) still refuses the commit, and the completion is then `conflict` (`not_stored`).
6. **`completedSeq`.** The `seq` of the `rules` commit; when none was written, the head `seq` the checks read. The participant is then marked `completed` with it. The service does this in `recordCompletion`, which the FRW-031 code already provided.
7. **The control commit.** "A control commit" in criterion 2 is read as 12 §6.2's "every transition is a control commit" is built (FRW-030): a control commit is written when the transition changes the lock, that is when the grants revision changes. A completion that leaves the workflow `in_progress` changes no lock and so writes none; the last completion moves the workflow to `completed`, and the room records a control commit for it. The `rules` commit is in the chain in both cases. Whether a completion that changes no lock should still write a control commit is not decided here (the same as for `sent` to `in_progress`).
8. **Exactly once.** Retrying the request, or a stop between the `rules` commit and the transition, applies the commit once: the same request has the same identifier; after the commit is stored the document already holds the written values, so the repeat finds nothing to write, completes at the head and goes on to the transition. The test stops the workflow store once after the commit and repeats the request (memory and PostgreSQL). If the process stops after the transition and before the evidence row, the evidence row is not written: a second call answers as a completed participant and writes nothing. Not repaired here.
9. **A second call.** A participant who is `completed` gets the resource as it stands, with the same `completedSeq`; nothing is written, raised or recorded. This holds after the workflow has ended.
10. **Events and evidence.** `participant_completed`, then `participant_activated` for each participant of the next order, then `completed` for the last one, are returned by `recordCompletion` and raised by the route with the control commit's `seq` and chain head when the room wrote one in time, else the head's. One evidence row with item `completed` holds `completedAtMs` from the server clock and the connection's address and user agent (kept or dropped by the tenant's capture setting). The salted hash of the evidence does not enter the chain yet (ADR 0397 item 8).

Not decided: whether the hidden fields cleared should be only those assigned to the participant's roles (the rules can read roles, so a field hidden for one participant may be visible to another); whether an approver's completion should be a separate `approve` action in the embedding API (12 §10 names `/complete` only).
