# ADR 0340: lane V-FRW-019-036, round 2 (status: proposed)

Date: 2026-11-13. Scope: FRW-019 to FRW-036 (highest number first). Nothing was ticked in this round.

## Context

The round looked at the stories that the earlier lanes left blocked by a container, a browser or another package. Of FRW-036 down to FRW-032, every open criterion needs one of three things that do not exist in the repository:

1. A workflow route or service that raises events. `services/document-service/src/control-plane/` has webhook plumbing (`webhook-dispatcher.ts`, `webhook-envelope.ts`, `webhook-deliveries-pg.ts`, `webhook-egress.ts`, `webhook-signing.ts`) but no route that calls `send`, `decline`, `void`, `correct`, `resume`, `remind` or `expire`.
2. A room that reads the workflow. `packages/authority/src/room/room.ts` `open()` (line 649) builds `ch.opened` from `head`, `incarnation`, `inflight` and `access` only. It has no workflow provider, so `workflowView` (`packages/authority/src/workflow/state-view.ts`) is not sent. Adding it means a new `RoomInit` member and a change to `room/types.ts`, which other lanes also edit.
3. A decision about event type names. `webhook-envelope.ts` accepts only types matching `^dep(\.[a-z][a-z_]*)+\.v[1-9][0-9]*$`, with a version suffix. The workflow events of `packages/authority/src/workflow/events.ts` are `dep.workflow.<name>` with no version. A workflow event therefore cannot pass `toCloudEvent` as the code stands. 12 §10 does not give a version. The spec default is to keep the names of 12 §10 and to add no version, but the schema in `spec/dep/webhooks/` requires one. This is an open question for the owner and the protocol owner, not decided here.

## Decision

- No criterion of FRW-032 to FRW-036 is ticked in this lane: each depends on one of the three gaps above.
- The workflow event type question (point 3) is recorded as open. The spec default (names of 12 §10, prefix `dep.workflow.`, version suffix to be decided) is not applied to the envelope.
- Wiring `workflowView` into `ch.opened` (FRW-035 criterion 1) is left to a lane that may change `room/room.ts` and `room/types.ts`. It needs a `RoomInit` workflow provider and a test in `packages/authority/test/` that opens a channel on a workflow document.

## Consequences

- No new code in this round. No tests were added or run for these stories.
- Next steps, when the owner or the main session agrees them: (a) the event type naming and its version in `spec/dep/webhooks/`, (b) a workflow route in document-service that calls `sendWorkflow`, `correctWorkflow` and the rest and writes the control commit (FRW-030), (c) the room provider for `ch.opened` and `wf.changed`.

## Round 5 (2026-11-14, status: proposed)

Scope: FRW-031, FRW-022 and FRW-021, taken from the top of the range. Three tests were added in `packages/authority/test/`, all run in Node.js 22.18 with vitest, and no product code changed.

Decisions taken where the spec is open (each is the spec default unless stated):

1. The room's refusal of a fill from a participant who is not active is `permission_denied` for a `sent` or `in_progress` workflow, whose participants are waiting or completed. For a `declined` or `voided` workflow the room refuses with `read_only`, because its document-state check runs before the fill check (`room/room.ts`, `checkFill` path). 12 §4.2 P7 and FRW-022 criterion 4 say `permission_denied`. The code is left as it is: changing it would change the existing `read_only` contract that other tests pin. Owner or protocol decision: which code a locked document gives to an inactive participant. FRW-022 criterion 4 stays unticked until it is decided.
2. A `paused` participant state is not in the workflow states of 12 §6 (`WORKFLOW_STATE_NAMES`). No test is written for it, and FRW-022 criterion 4's "paused" case is recorded as not applicable until the spec names the state.
3. The room is given `documentState` and `workflowActive` from `lockFor`, and `participantActive` from `fillActive`. The tests compose the pure functions the way the workflow service will. They do not make the service exist. The stories keep the standard of the 2026-11-13 review: no criterion that describes an action through an endpoint is ticked on the pure functions alone. FRW-031 criterion 1 is ticked because the room itself refuses and accepts the fills (its evidence is the room, not a function alone).

Files: `packages/authority/test/frw-031.activation-room.test.ts` (4 tests), `packages/authority/test/frw-022.inactive-participant.test.ts` (4 tests), `packages/authority/test/frw-021.sent-lock.test.ts` (3 tests). Stories edited: FRW-031 (criterion 1 ticked, Evidence and Notes), FRW-022 (Evidence and Notes, criterion 4 unticked), FRW-021 (Notes, criterion 3 unticked).

## Round 6 (2026-11-14, status: proposed)

Scope: FRW-024 (stories taken from the top of the range; FRW-027 and FRW-023 were assessed and not closed, see below). One test file was added and no product code outside the rules package changed.

Decisions taken where the spec is open (each is the spec default unless stated):

1. A rule is saved as the JSON tree it was opened from, with only the members the builder edits replaced; members the builder does not read (such as `ext`) are kept. This is the reading of FRW-024 criterion 2 ("saved without change, the JSON tree is identical"). Not an owner decision.
2. The sentence view covers only the comparison condition (`==`, `!=`, `<`, `<=`, `>`, `>=`) over a field or a literal, with field effects (`show`, `hide`, `require`, `enable`, `disable`). Any other rule has no sentence and the interface shows its JSON. The spec's sentence templates are interface strings (12 §11), so the wording here is a proposal.
3. The builder refuses a rule set that does not compile with the authority's compile problems (`compileRules`), and refuses the 501st rule with `rule_limit` before compiling. The 500 limit is `LIMITS.rules` (I15).

Files: `packages/rules/src/builder.ts` (new), `packages/rules/test/frw-024.builder.test.ts` (new, 15 tests, vitest, Node.js 22.18). Story edited: FRW-024 (criterion 2 ticked; Evidence and Notes).

Not closed this round, with reasons: FRW-027 criteria 3 to 6 need the workflow route and its control commit, the `sent` version and the webhooks, none of which exist in the repository (`packages/authority/src/workflow/send.ts` is pure). FRW-023 criteria 1 to 6 need a live field editor in `packages/ui` or `packages/element`; no code there sets `aria-invalid`, `aria-required` or the "n of m" count, so it is larger than this round.

## Round 7 (2026-11-14, status: proposed)

Scope: FRW-020 and FRW-019 (the only stories of the range not taken in earlier rounds). One test file was added, `packages/authority/test/frw-020.fixtures.test.ts` (3 tests, vitest, Node.js 22.18), and no product code changed. FRW-019 was checked, not changed, apart from its Notes.

Decisions taken where the spec is open (each is the spec default unless stated):

1. The fixtures' `rules` cases run through the authority's rule gate (`ruleGate`, `packages/authority/src/room/rules.ts`) with no instant, because the gate evaluates without one. The one case that sets `given.now` is not judged. Not an owner decision.
2. Commit-time refusal of invalid rule sets. `RULE_INVARIANTS` refuses on commit only `unknown_field` (as `rule_unknown_key`) and `cycle` (as `rule_cycle`), both with `invalid_op` and I14. The other problem codes of the rules package (`bad_shape`, `type_mismatch`, `conflicting_rules`, `duplicate_rule`, `unknown_effect`, `routing_effect` and others; 37 negative fixture cases in all) are not refused on commit. The gate fails closed on them, so the fields of such a rule set cannot be filled. The spec default would refuse every invalid rule set on commit, but 12 §5.2 does not name the code or the invariant for those, so the default is not applied here. Proposed: map every rules problem to `invalid_op` under I14 (or I11 for patterns, as `pattern_unsupported` does), and let the owner confirm. Not applied in this round because it changes what a commit may contain, which is a product decision.
3. Criterion 2 of FRW-020 stays unticked. Scope it as: the 30 judged `rules` cases agree with the fixtures and the 37 negative cases fail closed behind the authority; the expression, pattern and value cases and the instant case are not run behind the authority.
4. Criterion 3 of FRW-020 stays unticked. No `rules` profile exists in `packages/tck/src/profiles/index.ts`. Proposed shape, for the kit owner: a profile `rules` whose scenarios create documents with `rule_def` nodes and check fills through `sync.reject` (the `fields` profile in `packages/tck/src/profiles/fields.ts` is the pattern), with the fixture identifiers reported by `runFixtures`. Owner or kit decision.

Files: `packages/authority/test/frw-020.fixtures.test.ts` (new). Stories edited: FRW-020 (Evidence, Notes; In progress line added and removed), FRW-019 (Notes only; all criteria already ticked).

Not run: the browser project for `packages/rules/src/fixtures/fixtures.universal.test.ts` was not rerun in this round; the 2026-11-13 run is cited in FRW-020's Notes.
