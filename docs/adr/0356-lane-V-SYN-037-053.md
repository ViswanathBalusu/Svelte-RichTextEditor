# ADR 0356: Lane V-SYN-037-053, round 2 decisions

Status: proposed. Owner decisions are the owner's; where the spec leaves a question open, the spec default is used and named here.

## SYN-043: the room's choice to send `sync.check` (criterion 1)

- Spec 04 §13 says the room MAY send `sync.check` when it writes a checkpoint. Default used: yes. The document service's room host sends it after each checkpoint it saves, to the channels that see the full document (`services/document-service/src/data-plane/room-host.ts`, `#sendCheck`). The switch is the `syncCheck` setting, on by default (`settings.ts`).
- Cost: the host hashes the envelope of each checkpoint (SHA-256 of the canonical text, in the checkpoint worker's path). No measurement exists on the reference machine; the cost is not claimed as met for SYN-015.
- Hash convention. Two definitions of "canonical form of the durable document" exist:
  1. The service and the engine hash the whole envelope `{cdm, requires, doc}` (`contentHash` in `recovery.ts`; `documentHash` in the engine's session). This is what goes on the wire and what criterion 1 is tested against.
  2. `packages/authority/src/room/check.ts` (`syncCheck`, `documentCanonicalHash`) hashes the bare document node. It has no caller outside its own tests.
  Default used: convention 1 for the wire, because both ends already agree on it. Convention 2 is left in place; a later round should remove it or align it. Owner decision not needed; this is a consistency fix for the maintainer.
- Test: `services/document-service/test/data-plane/syn-043.v-syn-037-053.check.pg.test.ts` (PostgreSQL in the shared container).

## Open items for the main session (not decided here)

- Where a diverged client reports the event after `sync.check` (SYN-043 Open questions). Unchanged.
- Whether the check should hash the envelope or the document (convention 1 vs 2 above). Stated as a default; the spec wording "canonical form (03, section 2) of the document" should be read by the owner or spec maintainer.

## SYN-039: heavy work in worker threads (criterion 1, partly)

- Covered over PostgreSQL: the checkpoint write (`checkpoint` task), the content replay after a checkpoint (`materialise`) and the conversion of content to its stored form (`encode`, through `RoomHost.encode`). Test: `services/document-service/test/data-plane/syn-039.v-syn-037-053.workers.pg.test.ts`.
- Not covered: a comparison. The room has none outside the divergence hash, which the checkpoint task computes. `recovery.ts` (`rebuild`, `verifyCheckpoint`) is a command-line tool that runs its work inline (pool size 0) and is not the room's loop.
- Default used: the criterion stays unticked until the owner or the spec maintainer says whether the recovery tool's work must also run in a worker. No change of product code is made for it in this round.
