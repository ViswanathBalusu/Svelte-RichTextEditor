# ADR 0312: Lane U-PRO-052-068 decisions (proposed)

Status: proposed. Owner decisions stay the owner's. The choices below are the spec's defaults or the
smallest reading of it, recorded so that the owner can confirm or change them.

Context: round 2 of the protocol lane (stories PRO-052 to PRO-068). Three stories were closed where
a real test could prove the criterion: PRO-053 (criterion 3, region leases), PRO-064 (criterion 4,
export events) and PRO-068 (criteria 1 to 3, webhook routes over HTTP).

## 1. The lease identifier is the lease's ETag

The published heartbeat (`PUT .../regions/{rid}/lease`, `If-Match` required) and release
(`DELETE`, `If-Match` optional) name no lease identifier in their paths (spec/dep gaps G57, G66).
Decision (default): the lease's ETag is its identifier in quotes, `"<id>"`. A heartbeat finds the
lease in force for the region and the caller, and its `If-Match` must carry that ETag (412 when it
does not, 428 when it is missing). Release checks the tag only when one is sent.

Owner: confirm, or name the field the published contract should carry.

## 2. The holder is the host's `sub`

The `Lease` body's `holder` is the host's `sub` (D42). The stored holder is the user's surrogate, so
the response maps it through the same principal names that `GET .../regions` uses.

## 3. A service credential holds no lease

A service credential passes every gate (`gate.ts`), but it has no user to hold a lease. It is
refused on acquire and heartbeat (`forbidden`). On release it may break a lease, which is what a
`manage` holder may do.

## 4. The PostgreSQL grant store keeps the lease's identifier and acquisition time

`region_leases` already has `lease_id` and `acquired_at`, but the store wrote a fresh identifier and
`now()` on every write. A heartbeat would then restart the eight-hour maximum (PRM-044). The store now
writes the authority's identifier and acquisition time and reads them back. A legacy caller that
omits them gets a generated identifier and `now()`, as before.

## Open

- A break (`DELETE` by a `manage` holder of another user's lease) is a control change. The
  `lease.break` audit entry (authority `control-audit.ts`) is not recorded by the lease routes yet.
  PRO-053 criterion 1 and the audit trail are not claimed here.
- The `perm.changed` that the room sends when a lease expires (PRO-053 criterion 4) needs the real
  data plane's expiry timer; the stub data plane has none.
- `leases` in the discovery `features` list is set by configuration (`DOCEDIT_FEATURES`); the
  routes are not gated on it server side. Whether a server that does not announce `leases` should
  refuse the routes is for the owner.

## 6. Named versions over HTTP without the history package (PRO-054)

Status: proposed. Lane U-PRO-052-068, round 4 (2026-11-13).

- `GET` and `POST /documents/{id}/versions` are built in `src/control-plane/versions-routes.ts` on
  the version store (`PgVersionStore`, and `MemoryVersionStore` in `src/storage/versions-memory.ts`).
  The rules of `@docedit/history` (`createVersion`) are repeated there, because the package is not a
  dependency of `services/document-service`. The `edit somewhere` check is the matrix's row
  `version.create`, read by `authorise`, with the document's regions and grants at the head.
- The list holds named versions only (kind `named`); the other kinds are stored and not listed.
  It is a cursor list whose cursor names an offset.
- The wire `Version` is `{ seq, kind, name, note }`, as `spec/dep` names it. The creator and the
  time are stored (`createdBy` is the surrogate, `createdAt` the server time) but not sent. Owner:
  confirm whether `Version` should name `createdBy` and `createdAt`.
- A repeated creation for the same `seq` and kind returns the stored version with status 200 and
  sends no notice (HIS-007 criterion 5). A new one is 201 and sends `dep.version.created.v1` and a
  `version.created` notice.
- Open: `services/document-service/package.json` does not list `@docedit/history`. Until the main
  session adds it, PRO-054 criterion 1 (filters and grouping), PRO-055 and PRO-056 stay open.

## 7. Comment activity needs a position in the log (PRO-058 criterion 3); not decided here

Status: open question, not decided. Lane U-PRO-052-068, round 4 (2026-11-13).

- `GET /documents/{id}/activity` is keyed by `seq`, and the read marker is a `seq`. A comment has a
  creation time (`comments.created_at`) and no `seq`, so "comment activity since the marker" has no
  position to compare with the marker. The spec does not say how a comment takes a position.
- Options for the owner: record the head `seq` on each comment when it is made; or derive the
  position from the time of the nearest commit at or before the comment. The spec default is not
  stated, so neither is adopted. No code changes for this criterion.
