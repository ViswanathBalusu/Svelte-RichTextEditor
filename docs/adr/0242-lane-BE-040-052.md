# ADR 0242: Open choices of the asset lane (BE-040 to BE-052)

Status: proposed. Owner decisions remain the owner's; each choice below says what the code does now
and what the spec states.

## Context

Lane BE-040-052 built the control plane's asset resolve route (`POST /documents/{id}/assets/resolve`,
`services/document-service/src/control-plane/asset-routes.ts`). Row 7 of 07 §12 allows `asset.read`
with `view` on a document the asset is attached to. BE-044 Notes say read access before the first
attachment is not stated. The `doc_assets` table of BE-044 is not built.

## Choices

1. **Meaning of "attached" (BE-045 criterion 1, PRO-062).** Without `doc_assets`, an asset counts as
   attached when it is referenced in the caller's projection of the content at the head (SR-C4, ADR
   0019). Preserved fragments count only for a caller who sees the whole document (SR-C1). Proposed:
   when BE-044 lands, attached means a `doc_assets` row for the document and a reference in a scope
   the caller can see.
2. **The uploader's own unreferenced upload (BE-045 criterion 1).** The route also resolves a ready
   asset that the caller uploaded for this document, even when no content references it yet. This is
   not in row 7 of 07 §12. It lets the editor show an image between `asset.ready` and the commit that
   references it (PRO-096 criterion 1 resolves the URL after `asset.ready`). Other callers, viewers
   included, never get such an asset. Quarantined, processing and failed uploads are never resolved.
   The test is `services/document-service/test/control-plane/routes.assets.test.ts` (the owner's
   `loose` upload). Proposed: keep this; if the owner decides against it, drop the `mine` branch so
   that only referenced assets resolve, and the editor shows the image after its commit.

## Consequences

Until BE-044 is built, removing an image from the content stops it resolving for every caller except
its uploader, so earlier versions do not render their removed images (BE-044 criterion 5 is open).
