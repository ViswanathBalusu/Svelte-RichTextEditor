# 0397. The sign endpoint: one server-authored commit

**Status:** proposed, 2026-11-18. Written while building FRW-046 (lane w4). 12 §8.1 step 3 and §10 name the route and the commit and leave the request, the answer and several details open. The owner accepted the workflow design ADRs as a set (decision 184); this record is new and has not been seen by the owner.

1. **Request and answer.** `POST /documents/{id}/fields/{fid}/sign` takes `{ asset, mode }` and nothing else (a member such as a hash or a date is `validation_failed`), and answers `{ field, value, seq, chainHash, dateSigned? }`. The operation carried a placeholder body; the shape is proposed here. The caller is a user token bound to a participant (`wfp` and `sub`). The host's service credential does not sign for a person (`forbidden`).
2. **Order of checks.** The workflow runs (`sent` or `in_progress`), the field exists, the P7 conditions hold (`checkSignConditions`: kind, assignee in the participant's roles, active by `fillActive`, not read-only, visible and enabled under the rules), the consent stands (`consentVerdict`, ADR 0395), the image is the signer's own and ready (`adoptSignature`, ADR 0396). A failure of the P7 conditions or the consent is `forbidden`; a field that does not exist is `not_found`; an image that is not ready or has failed is `conflict`; a bad `mode` or identifier is `validation_failed`. Every check comes before the write, so a refusal writes nothing.
3. **The commit.** One step commit through the outbox, origin `sign`, attributed to the participant's surrogate: an attribute step for the field's `{ asset, mode }` and one for each `dateSigned` field assigned to the same role. A later signing by the same role sets those fields again, so the date is that of the last signing (12 §8.1 says "sets every `dateSigned` field assigned to the same role"; whether a later signing overwrites is not stated, and this is the reading that needs no extra state).
4. **The date.** `signedDate(now, workflow.timeZone)`: the server clock in the workflow's zone. Nothing the client sends reaches it.
5. **No `head` precondition.** The outbox request carries the grants revision, the document state and `workflowActive`, but not the head. A prefill carries the head. For a signing it cannot be used: after a workflow transition the room holds a control commit it has queued and not yet written, so its next sequence number is ahead of the stored head, and a request carrying the stored head is refused as `conflict` although nothing changed. Observed with the real data plane on memory and PostgreSQL: after the first signing the room's tentative `seq` was 2 and the log's head 1 for at least six seconds. That is the room's behaviour, outside this lane, and is reported. The consequence is a window between the checks and the apply in which another commit could change what the checks read (a rule that hides the field, for example). The grants revision and the lock are still checked by the room.
6. **Idempotency.** The operation now accepts `Idempotency-Key` (`idempotencyKey: true` in the definition; `spec/dep` regenerated). Without a key too, the commit identifier is derived from the field, the participant, the image, the mode and the send (`sentSeq`), so the outbox holds one item for one request. A request that finds the field already holding the same value writes nothing and answers with the first commit; a different image for a signed field is `conflict`.
7. **Evidence.** After the commit is stored, one `signed` evidence row holds the `seq`, the chain hash of that commit (`chainHeadAt`, or the head's chain head when the commit is the head), the field key, the mode, the time and the image hash. A repeat records the row only if the first attempt stopped before it did. `field_completed` is raised with that `seq` and chain hash.
8. **The hash in the chain.** The evidence names the signing commit's `seq` and hash, so the salted hash of the evidence cannot be in that commit. It enters the chain with a later control commit, which nothing writes yet (ADR 0391 item 3).
9. **Assets.** `assetRefsIn` (data plane) now names the asset of a `{ asset, mode }` value, in a field node and in a `value` step, so that the room accepts the reference (invariant I4) and attaches the image to the document with the signing commit.

Not decided: the answer when a signature field is signed again after a correction (the send number is in the commit identifier, so a new send gives a new commit); whether the sign route should hold the whole signing of a document in a single commit for several fields; the room's queued control commit (item 5).
