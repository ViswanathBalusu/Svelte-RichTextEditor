# ADR 0243: Open choices of the webhook lane (BE-055 to BE-057)

Status: proposed. Owner decisions remain the owner's; each choice below uses the spec's default or
has no default and is left as an input.

## Context

Lane BE-053-065, round 1, built the webhook dispatcher (`webhook-dispatcher.ts`) and the egress proxy
(`webhook-egress.ts`) on top of the envelope, signing and subscription modules that already existed.
The specification or the published contracts leave the points below open.

## Choices

1. **Rejection throttle rate (BE-055).** The spec gives no rate for `dep.commit.rejected.v1`. The
   dispatcher takes `rejectedThrottle` as a required input with no default. Tests use test values.
   Proposed: the owner sets the rate in configuration.
2. **Redirect bound (BE-056).** The spec gives no number of redirects. `EgressProxy` takes
   `maxRedirects` as a required input with no default. Proposed: a small fixed value set by the owner.
3. **Refused address categories (BE-056).** Refused: unspecified, loopback, private (RFC 1918,
   carrier-grade NAT 100.64/10), link-local, the metadata address (IPv4 169.254.169.254 and IPv6
   fd00:ec2::254), multicast and reserved; IPv4-mapped and NAT64-embedded IPv4 by the address carried.
   The PRO-071 list is not in the repository. Proposed: check this list against PRO-071 when it is
   published.
4. **Test ping event name (BE-057).** `dep.webhook.test.v1` is a placeholder. The published catalogue has
   no test event. Proposed: PRO adds one; until then the placeholder stays marked by `test: true`.
5. **Replay window (BE-057).** The spec does not state one. Replay covers every stored row. Proposed:
   the owner states a window; the store then drops older rows.
6. **Network policy (BE-056 criterion 4).** The proxy as the only route out is deployment
   infrastructure. Not built here. Proposed: the infrastructure lane adds egress rules that allow only
   the proxy.
7. **Secret source (BE-057 criterion 6).** Secrets are held in the subscription store. A secret store is
   not built. Proposed: the secret store is a separate port, decided with SEC-057.

## Consequences

The delivery rows are in memory. A PostgreSQL table, the PRO-071 retry schedule and the composition
wiring (including a timer for `DocumentChangeDebounce.flush`) are not built. Stories BE-055 to BE-057
record these in their Notes.

## Search design (BE-053, spike; desk design, no measurement)

Status: proposed. Written by lane BE-053-065 (round 2) from the spec, without the one-week spike's measurements. No figure below is measured. The indexer's extraction and index are in `services/document-service/src/control-plane/search-index.ts` (BE-054).

### Full-text search or a search engine (criterion 1)

PostgreSQL full-text search (a `tsvector` column, a GIN index, `ts_rank`) runs in the database the service already needs. Its entries commit with the checkpoint that produced them, so a search never lags a committed checkpoint by more than the indexer job. It adds no service to run, which matters for a self-hosted install. Its ranking is less tunable than a search engine's (no typo tolerance, no facets, limited language analysers), and index updates share the primary's capacity.

A search engine gives better relevance control, separates search load from the commit log, and can index asynchronously. It costs a second service, a second copy of the text, a sync path that can fall behind, and a second tenant-isolation surface.

The spec gives no size at which a search engine becomes necessary, and this design does not invent one. The trigger is a measured one: move when the search p95 measured by the BE-058 harness (or by a search-specific run) misses its target, or when the owner requires a relevance feature that PostgreSQL full-text search cannot give. Criterion 1 therefore stays open in BE-053 until such a measurement exists.

### What is indexed and the query and result shape (criterion 2)

- Indexed: text extracted from each checkpoint after it is written (BE-054), per document and per visibility class (ADR 0019, SR-M5). Text inside preserved content (ADR 0017) is not indexed. Only text is indexed; no marks, attributes or assets.
- Query parameters: `q` (required; tokens of letters and digits, lower-cased) and `limit` (required, positive integer; the spec gives no default). The tenant comes from the credential, never from the query.
- Result shape: a list of `{ doc, seq, score }`, one entry per document, best readable entry first, ties by document identifier. No total count is returned, because a count reveals that a hidden match exists. The class of a match is not returned.

### Permissions in results (criterion 3)

`GET /search` is for service credentials only (05 §6.2). The host's catalogue permissions apply: the host decides which documents a user may see. Where a credential names an acting user, the index returns only entries whose class that user may read (ADR 0019), so a match inside a hidden region is not returned. Two checks are needed and both are the composition's (not built): the document-level `view` grant of the acting user, and the class filter. A document the user cannot view produces no hit and no count. A result reveals a document identifier, a sequence number and a score; it reveals no text, no class name and no hidden match. Open: whether a score based on a restricted class can leak its size. The score is the occurrence count of the readable class only, so it does not, but this must be checked in the route test.

### Ranking and its test (criterion 4)

Ranking in the in-memory index: every query token must occur (AND); the score is the total number of occurrences of the query tokens in the best readable entry of the document; ties are broken by document identifier. The PostgreSQL implementation, if used, is `ts_rank` over the same tokens and must agree on which documents match, not on the order of ties.

Tests: `search-index.test.ts` (fast-check properties for tenant isolation, class filtering, purge, the limit, and the ranking order on fixtures). Not built: a relevance fixture set with expected orders written by people, and a comparison run against PostgreSQL full-text search. Criterion 4 is met for the ranking approach and its tests as the in-memory index implements them.

### Tenant isolation and purge (criterion 5)

Every key includes the tenant: the in-memory index keys entries by `[tenant, doc, class]`, and `search` filters on the tenant before anything else. No cache exists. In PostgreSQL, the search tables carry the tenant column in their primary key and in every index. A purge (HIS-038, HIS-040) deletes the document's rows by `(tenant, doc)` in the same transaction as the purge record, so a purged document leaves the index before the purge completes. In the in-memory index this is `SearchIndex.purgeDocument`, which is tested. The purge pipeline that calls it is not built.

### Open items

- The relevance fixtures and the PostgreSQL comparison run (criterion 1 and 4).
- The size at which a search engine is needed: a measurement, not a number.
- Index rebuild after a restore: rebuild from checkpoints, which is cheaper to specify than to replicate; not decided here.

## Internal bus (BE-059, decision; desk comparison, no measurement)

Status: the recommendation was accepted by the owner on 2026-11-15 (decision 136, [owner decisions](../owner-decisions-2026-11-15.md): "Valkey streams"). Written by lane BE-053-065 (round 2); recorded as decided by lane w5, 2026-11-18. No figure below is measured. The spec default is not stated in 06 §16 (it lists the choice as open), so this record proposes one and gives its reasons.

### The candidates on the four axes (criterion 1)

- Ordered per-room streams. Redis streams: one stream per room (or a shared stream partitioned by room key), entries ordered by an ID that the server assigns; the order within a stream is total. NATS JetStream: one stream with a subject per room (`room.<id>`); order is total per subject, and each message carries a stream sequence. Both give per-room order; neither gives it across rooms, which the design does not need.
- Gap detection. Neither system detects a gap in the application's own sequence for the room. Both designs therefore carry the room's `seq` in the message and check it at the receiver (BE-062 criterion 1). With NATS, the stream sequence also shows dropped messages to a consumer, which helps a forwarding node. With Redis streams, a consumer gap has to be found by comparing IDs or the application sequence.
- Recovery after a gap. The authoritative copy is the commit log in PostgreSQL (ADR 0001). A forwarding node that detects an unrepairable gap closes the channel with `unavailable` (BE-062 criterion 3), and the client resumes from the log. So the bus does not need to be a durable log for correctness.
- Operating cost. Redis is already required by BE-063 for presence and rate-limit counters, and that spec says it may be lost without losing data. Adding streams to that instance adds no new system. NATS is a second system to run, secure and monitor, and its JetStream persistence is a second durability setting to tune.
- Footprint for a self-hosted install. Redis streams add nothing where Redis is present. NATS is a small single binary and runs well on its own, but it is one more component in the install guide and in the support matrix.

### Recommendation (accepted: owner decision 136)

Redis or Valkey streams, because BE-063 already requires Redis or Valkey and the install then has one optional helper service instead of two. The reasons are the footprint and the operating cost, not the throughput, which has not been measured. NATS is the alternative if the bus must carry load that Redis's single-threaded stream handling cannot carry, or if a later requirement needs a durable bus with per-subject acknowledgements. Choosing NATS later costs one adapter behind `Bus`.

Revisit this record if the BE-058 harness or a stage 2 run (BE-066) shows that the bus is the limit.

### The protocol is unaffected (criterion 2)

As 06 §16 says, the choice is internal. Clients see the same messages whichever bus carries them; the wire protocol (05) and the commit log are unchanged. A forwarded channel delivers the messages of the owner (BE-062 criterion 1).

### The `Bus` interface (criterion 3, not checked)

BE-002 lists `Bus` among the named adapter interfaces, but no `Bus` interface is declared in `services/document-service/src` or in `packages/authority/src` or `packages/backend-dep/src` (checked by search on 2026-11-13). The interface cannot be checked against the choice until it exists. This record does not change any interface. If the interface is written, it must allow an ordered per-room stream with a sequence on each message and an announcement that may be lost (BE-063 criterion 5).

### Open items

- ~~The owner's choice between the recommendation and NATS.~~ Settled: Valkey streams (owner decision 136, 2026-11-15). The product is Valkey, not Redis, in every document; a Redis server that speaks the same stream commands may stand in for it.
- A measurement of the bus against the stage 2 targets (BE-066).

## Connect hint and node addresses (BE-061, choices; proposed, not built)

Status: proposed. Written by lane BE-053-065 (round 4) from the spec and the storage ports. The owner has not chosen. Nothing here is built: the connect route (`GET /documents/{id}/connect`) does not exist.

1. **Where a node's WebSocket address comes from.** `NodeLeaseStore` (`storage/types.ts`) holds node names and liveness only. Options: (a) an address column on the node's lease row, written by the node at start from its own configured public address, so the hint follows the lease; (b) a configuration map from node name to URL, read at start. Proposed: (a), because a node that moves updates its own row and no other node or file needs changing. Either option needs a configuration variable in `config.ts`, which is outside this lane.
2. **Who owns a document.** The head row of a document carries `owner` and `epoch` (`LogHead` in `storage/types.ts`), so the connect route can read the owner from the head. Proposed: when the head has an owner whose lease is alive, the hint names that owner's address; otherwise the hint names the host that `routeDocument` picks over `liveRoomHosts` (06 §2.1, the spec's default for a document with no recorded owner).
3. **The hint is not ownership.** The hint carries no epoch and grants nothing. The channel still wins ownership through the epoch check of BE-017, and a channel that lands on a non-owner is forwarded (BE-062), so a stale hint costs latency only.
4. **Access.** The route answers `forbidden` to a caller without `view` (BE-061 criterion 4). The owner or a host decides whether the route is in 05 section 6.2; it is absent there today (Open questions).

Open items: the owner's choice for points 1 and 2; the route itself; BE-062 forwarding, which the stale-hint criterion needs.
