# ADR 0315: decisions of lane U-PRO-103-119 (conformance kit against the reference service)

Status: proposed. Owner decisions are the owner's; each item below names the spec default used.

Date: 2026-11-13.

## Context

Lane U-PRO-103-119 closes the stories PRO-103 to PRO-119 where a criterion was blocked on a
container, PostgreSQL or a browser. This record lists what the lane decided or found open.

## Decisions taken in the lane

1. **Discovery and `welcome` announce the same features.** 05 §1 rule 4 requires that optional
   behaviour is announced "in discovery and in `welcome`". The reference service announced
   `exports` and `assets` in discovery when it runs with PostgreSQL (`externalWorkers` defaults to
   true with a database), but the data plane's session features did not include them, so every
   `ch.open` was refused with `unsupported_feature` ("not announced: exports, assets"). The fix is
   in `services/document-service/src/server.ts`: the data plane receives the discovery list.
   Spec default: rule 4, as written. No owner decision is involved.

2. **Test mode shortens the data-plane heartbeat to 2 seconds.** `testDefaults` in
   `services/document-service/src/data-plane/index.ts` sets `limits.heartbeatMs` to 2000 when the
   test-mode switch is on (BE-079, ADR 0042 item 9). The value is a test value, not a spec figure;
   it is announced in `welcome`, so clients follow it. Only test mode changes it.

## Open questions (not decided here)

3. **Close code of a silent peer.** 05 §4 says a side that hears nothing for two intervals "closes
   the connection". 05 §5.7 lists the close codes but does not say which one a silent peer gets.
   `session.ts` ends the socket with `terminate()` (ADR 0035, no close frame), so the peer sees
   code 1006. The kit (`core.session.silence`) expects a code of 05 §5.7. Proposed default: keep
   `terminate()`, and state in 05 §4 that a silent peer's connection ends without a close frame.
   The kit records it as a known difference until the owner or SYN decides.

4. **Token lifetime in test mode.** `TEST_TIMERS.tokenLifetimeS` is 60 seconds. PRO-109 criterion 3
   asks for "within seconds". 60 seconds is not seconds. Proposed default: 5 to 10 seconds, to be
   set when the kit's waits are measured. Not changed in this lane.

5. **Job lease, node lease and outbox poll in test mode.** 05 and 06 give no value for them, so
   PRO-109 criterion 1 cannot be ticked for them (see PRO-109 Notes).

6. **Intermittent 500 on `POST /v1/sessions/revoke` on PostgreSQL.** One of four runs of the core
   profile on PostgreSQL answered 500 "the request failed" to the revoke route (the kit's
   `core.close.4401` and `core.auth.revoked`). Not reproduced in the later runs. The cause is not
   found. Proposed next step: a repeated run with the service's error log kept in full.

## Evidence

- `services/document-service/test/postgres/u-pro-103-119-core.pg.test.ts`: the core profile against
  the reference service on PostgreSQL in test mode, with a database created and dropped by the test.
  Result on 2026-11-13: every core scenario passes except `core.session.silence` (decision 3, a known
  difference) and `core.channel.page` (skipped with the reason "catchUpCommits is 5000").
- Existing suites rerun after the changes: `services/document-service/test/server/server.test.ts`,
  `control-plane/pro-109-discovery.test.ts`, `data-plane/session-1b.test.ts`,
  `data-plane/session.test.ts`, `control-plane/routes.documents.test.ts` (95 tests), and the
  test-mode suites (43 tests) pass.

## Round 2 (2026-11-14)

7. **Podman machine route for the reference service's asset sandbox in tests.** On the WSL Podman
   machine the asset sandbox's `--memory` and `--pids-limit` fail through the remote client
   (services/asset-worker/src/container.ts). The PRO-114 test sets `DOCEDIT_PODMAN_MACHINE` to the
   machine name (`podman-machine-default` by default, overridable by the same variable in the
   environment). This is the development route the worker documents, not a change to the sandbox.
   Proposed default: keep it for the test environment only; CI on a Linux runner needs no machine.

## Evidence (round 2)

- `services/document-service/test/postgres/u-pro-114-assets.pg.test.ts`: the `assets` profile
  against the reference service on PostgreSQL in Podman and on the S3-compatible store of the test
  environment, with the in-process asset worker and its sandbox. Result on 2026-11-14: every assets
  scenario passes (upload into quarantine, completion, `asset.ready`, `asset.failed` for a mismatched
  type, short-lived URLs, refusal of a caller of another document). Run in 34 s.

## Fix round (U4 group 2, round 2, 2026-11-13)

8. **The bound for a "short-lived" signed asset URL (PRO-114 criterion 1).** 05 §6.2 and 10 §3.7
   say "short-lived" and give no number. The kit (`packages/tck/src/profiles/jobs.ts`,
   `SHORT_LIVED_MS`) accepts an `expiresAt` in the future and at most 15 minutes ahead, the longest
   token life 05 §3 allows. The reference service signs for 300 s by default (ADR 0036). Proposed
   default: 15 minutes, until the owner sets a figure. The same bound is proposed in
   docs/adr/0315-lane-V-PRO-103-119.md, decision 1; this item adds nothing to it.
9. **Quarantine as the kit checks it.** A resolve of an asset whose bytes are in the quarantine
   area but which was never completed must not return its URL. 05 §6.2 does not say whether the
   answer is a refusal or a `200` without the asset; the kit accepts either.
10. **The kit's wait for `asset.ready` and `asset.failed`.** 05 and 06 give no bound for the check.
    The kit waits up to 150 s and refreshes the connection's token every 25 s while it waits
    (`auth.refresh`, 05 §3.1), because the test-mode token lives 60 s (item 4). These are kit
    settings, not spec figures.
