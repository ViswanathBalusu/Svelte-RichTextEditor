# ADR 0341: Record the hash of a sealed PDF in a tenant table (lane V-FRW-037-054)

Status: proposed (2026-11-13)

## Context

FRW-054 criterion 1 asks that the sealed bytes are stored write-once and that their hash is recorded.
The bytes are stored under S3 Object Lock (`services/document-service/src/objects/sealed-pdf.ts`).
The spec does not say where the hash is recorded, nor whether the record is kept in the same
transaction as the control commit that FRW-054 criterion 2 requires.

## Decision (spec default, not an owner decision)

- The hash is recorded in table `workflow_sealed_pdf` (migration `0061_workflow_sealed_pdf.sql`),
  under row-level security by tenant (BE-011), one row per workflow.
- The row holds the sealed hash, the stored hash (which must equal it), the object key and the
  retention end. It holds no document text and no personal data.
- The service role may insert and read only. A recorded hash is not updated or deleted.
- The record is written by `recordSealedPdf` (`services/document-service/src/workflow/sealed-pdf-pg.ts`),
  called by `storeAndRecordSealedPdf` (`services/document-service/src/workflow/sealed-pdf-finalise.ts`)
  straight after the bytes are stored and read back. A record that cannot be written turns the
  store step into `store_failed`, so the workflow stays `completed` (fixer V-UX-031-045).

## Open

- Whether the record is written in the same transaction as the control commit and the `finalised`
  event (FRW-054 criterion 2). The control commit is the workflow service's and is not built, so
  the record is written on its own for now.
- The retention period, which FRW-084 leaves to the owner.

## Evidence

`services/document-service/test/postgres/frw-054.v-frw-037-054.sealed-record.pg.test.ts`
(PostgreSQL in Podman, five tests).
