# ADR 0343: Dark-theme colour of role markers (lane V-FRW-073-089)

Status: proposed (2026-11-13, lane V-FRW-073-089, round 1). Owner review is needed for the colour rule.

## Context

FRW-074 criterion 3 asks that role markers meet non-text contrast (3:1) in the light, dark and high-contrast themes and under forced colours. The marker is the role's colour painted as a shape (`.de-role-icon`, `background: currentColor`). A role colour chosen for a light surface, such as the author colour `#0d47a1`, falls to about 1.8:1 on the dark surface `#20242a`. The browser test `packages/ui/e2e/frw-074-markers.spec.ts` recorded this as a known defect.

The spec does not say how a role colour adapts to a theme. This is a design choice, so it is proposed here and not decided silently.

## Options

1. Keep the role colour as chosen, and add an outline in a contrasting colour in the dark theme. Keeps the exact colour, but the shape's own fill still fails the measured test.
2. Lighten the marker shape towards white in the dark theme only, keeping its hue. The role's stored colour is unchanged. Used in this lane.
3. Ask the author to pick a second colour per role for dark themes. More data, and an owner decision on the role model.

## Decision taken in this lane (proposed)

Option 2. In `packages/ui/src/styles/shell.css`:

    @media (forced-colors: none) {
      .de-shell[data-theme='dark'] .de-role-icon {
        background: color-mix(in srgb, currentColor 40%, #ffffff);
      }
    }

The rule does not apply under forced colours, which keep their system colour. The measured result is about 8:1 for `#0d47a1` and `#b71c1c` on the dark surface, from `packages/ui/e2e/frw-074-dark-contrast.spec.ts` (Chromium, Firefox and WebKit). The text of the role's name is unchanged.

Effect on other places: the legend and the role manager, if they are built, use the stored colour unless they also apply this rule. The owner should confirm whether the role's colour must match exactly across the dark theme.

## Consequences

- FRW-074 criterion 3 is ticked on this evidence.
- `packages/ui/e2e/frw-074-markers.spec.ts` still carries a `test.fail` for the dark theme. Its parser does not read `color(srgb …)` (what Chromium returns for `color-mix`), so it still reports 0. The owner or the lane that wrote it should retire that `test.fail` and use the parser of the new file.

## FRW-089 derived values, round 4 (lane V-FRW-073-089, 2026-11-13, proposed)

The authority's hidden set now includes values the rules compute from a value a connection may not read (`packages/authority/src/permissions/visibility.ts`, `addDerivedValues`). Two choices are not in the spec and are proposed here:

1. The closure uses only the rules of the document (`derivedFromHidden`, the taint defaults of ADR 0119 item 6): a `set` effect that reads a hidden value and a rule whose condition reads one. The implicit flow counts, as ADR 0119 item 6 says.
2. When the document's rules do not compile, no closure can be read, so every field value is hidden for a connection that has any hidden input (fails closed). The spec is silent on this. The other choice (show every value) would leak what a rule computes from a hidden value.

Not decided here: whether a derived value a reader cannot see may be changed by that reader (the outcome check does not refuse it yet), mirrors, computed labels and `cached` text (not built), and the owner's choice of what to show for derived values in the sealed PDF (FRW-089 criterion 3).
