# ADR 0411: The sealing spike's library, key emulator, test chain and profile (SPK-021)
Status: proposed. Spike S8, 2026-11-18. The owner allowed a library for development and tests (decision 221), a software key emulator (222) and a self-signed test chain with a local time-stamp authority (223). The production library, key store, certificate and time-stamp authority are not decided.
## Context
12 §8.2 has a separate signing service seal the final PDF with a PAdES signature and an RFC 3161 time-stamp, with keys that no compile worker ever holds. Spike S8 had to show that this works end to end before the workflow is built (FRW-052, FRW-053, FRW-056). The spike needs code that writes a PAdES signature when the hash is signed somewhere else, and none was in the workspace.
## Decisions
1. **Library: `pkijs` 3.4.3 with `asn1js` 3.0.10** (both BSD-3-Clause), for the CMS and RFC 3161 structures only. The PDF side (reading the cross-reference chain and objects, appending incremental updates, the signature field, the document security store, the document time-stamp) is our own code: about 830 lines in `services/signing-service/src/pdf.ts` and `pades.ts` (counted 2026-11-18, comments included). `pkijs`'s own signing call is not used, because it wants a private key object in the process. The signed attributes are built and hashed in `cms.ts`, and only the 32-byte digest goes to the key service.
2. **Key emulator: SoftHSM2 2.7.0 in a Podman container** (`services/signing-service/keyservice/`). The key is an RSA 3072-bit key made inside the container at start-up. The token reports it as sensitive, always sensitive and never extractable. No key is in the image. The container has no network, a read-only root file system and tmpfs for the token. Sealing code reaches it through the `KeyService` port (a public key and `signDigest`), here by `podman exec`. The command is `DOCEDIT_CONTAINER_CLI`, default `podman`.
3. **Test chain:** a root CA, an intermediate "sealing CA", the sealing certificate (issued for the public key the key service reports, so the private key is never seen) and a time-stamp authority certificate, all made with the OpenSSL command line for each run, with CRLs for both CAs.
4. **Time-stamp authority:** `openssl ts -reply` behind a loopback HTTP server in the test process. It is a different implementation from the client, so the tokens are not made by the code that checks them. No network beyond 127.0.0.1.
5. **Profile: B-LT for the seal at completion**, as the second review recommends (SR-K8), with B-LTA reached later by appending a document time-stamp (`addDocumentTimestamp`, tested as an append that leaves every earlier byte unchanged, and again as a renewal). Reasons: the signature time-stamp and the validation data (certificates, CRLs) together make the file checkable offline while the certificates are valid; a document time-stamp only starts to matter when something in the chain expires, and the job that renews it (FRW-056) does not exist yet; and nothing is lost by waiting, because the upgrade is an append. `finalisation.seal` in 12 §6.1 can name either value. **This is a recommendation; the owner decides.**
6. **Independent verifiers:** OpenSSL (`cms -verify`, `ts -verify`) in the test suite; pyHanko 0.38.1 as an optional second check (`DOCEDIT_PYHANKO_PYTHON`, not a dependency of the repository); veraPDF 1.30.3 for tagging. Acrobat is a manual check (the story's criterion 1).

## Licences added
`pkijs` 3.4.3 and `asn1js` 3.0.10 (BSD-3-Clause), `pvutils` and `pvtsutils` (MIT), `bytestreamjs` (BSD-3-Clause), `@noble/hashes` 1.8.0 (MIT), `tslib` (0BSD). `node scripts/licence-gate.ts` passes with them. In the key service image only: SoftHSM 2.7.0 (BSD-2-Clause), OpenSSL (Apache-2.0) and OpenSC's `pkcs11-tool` (LGPL-2.1), a command line tool inside a development image that is not linked into or shipped with anything. Tools used by the tests and not installed by the repository: the OpenSSL command line, veraPDF, and pyHanko with `pyhanko-certvalidator` (MIT).
## Is the chosen library fit for production?
Not as it stands, and the owner's open choice ("find one or build our own") is not answered by this spike.
- `pkijs` is a sound base for the ASN.1 and CMS structures. It is an established library, and its structures were accepted by OpenSSL and pyHanko here. It is not a PAdES library. Everything that makes a file a PAdES file is ours: the signature dictionary, the byte range, the placeholder size, the DSS and its VRI entries, the document time-stamp, the choice of attributes. That code passed OpenSSL and pyHanko on the files of this spike. It has not been checked against ETSI's conformance tests, EU DSS's validator, or Acrobat (the last is a manual check, still open).
- The PDF reader and writer is minimal on purpose. It refuses encryption and hybrid-reference files, assumes a reachable first page and keeps no repair path. It does not draw visible appearances (FRW-057), does not add OCSP responses (none were made here), does not renew expired validation data, and does not check that an earlier update left the document's form fields alone.
- pyHanko already does most of this, with a validator and PKCS#11 signing, under an MIT licence. Running it as the production sealer would cost a Python runtime and a process boundary; writing our own would cost the work above plus a conformance suite. Both options should be assessed against the same test files before the owner decides.
## Not decided here
- The production library (find or build), the production key store (hardware module or cloud key service), the production certificate and the production time-stamp authority.
- Whether the owner takes B-LT or B-LTA for phase 2 (decision 5 is a recommendation).
- OCSP versus CRL in the validation data. The spike uses CRLs (the test authority has no OCSP responder).
- Whether the sealing certificate needs an extended key usage that Acrobat's trust lists expect. The test certificate has `id-kp-documentSigning` (1.3.6.1.5.5.7.3.36) and `nonRepudiation`.
## Consequences
- `services/signing-service` exists as the place the real service grows (01 §6). Its sources import nothing from the export worker, and nothing on the compile side imports it (checked in `test/spk-021-no-key-on-worker.test.ts`).
- The sealing code keeps the `KeyService` port as its only contact with a key. A hardware module, a cloud key service or a Cloud Signature Consortium `signHash` call fits it.
- FRW-052 and FRW-053 can start from `sealPdf`, `addDocumentTimestamp` and the test support, and replace the emulator and the test chain.
