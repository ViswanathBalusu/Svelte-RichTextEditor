# 0402. The evidence bundle of a workflow

**Status:** proposed, 2026-11-18. Written while building FRW-055 (lane w4). 12 §8.2 step 4 and §10 name the bundle and its route and say what it holds in a phrase. They leave open its format, what the log segment holds, who may fetch it and from which state. The owner has not seen this record.

1. **Format `docedit-workflow-evidence/1`** (`packages/history/src/workflow-evidence-bundle.ts`): `{ doc, workflow, log, evidence, instructions }`. `log` is the records of the document's log from `max(1, sentSeq)` to the head, each as a log-bundle record (metadata, payload hash, previous hash, hash). `evidence` is the item list of `@docedit/authority` (`buildBundle`: id, salt, canonical text, commitment).
2. **Only control commits carry their payload.** A control commit has no steps, so its payload (`{ steps: [], retired, claimed }`) holds no document text; every other record is held without its payload and checked through its stored hash, as an audit segment is (HIS-037). The bundle therefore holds no document content. The criterion's "control commits" are those records.
3. **One verifier, one command.** `verifyWorkflowEvidenceBundle` runs the log check of HIS-033 (`firstSeq` set to `log.from`) and the evidence check, and names each failure: a record by its `seq`, an evidence item by its identifier. `packages/history/scripts/verify-log.ts` recognises the format and writes the verdict (exit 0 intact, 1 altered, 2 incomplete). No new command name is added.
4. **Recomputed hashes.** `LogStore` does not expose the stored hashes. The service recomputes the chain from the stored commits with `storage/codec.ts` (the codec that wrote them), from the first commit of the log. A commit whose payload was removed (a tombstone, thinning) would give another hash and fail verification; the history service (HIS-033) should provide the stored hashes. This is open, and untested on a tombstoned log.
5. **The route.** `GET /documents/{id}/workflow/evidence` needs `manage`: 07 §12 has no row for the bundle, so the matrix does not assign a credential (FRW-055 criterion 6 stays open). It answers only for a `completed` or `finalised` workflow that was sent; before that, `not_found`. Every retrieval is audited as `workflow.evidence_retrieved` (workflow, state, number of items) with the caller and the server time; a refused caller leaves no entry.
6. **Not done.** The PDF's signature and time-stamp and the match of the evidence hashes with the chain (criterion 2) need the sealed PDF and a validator (FRW-053). A bundle for a `finalised` workflow is built by the same code as for `completed`, but no test reaches a live `finalised` workflow through the signing service.
