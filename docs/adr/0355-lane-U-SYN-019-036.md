# ADR 0355: Comment anchors in checkpoints (lane U-SYN-019-036)

Status: accepted for choice 2 by owner decision 81 of 2026-11-15 ("Thread positions are kept for every checkpoint"; [owner-decisions-2026-11-15.md](../owner-decisions-2026-11-15.md)); built in lane w9, 2026-11-18, see "Built" below.

## Context

SYN-032 criterion 6 says that when a checkpoint is written, the mapped comment ranges are saved with it (BE-020). 06 §2.2 step 3 says a checkpoint holds "the canonical document, the attribution map and the comment ranges", and 06 §8 names the object `checkpoints/{seq}.side.json.zst` for the attribution map and comment ranges. `objectKeys.checkpointSide` exists in `services/document-service/src/objects/store.ts`, but nothing writes or reads that object.

Today the host (`services/document-service/src/data-plane/checkpoints.ts`, `Checkpointer.save`) writes only the `.cdm.json.zst` object and its index row. The room's `fx.checkpoints` entries carry `threads` (`packages/authority/src/room/room.ts`, `threadAnchors()`), which the host drops. A room opened from a checkpoint starts with no threads.

## The open question

The room keeps comment anchors at the durable head only (`ThreadState.anchor`, mapped on each stored commit). The host writes a checkpoint at `seq`, which can be below the head (the policy writes from the last checkpoint and the steps since, in a worker; 06 §2.2 step 3). Two choices:

1. Write the side object only when the checkpoint is at the durable head (a close or a snapshot). Anchors below the head are not saved; a room opened from an older checkpoint replays the tail and then has no anchors until the next head checkpoint. This loses threads after a crash unless a head checkpoint exists.
2. Keep anchors per checkpoint `seq` by mapping them, in the room, through the steps replayed for each checkpoint. This is a change to the room's replay and to the worker's input.

The spec does not say which. Neither is decided here.

## Spec default applied

None applied. The spec's text ("saves them with it") is met by choice 2 only; choice 1 is a narrower reading that the spec does not state.

## Consequence for the story

SYN-032 criterion 6 stays unticked. No product code was changed for it in lane U-SYN-019-036.

## Decision needed

The owner (or the main session) chooses 1 or 2, and then the side object format (`{ seq, threads: ThreadAnchor[] }` in canonical JSON, zstd, as the checkpoint is) can be built and tested against PostgreSQL and the object store in Podman.

## Built (lane w9, 2026-11-18; SYN-032 criterion 6)

Decision 81 keeps the ranges for every checkpoint, which is choice 2. It needs no change to the room's replay: the room maps its anchors through every stored commit, so at the moment the host writes a checkpoint at the durable head the anchors are at that `seq`. `HostedRoom` takes them with `room.threadAnchors()` in the same step that fixes the checkpoint's `seq` and steps, and `Checkpointer.save` writes `{ seq, threads }` as canonical JSON compressed with Zstandard to `checkpoints/{seq}.side.json.zst` before the index row (`CheckpointStore.putSide`, `encodeSide` in `src/storage/codec.ts`). A room opened from a checkpoint reads the side object (`getSide`) and starts with the anchors; the room maps them over the log after it. No side object is written when the room holds no ranges, nor for a checkpoint below the durable head (a repair of a snapshot's checkpoint), because anchors of a later `seq` would be mapped over the wrong steps; a side object whose `seq` differs from its checkpoint's is ignored. A checkpoint set aside after a database recovery takes its side object with it. The attribution map joins the side object with HIS-014.

Limit: nothing in the hosted service creates a range in a room. The control plane maps a thread's range on demand from the thread store (`thread-routes.ts`), so in a running service the room holds no ranges and no side object is written. The side object and the room's start from it are tested with ranges seeded through the side object of the first checkpoint.
