# 0420. The live seal step, the operator alert and the signing service's container

**Status:** proposed, 2026-11-18. Written while wiring the seal step into the running document service (lane w4). It builds on ADR 0411 and 0412. Owner decisions 221 to 223 leave the production library, key store, certificate and time-stamp authority open; nothing here chooses them. Each item takes the smallest reading that works; the owner may change any of them.

1. **What starts a seal.** The export hook `finalExportCompleted` (a final export job has completed) and a scheduled task `workflow.seal` (every minute, per tenant, like `workflow.schedule`) both call `FinalSealer.sealCompletedWorkflow`. The task finds a run that stopped, or a process that restarted, because the final export job has a derived identifier (`finalExportJobId`): the workflow and its `completedSeq` give the job. One run at a time per workflow in one process. Across processes the stores' rules hold (the signing service binds a document and `seq` to one hash, the sealed store refuses a second write, `finaliseSealed` refuses a workflow that is not `completed`).
2. **The pair of compiles.** When the service seals, the final export job carries `sealing { completedSeq, chainHead }` (the pin of EXP-079), so the worker compiles twice and records both hashes in the job result. The pin is added only when sealing is on (`ServiceConfig.sealing` or `StartOptions.finalSealing`), so a service that does not seal does not pay for a second compile, and the job's cache key says so, so an ordinary export is never reused for a sealing one. The chain head is computed for the pin as it already was for the certificate.
3. **The operator alert.** The document service has no pager, no mail and no operator webhook; its webhooks are tenant subscriptions on a fixed list of event types, which a new type would change (the protocol package's registry). The alert is therefore what the service has for operators: an `error` log line (`event: workflow.finalisation_stopped`, tenant, document, code), a counter `docedit_finalisation_stopped_total{reason,code,retryable}` on `/metrics` to alert on, and the audit entry `workflow.finalisation_failed` (stage `seal`). The workflow stays `completed`. An alert is raised once for each run that stops. A stop that asking again cannot mend (the signing service refused the request, the job has no equal pair, the PDF is missing its hash) is remembered in the process and not retried by the task; a stop that can pass (the service or the time-stamp authority not answering) is run again at each task run and alerts again. Nothing is stored for this: a restart forgets which stops were final.
4. **Settings with no default.** `DOCEDIT_SEAL_URL` turns sealing on and then needs `DOCEDIT_SEAL_CREDENTIAL`, `DOCEDIT_SEAL_TIMEOUT_MS`, `DOCEDIT_SEAL_ATTEMPTS`, `DOCEDIT_SEAL_DELAYS_MS` and `DOCEDIT_SEAL_RETENTION_DAYS`. The spec gives no retry policy, no retention and no timeout, so none is built in (as ADR 0146 does for webhooks). A service started with the URL and without the sealed PDF store (`parts.sealedPdfs`) stops at start-up. The PostgreSQL composition has no sealed store yet: the write-once object store needs a bucket with Object Lock and a setting for it, which is the deployment's. Until then a deployment that seals supplies `parts.sealedPdfs`.
5. **The signing service's image.** `services/signing-service/Containerfile` (Node.js 22.18.0 pinned by digest, as the authority service) holds the service and the four packages it reads, with production dependencies, and no key, certificate, test, worker or other service. It runs as `node`. It has no default configuration: `DOCEDIT_SIGNING_CONFIG` names a module the deployment mounts (the key service adapter, certificate source, time-stamp client, callers' hashes, rate limit, audit sink and address), and without it the service stops with exit code 2. The network (no route from the compile workers) and the hardware key store are the deployment's and are not shown by the image.
6. **Not built.** The retry waits inside one run are in process (`retry.delaysMs`); a durable queue job for the seal would survive a restart without the task. The sealed store's retention end is `now + retention` at the time of the seal; the spec states no figure. The tenant-visible `finalised` event is raised as the other workflow events are; no event tells the host that a seal stopped.
