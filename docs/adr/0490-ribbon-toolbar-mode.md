# 0490. A ribbon layout for the toolbar (`toolbar="ribbon"`)

Status: proposed (lane ci-b, 2026-11-27). The owner asked for the demo to look like an office word processor and approved a design mock; the attribute value and the grouping below are not in the spec yet.

## Context

05 §8.1 lists three values for the `toolbar` attribute: `full`, `compact` and `none`. 13 §3 says the toolbar groups commands by task (formatting, inserting, page layout, references, review, view), with contextual groups, and that the grouping and the look are this product's own. The full layout groups by the registry's `group` and shows one group at a time as plain rows. The owner wants the demo to look like a familiar office word processor: a title bar, tabs of labelled groups, the page centred on a grey canvas, side panes and a status bar.

## Decision

1. A fourth value, `ribbon`, for the `toolbar` attribute and the shell setting. Unknown values still read as `compact`. The attribute and `ToolbarMode` carry it; nothing else in the protocol changes. 05 §8.1 names it as proposed.
2. The ribbon reads the same registry entries as the compact and full layouts. It adds no command and no registry field. A command is placed by its id (a table in `shell/ribbon-groups.ts`), else by its `group`: edit and format go to Home, insert to Insert, page to Layout, review to Review and view to View; footnotes, captions, cross-references and citations go to References. Each command is in one group of one tab, and none is dropped. A contextual group (table, picture, header and footer, field) and any group an extension adds get a tab of their own, as in the full layout.
3. Behaviour is the full layout's: the WAI-ARIA tabs pattern (arrow keys, Home, End, Escape), one tab stop for the commands of the open tab, roving focus, Alt+F10 to the floating format bar (decision 168), disabled commands that stay focusable and say why. Nothing goes into a "More" menu; groups wrap onto another row.
4. The ribbon always shows an icon over each label, from the host's set, then the built-in set, then a set of the ribbon's own drawings (`RIBBON_ICONS`) for the commands that name none. Other layouts do not use them.
5. The look is scoped to `.de-shell[data-toolbar='ribbon']` and `.de-ribbon`, so the other layouts keep theirs. It adds four tokens with defaults in each theme: `--de-chrome` (the strip behind the tabs and the status bar), `--de-canvas` (the grey the page lies on), `--de-accent` and `--de-accent-text` (the main action).
6. Group captions and tab names are strings of the core table (`ribbon.tab.*`, `ribbon.group.*`).

## Consequences

- A host chooses the look with one attribute. The reference host uses it.
- The tab names and the group captions are provisional with the rest of 13 §3.
- The visual baselines of UX-064 cover the compact layout and are unchanged. The ribbon has its own.
- No vendor's name, icon, font file or layout is used; the icon drawings and the arrangement are this product's own.

## Notes: the Home tab (lane ci-b, 2026-11-27)

The Home tab first showed Undo, Redo, Select all, Bold, Italic and the format painter. It now has the controls of the owner's design mock. Groups, in order: Edit, Styles, Font, Paragraph, Copy format.

- **Commands added** (`commands/home.ts`): `format.underline`, `format.strike`, `format.clear`, `format.fontSize`, `format.color`, `format.highlight`, `format.align.start|center|end|justify`, `format.bulletList`, `format.numberList`, `format.indentLess`, `format.indentMore`. Each runs a named command of the core with `enabled: canEditSelection`, so access and mode apply as for bold. `format.applyStyle` gets a place in Styles. Underline, strike and the four alignments show as pressed (`active`), from the selection's marks and the paragraph options.
- **On the ribbon alone.** The new commands, and the style command, have `toolbar: false` and `ribbon: true` (a new `CommandEntry` field): the ribbon's toolbar shows them, and the compact and the full toolbars, with their visual baselines and tests, are unchanged. They are all in the registry, so command search and `exec` reach them in every layout. Whether the compact layout should have an Underline button is the owner's.
- **Lists that are chosen from.** A command with `picker` (`style`, `fontSize`, `colour`, `highlight`) is shown by the ribbon as a menu button. `exec(id, { value })` takes the choice (`{ style, kind }` for the style). The menu is a `role="menu"` of radio items; Down, Up and Enter on the button open it, the arrow keys, Home, End, Enter, Escape and Tab work inside it, and focus returns to the button. The button is one control of the toolbar's roving focus.
- **What the lists offer is the model's** (03 §4.5, §4.8): the document's paragraph styles; sizes of 8 to 72 points in twentieths of a point (the model allows 1 to 1,638 points); a text colour as `#RRGGBB` upper case, five dark ones (each at least 4.5 to 1 against white) and "Automatic", which takes the colour off; five of the sixteen highlight names and "No highlight". The palettes are a proposed default, not an owner decision.
- **Alignment is in the model** (`align`: `start`, `center`, `end`, `justify`, `distribute`) and in the engine (`setParagraphFormat` with `{ align }`), so the four buttons exist. `distribute` has no button.
- **Lists need a numbering definition.** `applyList` took the identifier of a definition the document holds, and a new document has none. It now also takes `{ listKind: 'bullet' | 'number' }`: the paragraphs join the document's first definition of that kind, or the document gets one (nine levels, as a paste makes them) in the same transaction, which is one undo step. Paragraphs already in a list of that kind leave it. **Decision left open:** adding a definition changes the document's `defs` and their order, which the guard allows only with `structure` (07 §7). An editor without it can make a list only in a document that already has a definition of that kind; otherwise the button does nothing. Whether the default definitions should be in every new document, or whether `edit` should be enough for the first list, is the owner's.
- **Indent buttons.** In a list they change the item's level (`listLevelUp`, `listLevelDown`); elsewhere they move `indentLeft` by the tab step (720 twips unless the document says another), never below the margin. A list item at its deepest or shallowest level that cannot move falls back to the paragraph indent; this edge is not decided.
- **No keys.** The shortcut table (UX-013) lists no key for these commands, and it records a conflict only from a browser's published list, which has not been read for Ctrl+U (a view-source key in three of the four) or the alignment and list keys. None is invented; a key for each belongs to the next reading of the lists.
- **Left out:** small capitals, all capitals, superscript, subscript and the font family (not in the mock; superscript and subscript have no readable state in the selection summary); `distribute` alignment; a font size box that takes any number.
- **Loading.** The commands, their labels (`ribbon.command.format.*`, group `ribbonToolbar`), their queries, the menu button and the drawings are in code loaded on demand. The shell asks for the commands after it has mounted (`App.svelte`), so `exec` and command search have them in every layout a moment after the editor is up, and do not know them before. The rules of the ribbon's toolbar (tabs, groups, commands) moved from `shell.css`, which the first load carries whole, to `styles/ribbon.css`, which the ribbon adopts into its shadow root when it loads (`shell/ribbon-styles.ts`; a constructable sheet, or a `<style>` with the element's nonce). The title bar, the canvas and the status bar stay in `shell.css`, because they are drawn at once. The first load carries only: the `picker` field, the engine's list kind and font size in the selection summary, and the element's pass-through of the core's named commands. FND-008 after this change: the first interactive editor with the DEP client measured 319,793 bytes of gzip (budget 320,000; it was 319,349 before). That is 207 bytes of room, which the next first-load change will use up.
- **The other panes of the mock** (checked in the build, not changed): the navigation pane, the comments pane with suggestions, presence avatars, the Catch up button, the mode switcher, Share, the status bar's language, classification ("Confidential") and connection, and the zoom already exist and are not hidden by the ribbon; they are drawn by the header and the status bar, which the ribbon shares with the other layouts.
