# 0303. Clipboard events of the body web view go through the core (lane U-FE-049-064)

Status: proposed

## Context

FE-050 and FE-055 need the browser's copy, cut and drag events on the body surface to write what the core chooses, and paste events to reach the core's paste rules (FE-051, FE-052). Before this lane the web view only took picture paste (FE-053). Copy and cut used ProseMirror's own format, and a paste of HTML went to ProseMirror's parser, which does not sanitise (FE-054 is not built).

## Decisions taken here (not in the spec; for the owner to confirm)

1. Copy, cut and dragstart on the body surface call `copySelection` or `cutSelection`. The browser's default is always prevented, so a refused copy writes nothing (FE-055).
2. A drag that the core refuses is not started. A drag the core allows keeps ProseMirror's own drag handling, which writes ProseMirror's format; the spec does not say what a drag writes, so this is left as it was.
3. A paste is routed through `pasteFromClipboard` with the HTML and plain text. Picture files keep their own path. HTML that holds no CDM fragment is not parsed by ProseMirror: the plain text is used, as FE-052 criterion 3 says. If the clipboard holds HTML and no text, nothing is inserted until FE-054 adds the sanitiser. The spec default (plain text first) is kept.
4. Synthetic clipboard events in Firefox keep no data written by a listener, so the browser tests that read the clipboard back skip there (`clipboard-fragment.universal.test.ts`). Firefox is not proven for those criteria. A trusted-event run (keyboard copy and paste) would prove them and is not built.

## Consequences

- FE-050 criterion 4 stays open until Firefox is run with trusted events.
- The picture paste test (`paste-picture.universal.test.ts`) fails in Firefox for the same reason as in point 4. It is not changed by this lane.

## Round 8 (lane U-FE-049-064, FE-054)

Status: proposed. The spec's default or a default taken where the spec is silent; for the owner to confirm.

1. Paste of HTML is taken in `handleDOMEvents.paste` of the body view (`packages/engine/src/view/web.ts`), not in `handlePaste`. Reason: ProseMirror parses the clipboard HTML before it calls `handlePaste`, under its own Trusted Types policy `ProseMirrorClipboard`, which a host that allows only `docedit-paste` refuses. A read-only view keeps ProseMirror's handling.
2. Criterion 5 of FE-054 names `innerHTML`. The view parses with `DOMParser.parseFromString` through the named policy `docedit-paste` (`packages/engine/src/view/paste-policy.ts`). Both are Trusted Types sinks; the parser is kept because it runs no script and loads no resource in an inert document. Owner to confirm the wording of the criterion.
3. A host that enforces Trusted Types must list `docedit-paste` in its `trusted-types` directive for HTML paste; otherwise HTML paste falls back to plain text. The integration guide must publish this name next to `docedit-worker` and `docedit-math`. Needs the main session or the documentation lane (not a root file).
4. FE-054 criterion 7 is tested on a generated corpus (fast-check, seed 54, 300 documents), not on a stored corpus. A stored corpus of real Word and Google Docs clipboard samples (criterion 4) does not exist and is not made here, since inventing samples would not prove the mapping.
5. Open, not decided and not changed: the sub-editor's paste and an HTML drop still use ProseMirror's own parser, so both can fail under enforcement. Their owners are FE-056 and the drag-and-drop story; not changed in this lane.
6. Open, not decided: whether remote image URLs in pasted HTML are fetched (FE-054 criterion 6). Not built.
