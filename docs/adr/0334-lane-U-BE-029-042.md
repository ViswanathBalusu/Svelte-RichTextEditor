# ADR 0334: Share one rate-limit instance between sockets and REST (lane U-BE-029-042)

Status: proposed (lane U-BE-029-042, 2026-11-13). Owner review needed.

## Context

BE-030 criterion 2 says a user over a limit gets `rate_limited` on the socket and a 429 with
`Retry-After` on REST. The user and tenant buckets must be the same ones for both surfaces, so that
a user over the limit on one is over it on the other. Before this lane the data plane built its own
`RateLimits` privately and no REST route called it.

## Decision

1. `DataPlaneDeps` takes an optional `limits: RateLimits`. The data plane uses it when given and
   builds its own from its settings otherwise (`src/seams.ts`, `src/data-plane/index.ts`).
2. `startService` takes an optional `rateLimits`. It defaults to `new RateLimits(DEFAULT_RATES)`,
   passes the instance to the data plane and to the REST pipeline (`src/server.ts`).
3. The pipeline checks `rateLimits.rest(tenant, user, now)` after authentication of a user token and
   before the handler. A refusal is `rate_limited` with `retryAfterS` (`src/control-plane/pipeline.ts`).
   A service credential is not limited by this check.

## Open points for the owner

- The spec names no limit values (ADR 0053 gives the figures in use). Whether service credentials
  should be limited per tenant on REST is not stated; this lane does not limit them.
- The data plane's refusal count (`closeAfterRefusals`) still reads its own settings, while the
  buckets come from the shared instance. If a deployment sets different rates in the two places,
  the injected instance wins for buckets. Config-level rate settings are not yet wired into
  `startService`.
- Stage 2 moves the counters to Redis or Valkey (BE-063); this decision keeps one place to change.
