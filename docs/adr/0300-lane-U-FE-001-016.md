# ADR 0300: Decisions taken by lane U-FE-001-016 (round 3)

Status: proposed. Decisions the spec leaves open, taken on the spec's default or on the narrowest
reading, for the owner to confirm. Date: 2026-11-13.

## Context

Lane U-FE-001-016 closed FE-008 (the recovery journal), FE-011 (flush on hidden) and the journal
half of FE-012 (flush rejects and the work stays journalled). The spec (02 §2.2, 04 §8) fixes what
the journal must do, not how it is stored or ordered.

## Decisions

1. **Ordering by commit identifier.** Journal entries are read oldest first by identifier. Commit
   identifiers are UUID version 7 (04 §3.1), which sort in the order the client made them.
   Resubmission (FE-009) will use the same order.

2. **One write chain per session.** Journal writes run one after another in the order requested:
   commit, then the queue. A commit is sent only after its write has resolved. A failed write sends
   nothing, reports `unsaved` and is retried after a delay that starts at `retry.minMs` (250 ms) and
   doubles up to `retry.maxMs` (10 s). These are the 05 §5.8 backoff defaults already used for
   reopening channels (ADR 0038), not measurements.

3. **Queue written with each commit and on each local edit that changes it.** The queue is
   replaced as a whole, so the journal holds the queue as it was at the last write.

4. **Acknowledged commits are removed; a failed removal is not retried.** A stale entry left by a
   failed removal is deduplicated by identifier when FE-009 resubmits it (the server recognises the
   identifier). The `journal` event reports the failure as `unsaved` until the next successful write.

5. **Journal on by default in the browser.** The element opens an IndexedDB database named
   `docedit-journal` before it opens the channel, when the browser gives one, and closes it on
   teardown. Where it cannot be opened, the element carries on without a journal, as before this
   ADR. Spec default: 02 §2.2 requires the journal; it does not name a default on or off. Owner to
   confirm.

6. **Only commits and steps are stored.** An entry holds the document identifier, the commit
   identifier, its base, its steps and its origin. No token or credential is stored (10 §3.1).

7. **Flush count unchanged.** `flush` still counts the in-flight commit and the queue as one each
   (round 8 note on FE-012). Counting the commits the queue would send is the engine owner's.

## Not decided (open)

- Two tabs on one document (one tab should own a document's journal through a lock; SR-M33).
- Whose entries a returning user may resubmit (user binding; the Open questions of the epic).
- A journal write that fails after a commit has been acknowledged by the server.
- Recovered edits in the journal: partly built in round 4 (see below). The region they were meant
  for, the pane, and the rebuild after `sync.reset` or a reload are still open.

## Consequences

- `packages/engine/src/sync/journal.ts` (port and memory store), `packages/engine/src/sync/session.ts`,
  `packages/engine/src/core.ts` (`flushJournal`, the `unsaved` state on a failed write),
  `packages/element/src/journal-idb.ts`, `packages/element/src/session.ts` (open, attach, visibility
  flush, close).

## Round 4: recovered edits (FE-010, lane U-FE-001-016)

Proposed. The spec (02 §2.2) says recovered edits are written to the journal; it does not say how.

8. **Recovered edits in their own store, one row per document.** The `recovered` store of
   `docedit-journal` (database version 2, upgraded in place from version 1) holds the list of set-aside
   items for a document. The list is replaced as a whole on each write, as the queue is.

9. **Restored once, as an ordinary `discarded` event.** The session reads the list when it starts and
   sends it to the core in the same event the core already handles, so the count and the pane follow
   from the core as before. The restored items come first, then those set aside in this session.

10. **No purge yet.** Nothing removes a recovered item: there is no dismiss action in the element API.
    The list grows until the person deals with it. Purge and dismissal are open: ADR 0019's purge
    rules and the UX pane decide them.

11. **Text of a recovered item.** The engine's `text` joins the characters of the steps with a newline
    (for example `R\ne\nc`). It is kept as it is here, because the format is shared with other code and
    tests; the owner or the engine owner should choose a format.

Not decided: whether a recovered item must name its region in the journal, which is FE-010 criterion 6
and needs a CDM fragment (not built).
