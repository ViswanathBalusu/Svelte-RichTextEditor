# ADR 0328: decisions of lane U-UX-046-060 (round 2)

**Status:** proposed, 2026-11-13. Owner decisions are the owner's; each item below says which default
the code keeps.

## Context

Lane U-UX-046-060 closes the criteria of stories UX-046 to UX-060 that were blocked on a browser, a
container, a dependency or a decision. This record lists the questions the lane met that the spec
leaves open, or that the stories answer differently from the code.

## Decisions

1. **UX-048 criterion 2: the action queue.** `packages/ui/src/assistant/action-queue.ts` holds each
   side effect the assistant's output may request as a proposal, and runs the executor only on that
   proposal's approval (13 section 6.2). The kinds are: insert text, insert a link as a mark (not
   followed), insert an attached asset as a picture, create a comment and call a host action. Following
   a link and loading a picture from an address are not kinds, so no code path can run them through
   the queue. Spec default kept: approval is per action. The queue has no size bound, because the spec
   gives no number (decision 3). The product does not yet send output to the queue: the assistant
   pane (UX-045) is not built.

2. **UX-056 criterion 4: refusal code (open, not changed).** The story says a commit that a connected
   client cannot take is refused with `unsupported_feature`. The room answers `conflict` with action
   `drop` when `requires` would grow and a client lacks the feature (03 section 11.1; CDM-047; ADR 0050
   item 5; `features.test.ts` asserts this). The code keeps the room's answer. The accept half (the first
   extension block adds `extensions` when every client announced it) is tested in
   `packages/authority/test/ux-056-extension-requires.test.ts`. Owner or PRO to choose which code the
   spec names.

3. **Action queue size.** No bound is set for pending proposals. A bound needs a number from the owner;
   none is invented here.

4. **UX-046 criteria 1 and 3: agent identity and direct edits (open, not changed).** The story says an
   assistant result is always a suggestion, even when the author is an editor, and that a hand-crafted
   commit under the agent identity that changes text directly is refused with `permission_denied`. The
   authority does not do this. The control test in `packages/authority/test/sec-010-assistant-origin.test.ts`
   asserts that the same agent identity acting for an editor is accepted with origin `assistant`, and
   that is another lane's test. Changing the rule would make that test fail, and the rule belongs to the
   permission model (07 section 17 leaves block-level P4 rules open). Nothing is changed. Owner or PRM
   to decide whether an agent's direct edits are refused for editors too.

5. **UX-058 criterion 2: the save path.** The authority does not know which extensions a reader has
   registered, so availability is decided by the client (`resolveExtensionNode`). The save is the room's
   commit. `packages/authority/test/ux-058-extension-payload.test.ts` shows that an editor's commit to
   another paragraph leaves an extension block's payload, extension and fallback text unchanged. No
   browser save was run.

## Consequences

- Criteria ticked: UX-048 criterion 2 (function level, with the product path open); UX-058 criterion 2
  (authority commit and client view, no browser run).
- Criteria left open with a stated reason: UX-046 criteria 1 and 3 (decision 4); UX-056 criterion 4
  (decision 2).
