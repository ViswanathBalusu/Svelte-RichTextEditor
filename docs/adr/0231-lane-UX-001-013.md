# ADR 0231: activation gesture for access keys (UX-012) and the reserved-sequence check (UX-013)

**Status:** proposed. Not decided. The owner or the main session chooses the gesture; nothing in `packages/ui` binds one yet.

**Date:** 2026-11-13. **Lane:** UX-001-013 (round 2).

## Context

UX-012 criterion 5 (a command disabled for the user's permissions does not run when its access key is pressed, and the reason is exposed) is proven only at the logic level. `pressAccessKey` in `packages/ui/src/commands/access-keys.ts` runs the command, or returns `reasonKey`, but no key gesture reaches it in the product, and the shell shows no reason. To prove the criterion, the shell needs:

1. an activation gesture (UX-012 criterion 1) that sends key presses to `pressAccessKey` and shows the returned `reasonKey`; and
2. a browser test in Chromium, Firefox and WebKit.

The gesture is not chosen by the specification. 13 section 4 and section 12 name access keys and the shortcut table, but give no key sequence. The open-questions table of `docs/stories/UX-experience.md` lists it as open ("Access-key activation gesture is not specified, and browsers and assistive technology reserve many sequences"), for UX-012 and UX-013.

Choosing the gesture in code would decide an open question silently, so it is not chosen here.

## What the choice depends on

- **Reserved sequences.** UX-012 criterion 3 requires that the chosen gesture is not reserved by a browser or assistive technology in any supported browser, shown in the shortcut table (UX-013). The table's Firefox list has not been read (`SOURCES.firefox` is `null` in `packages/ui/src/shortcuts/table.ts`), so Firefox's reservations cannot be checked. Chrome, Edge and Safari are read (2026-11-06).
- **Windows and Linux menu keys.** On Windows, a press of Alt on its own can move focus to a browser menu bar. A gesture that uses Alt alone is therefore a candidate only if the browser lists confirm that it does not conflict.
- **Assistive technology.** Screen readers reserve their own keys. The shell has to show the access key as text on each control (UX-012 criterion 4), so the key is announced whichever gesture is chosen.
- **Host page.** The editor must not react when focus is in the host page (UX-012 criterion 6). A gesture handled only while the editing surface or the shell has focus meets this.

## Options

| Option | For | Against |
|---|---|---|
| A. Alt, pressed and released alone, enters access-key mode; a letter or digit then runs the command; Escape leaves | Alt-based access keys are the usual word-processor convention (a general assumption; the spec does not name it) | Alt alone opens the browser menu bar on Windows (to be checked in Firefox's list); Safari and Chrome differ |
| B. Alt+Shift+letter per command, no mode | No mode to leave; each command has a fixed sequence | Browsers reserve many Alt+letter sequences; the table would need a conflict per browser |
| C. A documented sequence such as Ctrl+Alt+letter, with a shown key list | Few browser reservations on Windows | Unknown reservations in Firefox and Safari; Ctrl+Alt is AltGr on some keyboards |

## Proposal

Adopt option A, provisionally, and only after the Firefox list is read and checked against it. This is the lane's recommendation, not a decision. If the Firefox list reserves Alt alone, adopt option B for the commands that do not conflict and leave the rest of the table as "not checked". The choice must be recorded in 13 section 4 (spec default) or in a decision by the owner, and the chosen gesture then goes into the shortcut table as a shell row with its conflicts.

## Consequences if accepted

- A shell key handler in `packages/ui` (the shell's keyboard code, not the root configuration) sends key presses to `pressAccessKey` and shows `reasonKey` as an accessible message.
- The shortcut table gains a shell row for the gesture, with its conflicts (UX-013 criterion 3 then holds).
- A browser test (Playwright) runs in Chromium, Firefox and WebKit; that run is not done in this lane.
- UX-012 criteria 1, 3, 4 and 6 and UX-013 criteria 1, 3 and 4 remain open until those steps are done.

## Not decided here

- The gesture itself.
- Whether Firefox reserves the proposed gesture (the list must be read first).
- The key label shown on a control, and its text for assistive technology (a design and string decision, UX-063 and UX-064).

## Later record

- 2026-11-15: the owner chose option A (docs/owner-decisions-2026-11-15.md, decision 116). The Firefox list had not been read then.
- 2026-11-20 (lane w3, UX-013): the four lists were read. Firefox's gives Alt on its own the meaning "Toggle Menu Bar activation (showing it temporarily when hidden)" on Windows and Linux, and Edge's gives it "Set focus on the Settings and more button" on Windows. Chrome's and Safari's lists do not name the key on its own. So the condition this record put on option A does not hold in Firefox and Edge. The shell takes the key where the browser lets a page take it; what each browser then does is not measured. Nothing is changed here: whether to keep option A is the owner's (UX-012 criterion 3).
