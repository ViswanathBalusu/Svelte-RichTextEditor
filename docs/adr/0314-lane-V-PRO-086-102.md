# ADR 0314: Lane V-PRO-086-102 decisions (proposed)

Status: proposed. Owner decisions stay with the owner; the spec default is used and recorded here.
This file is separate from `0314-lane-U-PRO-086-102.md`, which belongs to an earlier lane of the same
range.

## Context

Lane V-PRO-086-102 closes the protocol stories PRO-096 to PRO-102 where their blockers are object
storage, a container, or a written decision. It works from the highest number down (PRO-102, PRO-101,
PRO-096 in this round).

## Decisions

1. PRO-101 criterion 5 is met by a section of the integration guide, not by a new file. The section
   "Backend tiers (05 section 9; PRO-101)" in `apps/reference-host/docs/integration-guide.md` gives
   the three tiers of 05 section 9, what each may announce, and that a relay is for trusted clients
   only (SYN-044, and 04 section 14). Its wording follows 05 section 9 and 04 section 14. The test
   `apps/reference-host/test/v-pro-101-tiers-guide.test.ts` holds the table rows and the sentence.

2. PRO-096 criterion 1 is ticked on the reading that `upload()` resolves the asset identifier
   (`{ asset }`, the port contract in `packages/protocol/src/ports/optional.ts`), and that the
   resolved URL comes from `resolve()` once `asset.ready` has arrived. The criterion says "its URL".
   This is the reading already recorded in `docs/adr/0110-backend-dep-backlog-batch.md`; the owner may
   prefer `upload()` to return the URL too. The test
   `packages/backend-dep/test/v-pro-096-s3-upload.test.ts` sends the bytes to a real pre-signed PUT
   of the S3-compatible store (`docedit-test-s3`, Podman). The presigned address is made by the asset
   worker's own S3 code (`services/asset-worker/src/s3.ts`), not by the mock server, and the test
   reads the bytes back from the store. The keys sit under a prefix that the run creates and deletes.

3. PRO-102 recommendation (proposed, for the maintainers to accept or reject). This is the written
   recommendation the spike asks for. It is not a decided wire format.

   - Transport: HTTPS with HTTP/2 (HTTP/1.1 is accepted for the first sidecar). Each authority call
     is one request and one response. The authority service is server-to-server, so browsers never
     call it. Problem details (PRO-040) carry transport errors.
   - Encoding: canonical JSON of the kind the protocol already uses for its canonical-hash fixtures
     (PRO-110), so that a commit has one byte sequence in every language. Bodies over a set size
     (a long `open` log) are sent as newline-delimited JSON, one commit per line.
   - Mapping of 05 section 10 (`{stateId}` is the hash-chain head):
     - `open(doc, checkpointRef, commits, stateId)`: `POST /v1/authority/documents/{doc}/open`, body
       `{ checkpointRef, commits, stateId }`. The answer is `201` with the new `stateId` and the
       sequence reached. A `commits` array is streamed as NDJSON when it is large.
     - `applyCommit(stateId, commit, permissions, preconditions)`:
       `POST /v1/authority/states/{stateId}/commits`, body `{ commit, permissions, preconditions }`.
       A rejection is an answer, not a transport error: the answer is `200` with
       `{ rejected: { code, ... } }` in the same shape as a `SyncReject`. The success answer carries
       the mapped steps, the scopes touched and the new `stateId`.
     - `materialise(stateId or seq)`: `GET /v1/authority/states/{stateId}/content?seq=N`.
     - `mapRanges(stateId, ranges)`: `POST /v1/authority/states/{stateId}/ranges`.
     - `restoreSteps`, `diff`, `attribution`, `migrate`, `evaluateRules`: `POST` under the same state
       path, one route each.
   - The state identifier is in the path so that the call names the state it reads or changes, which
     keeps a call from being applied to a stale head by accident.

4. PRO-102 options ruled out (for the reviewers):
   - gRPC (HTTP/2 with generated stubs). It is a fine wire for non-browser clients, but it adds a
     second interface definition to keep in step with the artifacts of PRO-001 to PRO-003, and the
     canonical-hash rule still needs a byte-exact encoding, which protobuf does not give by default.
   - MessagePack or CBOR. They are smaller than JSON, but they add a second canonical encoding that
     every client must reproduce for the hashes. The size gain is not measured, so it is not a reason
     to take that cost now.
   - WebSocket for the authority calls. These calls are request and response, and the channel that
     carries streams to clients already exists in DEP (05 section 4). A second socket for the
     sidecar would duplicate it.
   - JSON-RPC over stdio. It suits a local process, not a network service between two tiers.

5. Effect on a non-JavaScript client. Any language with an HTTP/2 or HTTP/1.1 client and a JSON
   library can call the interface. The one hard requirement is the canonical JSON: the client must
   produce the same bytes for a commit as the service, which the protocol's canonical-hash fixtures
   (PRO-110) test in each language. A client in another language does not need the TypeScript
   typings, only the schemas of the interface.

6. PRO-102 criterion 2 stays open. No prototype of `applyCommit` over this binding has been built in
   this lane, and no CPU overhead has been measured. The target of 04 section 12 is a figure for the
   reference machine (ADR 0037), so a measurement on this development machine would not count as
   meeting it. The needed work is a prototype on the reference machine, which this lane cannot run.
   It is listed in needsFromOthers of the lane report.

## Consequences

- PRO-101 criterion 5 ticked, with a Node.js test that checks the guide's tier table and the trusted-clients sentence.
- PRO-096 criterion 1 ticked on the reading in decision 2.
- PRO-102 criteria 1 and 3 are met by this written recommendation; the recommendation itself waits
  for the maintainers' decision.
- Criterion 3 of PRO-101 (the kit runs `core-relay`) and criteria 1 and 2 of PRO-101 (native and
  sidecar announcements) stay open: they need PRO-124 and the authority service interface.

## Round 3 (2026-11-13)

7. PRO-099 criterion 3 is ticked on a positive control. The absence check (no `.de-presence` with
   `presence: false`) on its own cannot show that the gate can open. The control in
   `packages/element/e2e/pro-099-mock-backend.spec.ts` mounts a second user (`bob`) on the same
   document of the default mock, and the first editor then shows `.de-presence`. It passes in
   Chromium, Firefox and WebKit on port 57140 (3 of 3 each).

8. PRO-098 criterion 2 stays open. The reference-service half now passes in Node.js
   (`pnpm vitest run packages/tck/test/ports.test.ts`: 112 passed, 46 skipped as not applicable to
   the mock). The criterion also needs `backend-local` (PRO-100), which does not exist. Note: one
   full run of the same file failed 46 reference cases with `fetch failed: bad port` on the
   discovery request; the next two full runs and a single-case run passed. The cause was not found.
   It is recorded as a flake to watch, not as a fix. The known exclusions in `DEP_ON_REFERENCE`
   (BE-037 and the three ordering cases) are unchanged.

9. PRO-100 was not started in this round. Its five criteria need a `backend-local` package that
   does not exist. The package would persist the segment logs and the grants of `MockDocument`
   (`packages/backend-mock/src/document.ts`) in IndexedDB and fan commits out over
   `BroadcastChannel`. That needs a restore path in `MockDocument`, which has only a creation
   constructor today, and browser tests for reload and two tabs. It is too large for the time left
   in this lane and is left for a later round, with its Notes unchanged.

10. PRO-097 criterion 4 (imports) stays open. The `ImportsPort` (`packages/protocol/src/ports/optional.ts`)
   has `request` and `get` but no upload. Adding one changes a public port type and depends on the
   owner's reading of PRO-096 criterion 1 (decision 2 above).
