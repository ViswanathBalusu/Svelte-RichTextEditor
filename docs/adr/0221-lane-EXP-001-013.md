# ADR 0221: Open questions from lane EXP-001-013 (export, round 1)

**Status:** proposed. Nothing here is decided. Each item uses the spec default until the owner or the joint owner decides.

**Context.** Lane EXP-001-013 works on the export stories EXP-001 to EXP-013 in `docs/stories/EXP-export.md`. Three questions below need a decision across packages, or a decision the spec leaves open. The lane did not change the hash or the manifest contract, and did not edit another lane's package.

## 1. Options in the bundle hash (EXP-005 criterion 6)

The story says the options are recorded in `manifest.json` and are part of the bundle hash, so jobs with different options never share a cached result.

- Today `manifest.json` records the options (`convert.ts`, `options` block), but `bundleHash` is the SHA-256 over the sorted `name sha256` lines of the files (`convert.ts`), and the manifest is not in that list. An option whose value reaches no file leaves the hash the same.
- `services/export-worker/src/verify.ts` recomputes `bundleHash` the same way and refuses a mismatch (`'Its bundle hash is wrong.'`). Changing the converter alone would make every bundle fail verification.
- Options: (a) add a `options` line to the hash input in `convert.ts` and in `verify.ts` together; (b) keep the hash over files and make each option reach a file (for example a comment line in `main.tex`), which changes bytes and needs no contract change; (c) keep the story as it is and say that cache separation relies on the request key (EXP-006 already keys on the options).
- **Spec default:** (c) until a decision. Owner: the export-worker and export-latex owners, with the spec author for 09 §9.1.

## 2. The chain head in the export result (EXP-011 criterion 5)

- The converter writes `chainHead` into the manifest when it is given one (`ConvertOptions.chainHead`).
- `services/export-worker/src/job.ts` passes `chainHead: null` (around line 235). The result that the job returns holds `bundle.hash`, the class version, the CDM version and the options, but not the chain head.
- The fix belongs to the worker: pass the head of the log at `seq` and expose it in the result, so the host can anchor the export. The commit path already holds the head.
- **Spec default:** the manifest holds the head when the job supplies it; the result exposes it. Owner: export-worker lane.

## 3. Spacing in the flattened style (EXP-013 criterion 5)

- The style macro in `styles.tex` carries font size, weight, shape, alignment, the three indents, widow control, keep lines and the line rule. It does not carry spacing before and after, keep with next, page break before or contextual spacing (`props.ts` `setters`).
- `blocks.ts` and `flow.ts` apply those from the same resolved paragraph (gap and keep logic). The values are equal to the cascade at the point of use, but they are not in the flattened macro.
- Question: does a "flattened style" under 03 §6 have to carry them in its macro? If yes, the macro gains four setters and the flow code reads the macro instead. If no, the criterion wording should say which properties the macro carries.
- **Spec default:** not decided; criterion 5 stays unticked. Owner: the spec author for 03 §6 and the CDM/export owners.

## 4. Capacity sheet for the worker plan (EXP-007 criterion 5)

- The criterion needs a capacity sheet that plans workers from one core and up to 1.5 GiB for each running job. No file under `docs/` is named as that sheet.
- `docs/research/2026-11-06-unit-cost-sheet.md`, row A17, states "4 (one vCPU and 1.5 GiB each)" for jobs per worker node, with the job limits of 09 §8 and §9.3 as its source. It is a research note for SPK-025, and no test reads it.
- **Spec default:** the criterion stays unticked until the owner says whether that research note is the sheet, or a sheet is written in the operator's documents. Owner: the owner of 09 §9.3 and the operator lane.
