# ADR 0328 (lane V-UX-046-060): decisions for the blocked UX-046 to UX-060 criteria

Status: proposed. Lane V-UX-046-060, round 1, 2026-11-13. Owner decisions stay the owner's; each
item below uses the spec default and says so.

## Decision 1: the code of an extension problem on `de-error`

The element raises an extension problem (an invalid manifest, an unsupported API version, a failed
activation or removal) as a `de-error` event. 05 section 5.8 gives no code for extensions, so the
element uses `internal` (the spec default for an error with no registered code, as `register.ts`
does for a command collision). The message names the extension: `extension <id or #position> was not
loaded: <reason>`. It never carries document content. Owner to decide whether an `extension` code
should be added to the registry.

## Decision 2: the shell's extension list and the element's `extensions` property

`extensions` on the element is read at mount and set on each change. The shell's `setExtensions`
runs `ExtensionHost.sync` (packages/ui/src/extensions/host.ts). The shell's API for an extension
offers `registerCommand` only; panels, toolbar groups, hooks and filters remain on their own
properties. The API version list is `['1']`, which is the spec default (ADR 0136, decision 12).

## Decision 3: a command the harness counts as run

`tryRegister` in packages/ui/e2e/harness/main.ts records each run of a registered command in
`commandRuns()`. The harness previously recorded only core calls, so a command's run could not be
seen. This is a test-only change.

## Decision 4: accessible name as the screen-reader check (UX-051 criterion 5)

UX-051 criterion 5 asks for keyboard and screen-reader use. The test reads the accessible name
through Playwright's accessibility name and runs the command from the keyboard. No screen reader
was run, and the evidence says so.

## Decision 5: the UX-057 and UX-058 criteria stay open

Criteria that need an extension node in the document (custom blocks, inline content and the
fallback view in the editing surface) need a schema change in the core and a rendered fallback. They
are not built, so they stay unticked. The authority's `unsupported_feature` answer for UX-056
criterion 4 is a decision (the spec says `unsupported_feature`; the room answers `conflict`, as
lane U-UX-046-060 recorded in ADR 0328, decision 2). This lane does not change it.

## Decision 6 (round 2): UX-046 criteria 2, 4, 5 and UX-048 criterion 5 ticked on the room path

Round 2, 2026-11-13. The assistant's commits are tested through the in-process room
(`packages/authority/test/ux-046-assistant-commit.test.ts`, 4 tests). A suggester's result is accepted
only as `ins` marks naming the suggester; a viewer's result in the inherit region is refused with
`permission_denied`. These are the rules the authority already applies (P4; PRM); no rule is changed.
Two points are the spec default and are stated here so the owner can overrule them:

- UX-046 criterion 2 ("history shows both") is joined by field name: the room's stored commit carries
  `user`, `origin` and `agent`, and the history test shows that history names both for such a commit.
  No test runs the two together. The owner or HIS can ask for an end-to-end test.
- UX-048 criterion 5 is ticked with the room's insertion test plus the existing export escape test.
  The two tests do not run in one pipeline. The spec's "when it is applied" is read as the commit
  path, since the assistant pane (UX-045) that produces the result is not built.

UX-046 criteria 1 and 3 remain open (decision 4 of the U lane). UX-047 criterion 3 and UX-048 criterion
6 stay open for the reasons given in their Notes.
