# ADR 0208: Reflow of the web view and the table scroll it uses (lane FE-105-117)

Status: proposed (2026-11-13). Written by lane FE-105-117, round 2, for FE-106. Not confirmed by the owner or by the accessibility specialist.

## Context

FE-106 asks that paragraphs reflow at 320 CSS pixels with no horizontal scroll, and that only tables and images scroll sideways, each in its own container. The spec does not say how a table scrolls. The web view's editing surface (`packages/element/src/styles/element.css`) had no width rules for tables or images.

## Decision (proposed)

1. The editing surface and sub-editors take the width of their container (`max-inline-size: 100%`, `min-inline-size: 0`) and break long unbroken words (`overflow-wrap: anywhere`). No fixed inline or block size is set on them.
2. Images inside them are capped at the container width (`max-inline-size: 100%`, `block-size: auto`).
3. A table inside them is a block (`display: block`) with `overflow-x: auto` and `max-inline-size: 100%`. The table keeps its rows and cells; only its box scrolls.
4. The rules live in a new file, `packages/element/src/styles/reflow.css`, concatenated after `element.css` and before the shell's sheet in `packages/element/src/styles.ts`.

## Why

`display: block` on a `<table>` is the usual way to let a wide table scroll inside its own box without changing its cells. The alternative, wrapping each table in a scroll container, needs a change to ProseMirror's node view for tables in the engine, which is FE-040's and FE-066's area and was not in this lane.

## Consequences and open points

- A table that is `display: block` may lay out column widths differently from a table in normal display. A browser check at 320 CSS pixels is needed before the rule is accepted. Until then FE-106 criteria 1, 2 and 4 stay unticked.
- The spec's default for the sub-editors' reflow is assumed to be the same as the web view's. Not stated in 02 §10.
- Whether the shell's own page width (`packages/ui/src/styles/shell.css`) can exceed 320 CSS pixels was not checked and is UX's to change.

## Also recorded in this lane (no decision taken)

- FE-113 criterion 2 (touch device uses the web view): the decision function exists in `packages/element/src/view-select.ts`; the element does not call it yet. Left to the lane that wires `view` (FE-065 Notes).
- FE-116 criterion 4 (`Selection.getComposedRanges()` for Safari and the Firefox `getSelection` patch): not built; the Firefox and WebKit shim exists in `packages/engine/src/view-support.ts`.

# Plan for FE-112: bidirectional, complex-script and East Asian layout in the page view (round 3, 2026-11-13)

Status: proposed. Written ahead of SPK-013, so it is a plan for a page view that may not go ahead. Not reviewed by the maintainers. It is a written plan, not a decision; it changes no code.

## What is in the code today (checked by reading)

- `packages/layout/src/measure.ts`: `TextMeasurer.advance(font, text)` returns one width. The optional `advances(font, text)` returns one advance per UTF-16 code unit, and ligature interiors carry 0. Nothing returns cluster boundaries.
- `packages/layout/src/lines.ts`: `BreakOpportunities.opportunities(text)` returns UTF-16 offsets only. There is no language tag, no class per offset and no prohibition rule. `firstFitBreaker` is greedy.
- `packages/layout/src/caret.ts`: caret and selection geometry work on `DocPosition` and `PaintedLine`. No bidi level is carried, so every line is treated as logical order from left to right.
- Nothing in the layout package reorders text for bidirectional display.

## 1. Bidirectional reordering, caret movement and selection rectangles (criterion 1)

- Reordering follows the Unicode Bidirectional Algorithm (UAX #9) per paragraph. The engine computes the embedding level of each run and stores it on the run in the layout tree (`PaintedLine` gets one level per run, in logical order).
- The visual order of runs on a line comes from the levels (rule L2). Hit testing and the caret map a logical offset to an x position through that visual order, not through the DOM.
- Caret movement by character moves in logical order inside a run and crosses run boundaries in visual order at direction changes, which is what users expect at a mixed boundary. Home and End (FE-097) use the paragraph's start and end in logical order.
- A selection rectangle is one rectangle per visual run of the selection on each line, so a selection that spans an embedding boundary gets two or more rectangles.
- The painter keeps `white-space: pre` and sets the `dir` of the line box from the paragraph direction. The browser does not reorder what the engine has laid out, so the levels must agree with the browser's own rendering of the same paragraph. That agreement is what the CI harness of 09.3 must check per browser.

## 2. Complex scripts: measurement clusters and shaping checks (criterion 2)

- The measurement provider must return cluster boundaries as well as advances. A cluster is the unit a caret or a break may not split (an extended grapheme cluster, and for Indic scripts and Thai the shaped cluster). The current per-code-unit `advances` does not carry this, so the interface needs a new optional method (for example `clusters(font, text)` returning start offsets and advances per cluster). The existing method stays for Latin text.
- Shaping (ligatures, reordering of Indic vowel signs, and mark positioning) is produced by the measurer, not by the engine. A HarfBuzz-based measurer compiled to WebAssembly (spike S5) is the candidate, and it belongs to the WASM epic.
- Shaping is checked against the typeset result: for a sample of paragraphs in Arabic, Hebrew, Devanagari and Thai, the engine's line widths and cluster positions are compared with the widths the browser paints (the 09.3 harness, within half a pixel). A paragraph that fails is reported, not silently re-laid out.

## 3. East Asian line breaking beyond FE-080 (criterion 3)

- FE-080 uses a bundled Unicode line breaking algorithm (UAX #14). For Japanese, Chinese and Korean text this needs more than the default rules:
  - the prohibition of certain characters at line start or line end (the kinsoku rules for Japanese and their equivalents for Chinese);
  - the treatment of ideographic spaces and of small kana as non-starters;
  - the tailoring by language, so the breaker needs the run's language tag (`lang`) as an input;
  - the handling of Korean word spacing, which breaks at spaces only.
- The interface change is small: `BreakOpportunities` takes an optional language per run. The rules themselves are data in the bundled breaker, and their coverage is tested with the property tests of FE-080.

## 4. What each provider interface carries and what the WASM epic provides (criterion 4)

- `TextMeasurer` (FE-079): advance per run as today; cluster boundaries and their advances (new, optional); a per-font flag for whether shaping is applied (so the cache key of 02 §6 includes it).
- `BreakOpportunities` (FE-080): opportunities as today; a language tag per run (new, optional); a per-offset class where a break is forbidden (new, optional).
- Bidi levels (new, produced by the engine from UAX #9 data): one level per run, in logical order.
- The WASM epic must provide: a shaping kernel with cluster output (for complex scripts), and optionally UAX #9 and the tailored UAX #14 data, if the engine does not carry them in TypeScript.
- Size estimate, by the story scale: the bidi levels and the caret and selection changes are L; the cluster interface and the shaping check are L, and depend on the WASM epic; the East Asian tailoring is M; the language tag and forbidden-break class are S.

## Open points

- SPK-013 decides whether the page view goes ahead at all. Until it does, nothing here is built.
- Whether the bidi reordering is done in TypeScript or in the WASM kernel is open. The spec does not say; the default taken here is the TypeScript engine, with the kernel optional.
- The review of this plan has not happened; FE-112 criterion 4 stays unticked until it has.

# FE-107 presence announcements: two readings (lane FE-105-117, round 5, 2026-11-13)

Status: proposed. Not confirmed by the owner or by the accessibility specialist.

The spec (02 §10) says that a collaborator arriving or leaving is announced, with the name from `resolveUsers`. It does not say which sessions count, or what the reader hears when it opens.

1. A session is the unit. A user with two sessions open gives two notices, one per session. The alternative (one notice per user, while any session remains) is not taken.
2. The peers already in the document when the reader opens it are the baseline, and are not announced. Later arrivals and departures are. The alternative (announce every peer on open) would flood a reader who joins a busy document.

Fixer round 5 (2026-11-13): reading 2 as first built did not hold. The core's `presence` list starts empty and is filled only when the backend's first `presence.state` arrives, which is after the session starts watching, so the baseline was always empty and every peer of a busy document was announced. The protocol does not mark a list of the peers already there (gap G42 in `packages/protocol/src/definition/gaps.ts`: whether `presence.state` is a full set or a change). The document service sends the peers that have published right after `ch.opened`, and nothing when there are none (`services/document-service/src/data-plane/presence.ts`, `join`). The reading now taken:

- The session hands the core a wrapped presence port. After the core has taken its first `presence.state`, its list is the baseline.
- When no `presence.state` arrives within an opening window after the channel is attached, the list then (empty) is the baseline, so a reader who opened the document alone hears the first arrival. The window is `DEFAULT_PRESENCE_BASELINE_MS`, 500 ms: a provisional default, not a measurement; `SessionOptions.presenceBaselineMs` overrides it.
- Known limits. A peer that joins and publishes within the window of a reader who opened alone is taken as already there and not announced. A list on joining that arrives after the window is announced, one notice per peer. A peer update held because its `seq` is ahead of the reader (SYN-036) is announced when it is placed. backend-mock sends no list on joining, so against it a peer that was there before the reader is announced when it first publishes after the window.

Both readings are implemented in `packages/element/src/presence-notices.ts` and `packages/element/src/session.ts`, and tested in `packages/element/test/fe-107-presence.test.ts` and `packages/element/test/fe-107-presence-core.test.ts` (the real core and backend-mock, with the service's list on joining added to the reader's port). The accessibility specialist confirms or changes them; whether `presence.state` on joining is a full list is for the protocol owner (G42).
