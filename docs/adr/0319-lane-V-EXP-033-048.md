## Earlier items (restored)

E1. **Date pattern and the job's time zone (EXP-033, criterion 2).** A `date` form field stores a
   calendar date (`YYYY-MM-DD`). When fields are flattened, the converter applies the field's
   `datePattern` to that date anchored at UTC noon (`formFieldValue` in
   `packages/export-latex/src/inline.ts`, `timeZone: 'UTC'`). The export job's time zone (the bundle
   carries one, `bundle.ts`) is not used. The criterion says dates are formatted "using the export
   job's time zone". A calendar date has no instant, so a zone does not change its day, but the code
   and the criterion read differently. `packages/export-latex/src/exp-033-format.compile.test.ts`
   compiles a number, a date with a pattern and a choice label in the Podman sandbox and reads them
   from the PDF (a pass on 2026-11-13, as the EXP-033 Notes record; not rerun by the fixer). Default kept: UTC noon, no change to the converter. Criterion 2 stays
   unticked. Owner question: format the date in the job's time zone (which matters only for a pattern
   that prints a time or a zone), or reword the criterion to say the stored calendar date is printed
   as it is. The same question is ADR 0115, item 32, and ADR 0319 (lane U-EXP-033-048), item 2.

E2. **`/run/secrets` overlay in the export sandbox (EXP-072).** ADR 0324 §1 records that this lane
   added `--tmpfs=/run/secrets:ro` to the job's arguments in `services/export-worker/src/sandbox.ts`,
   citing the readiness probe of that time, and cited this ADR for it. The overlay had been withdrawn
   before (ADR 0346, lane U-SEC-033-048, "Round 3 fix"), because the EXP-072 escape case in
   `sandbox.escape.test.ts` asks for no `/run/secrets` at all. Current state (read 2026-11-14): the
   job's arguments in `sandbox.ts` have no `/run/secrets` overlay; the host's files are kept out by the
   empty default mounts file (`container.ts`), and `secrets-probe.ts` accepts either form. Whether the
   job keeps an overlay is open and left to the main session (ADR 0324 §1).

E3. **Earlier font and image items (EXP-047, EXP-048, EXP-073).** The story Notes of this lane's

## Round 3 items

1. **Title metadata (EXP-043, criterion 1).** The class writes the document title to XMP `dc:title`
   only. Under `\DocumentMetadata` with PDF 2.0 and PDF/UA, the Info dictionary has no `/Title` in the
   compiled output (observed in the Podman sandbox, 2026-11-13). The test now reads XMP. Default kept:
   no change to the class. Owner question: whether a reader that uses only the Info dictionary (for
   example `pdfinfo`) must also see the title, which would need a different PDF version or profile.

2. **Row-span tagging (EXP-041, criterion 4).** tagpdf records a column span as `/ColSpan 2` (tested),
   but not a row span, because `\DErowspan` is a `\vbox` and the class does not tag the cell. Spec
   default: spans are recorded in the table structure (EXP-112). Proposed: the class tags the covered
   cell with a tagpdf table attribute. This needs class work, and the attribute key is not yet checked
   against the installed tagpdf version. Not built.

3. **Complex-script shaping (EXP-037, criterion 2).** The converter defaults to `renderer=node`
   (`convert.ts`, `renderer: options.renderer ?? 'node'`). The class uses HarfBuzz only when the
   renderer is `harfbuzz`. The criterion says complex-script text is shaped by HarfBuzz. Spec default:
   keep the existing default and do not change it silently. Proposed (owner): choose HarfBuzz for
   paragraphs in complex scripts, or for all exports. Not built.

4. **Row-span shading (EXP-041, criterion 3).** Shading a row span colours its first row only, because
   the rows it covers are not measured (ADR 0143, question 2). Not built.

5. **Split of tall table rows (EXP-039).** The converter does not call `splitRow`, because no row
   height measure exists (ADR 0143, question 2). A measure would come from a compile (layout data,
   EXP-055). Not built. This is an owner decision on the measure and its cost.

6. **Link title emitter (EXP-043, criterion 4).** The link title is written by `pdfHexString`, not
   `pdfString` as `attributes.ts` names. Open question for the owner (already in
   `docs/adr/0115-export-latex-backlog-batch.md`). Not changed here.

7. **Percent-encoding of URLs (EXP-043, criterion 3).** Left as the earlier decision: the whole target is
   hex-encoded, so no TeX-special character reaches TeX. Open question (ADR 0115).

## Round 5 (2026-11-14)

V38. **Vertical alignment in the longtable (EXP-038, criterion 4), status proposed.** The Podman sandbox compile of one four-line row with a top, a centred and a bottom cell (the table of `tables.shading.compile.test.ts`) gives, by `pdftotext -bbox`: top cell at yMin 91.3 pt, centred cell at 94.5 pt, bottom cell at 91.3 pt, the last line of the tall cell at 136.3 pt. So `b{}` and `m{}` set through `\multicolumn` in `longtable` do not move the cell to the bottom or the centre of the row; the cells are top-aligned. The existing check `top < mid < T4` is satisfied by a 3 pt offset and does not show centring, so the round 11 statement that centre is drawn is not proven. Options (none built): a converter pass that measures row height (no font metrics exist in the repository, ADR 0143 question 2), or a class macro that sets the cell's vertical position from a row height the converter supplies. Default kept: no change to `tables.ts` or the class in this round; criterion 4 stays unticked. Owner or main session to choose the approach.

## Round 11 (2026-11-14)

V41. **Row spans carry /RowSpan in the tagged structure tree (EXP-041, criterion 4), status proposed.** The class drew a row span with `\DErowspan` (a `\vbox`), so tagpdf wrote no `/RowSpan`. The latex-lab table test phase has the key `table/multirow` (`latex-lab-testphase-table.sty`), which sets `/O /Table /RowSpan n` on the current cell. Changes: `class/docedit.cls` takes `\DErowspan{rows}{content}` and sets `table/multirow=rows` when tagpdf is loaded; `src/tables.ts` writes the count; `src/convert.ts` adds `testphase={table}` to the `\DocumentMetadata` line whenever tagging is on or draft. Decision for the owner: `testphase={table}` is a test-phase module of the LaTeX kernel, and it is the only route to this key found here. The owner should accept it, or name another route (for example a row span tagged by a class macro), before the criterion is treated as settled. Evidence: `packages/export-latex/src/tables.spans.tagged.compile.test.ts` (criterion 4, both `/ColSpan 2` and `/RowSpan 2`), with `tables.spans.test.ts`, `class.structure.test.ts`, `exp-111-tagging.test.ts`, `exp-015-draft-tagging.test.ts`, `exp-111-tagged.compile.test.ts`, `tables.borders.compile.test.ts`: 7 files, 37 tests passed (Podman sandbox, machine route, `DOCEDIT_REQUIRE_SANDBOX=1`, 100.8 s, 2026-11-14).

## Round 12 (2026-11-14)

V34. **Signature and initials pictures (EXP-034, criterion 1), status proposed.** A `signature` or `initials` value `{ asset, mode }` is drawn as the asset's picture at the field's width (`signaturePicture` in `packages/export-latex/src/inline.ts`). The height follows the image's proportions, read from the bytes the job supplies: PNG from its IHDR chunk, JPEG from its start-of-frame segment (`packages/export-latex/src/signature-picture.ts`). Defaults chosen by this lane, for the owner to confirm: (a) the picture needs the bytes; a job that gives only a hash prints the blank field and keeps `form_value_not_printed`, because the converter cannot read a size it does not have; (b) `mode` does not change the picture, since the spec does not say what the modes print; (c) the label is the alternative text of the picture, as it is of the field. Tests: `packages/export-latex/src/exp-034-signature.test.ts` (Node.js) and `packages/export-latex/src/exp-034-signature.compile.test.ts` (Podman sandbox, PNG; the picture's dictionary is 200 by 100 and the label is in `/Alt`). The JPEG path is not compiled here: no JPEG encoder is in the repository, so its size reader is checked on header bytes only.
