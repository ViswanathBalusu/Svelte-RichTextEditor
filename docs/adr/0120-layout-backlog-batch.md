# 0120. Layout backlog batch: open questions and defaults from the layout packet

**Status:** proposed (2026-11-13). Written by the layout developer in the backlog batch, round 1, for the stories of `packages/layout` (FE-078, FE-081, FE-082, FE-086). Not reviewed by the owner.

## Context

The layout package holds the spike S7 adapters and the first-fit breaker (`lines.ts`), the layout tree (`tree.ts`) and the measurement interface (`measure.ts`). This round adds the page-level pass `paginate.ts` (FE-082), the section page setups it takes (FE-086), and the frozen result that FE-078 asks for. `pnpm vitest run packages/layout` passes 13 test files, 130 tests and 6 skipped (the browser-only cases); `tsc --noEmit` passes for `tsconfig.json` and `tsconfig.test.json`. The browser engines and Podman were not used in this round.

## Decisions taken as defaults

Each of these is a choice the spec leaves open. The spec default is used where one exists; the rest are recorded here so that the owner can change them.

1. **An unbreakable word or line wider than the line or page (FE-081).** Placed alone on its line and overflowing it. The breaker reports nothing, as the spec does not give a rule. Owner question: should the editor warn, or hyphenate, when hyphenation is later allowed?

2. **A block taller than the page body (FE-082 criterion 3).** Paragraphs split across pages at line boundaries and always move on. A box (figure, equation) taller than the body is placed alone at the top of a page and its block identifier is reported in `overflowed`. The spec does not say what happens to a single line taller than a page; the same rule applies to it.

3. **`spaceBefore` at the top of a page (FE-082).** Kept. Word suppresses it in some compatibility modes and not in others. The spec does not say; the default here is the simpler one.

4. **Rule priority (FE-082).** Explicit page breaks, then `pageBreakBefore`, then `keepNext` chains, then `keepLines`, then widow control, as 02 §9.4 orders them. Two consequences are coded and tested. A `keepNext` chain moves as one whole, including a `keepLines` terminal, so a heading is never left alone above the paragraph it introduces. Widow control does not split the first line that a `keepNext` chain has placed, so the chain wins over widow control for that one line.

5. **A `keepNext` chain longer than a page (FE-082).** The chain is broken: when its total height cannot fit a page body, nothing moves for it and pagination goes on. This is the termination guarantee of 02 §9.4 and ADR 0005.

6. **Page break on an empty page (FE-082).** Does nothing, so a break at the top of a page makes no blank page. A break after content starts a new page.

7. **Continuous section break (FE-086).** The current page keeps the setup it started with. The new section's page setup and numbering apply from the next page, so a margin change in a continuous break takes effect at the next page turn. The LaTeX writer reports such a break as unsupported (03 §10); what the editor shows is this default.

8. **`evenPage` and `oddPage` (FE-086).** Test the displayed page number of the section. When the parity does not match, a blank page is inserted, as Word does.

9. **Page numbering (FE-086).** A section with `pageNumberStart` restarts there; without it, numbering continues from the last page. The format is `formatNumber` from `flow.ts`, with `decimal` as the default.

## Open questions left open

- The priority cases of FE-082 criterion 1 are tested, but the comparison with stored fixtures from `packages/model` is not: the conversion of CDM blocks to pagination items is FE-077, which is still a spike.
- Columns, column balancing and footnotes are FE-084 and FE-085; headers and footers are FE-087.
- The tree has no table rows (FE-083), so the shape criterion of FE-078 stays open.

## Decision requested

No decision is taken in this note for the owner. Items 1, 2 and 7 are the ones most likely to need the owner's answer before FE-082 and FE-086 can be called done.

## Round 2 (layout packet, 2026-11-13): headers, footers and columns

`pnpm vitest run packages/layout` passes 14 test files, 148 tests and 6 skipped (the browser-only cases); `tsc --noEmit` passes for `tsconfig.json` and `tsconfig.test.json`. Podman, PostgreSQL and the browsers were not used. Stories: FE-085 (criteria 1 to 3 ticked), FE-087 (criteria 1, 2 and 4 ticked), FE-082 (criterion 5 ticked).

10. **A `continuous` break that changes the column count (FE-085).** The current page changes its columns at once, as Word does: the tallest column ends the earlier run and later content starts below it in the new column count. Other page setup from a continuous break still applies from the next page (item 7). Owner question: confirm the column case.

11. **Balancing (FE-085).** Amended in the fix round (below): every multi-column run that a `continuous` break ends is balanced on the page where it ends, whatever starts it (the document's start, any section break, or a `continuous` break mid-page). The round 2 rule (only a run that starts at the top of a page and fits on one page) did not meet the criterion. The balanced column bottom is the lowest at which the rest of the run holds on that page, found by bisection to 0.001 points (a precision, not a figure of the spec). Earlier pages of a long run fill their columns in order. A run that ends at another kind of break is not balanced.

12. **Column width and breaks (FE-085).** The caller breaks paragraphs to the column width; the layout does not re-break lines. `pageBreakBefore` starts a new page even inside columns. A column break in the last column starts a new page.

13. **Headers and footers (FE-087).** The distances default to 0 when the page setup has none, so no distance is invented. The variants are the three stories of `page_setup` (03 §4.1): default, first and even; there is no odd story. Amended in the fix round: the first page of a section takes the `first` story when `differentFirstPage` is set, and none when that story is missing; under `differentOddEven` even pages take the `even` story, and none when it is missing; every other page, odd pages included, takes the `default` story, and none when it is missing. This follows OOXML, where the default header serves odd pages. Owner question: whether a missing first or even story should fall back to the default story instead of leaving the page bare (Word leaves it bare within a section, but inherits from the previous section; the CDM has no inheritance). `differentOddEven` tests the displayed page number. A story is moved by its distance and its left margin; tables inside a story are not moved inside. The story factory gets the page number and the document's page count. The count is iterated (at most 8 passes, `MAX_COUNT_PASSES`); when it does not settle the result says so (`pageCountSettled`), and the pages of the last pass are returned. Owner question: whether the count should instead be fixed by a second layout over the whole document.

Not decided here: how a table inside a column or a story is placed (FE-083), footnote placement (FE-084), and the painted page number (FE-090).

## Fix round (group 4 round 2, 2026-11-13)

A reviewer unticked FE-082 criterion 5, FE-085 criterion 3 and FE-087 criterion 1. `pnpm vitest run packages/layout` passes 15 test files, 160 tests and 6 skipped; `tsc --noEmit` passes for `tsconfig.json` and `tsconfig.test.json`. Items 11 and 13 above are amended. In addition:

14. **Runs of columns that start mid-page (FE-085).** Every column of a run that a `continuous` break starts mid-page starts below the tallest column of the earlier run. Before this round only the first column did, and the others started at the top of the body, over the earlier content. Such a column passes what does not fit on to the next column or page; only an empty column at the top of a page is made to take one line (the termination rule).

15. **Flow blocks to pagination items (FE-077, FE-082).** `items.ts` is the adapter from the flow to `paginate`: paragraphs are broken by the first-fit breaker at their section's column width, and line offsets are CDM offsets inside the block. A paragraph split at a page or column `break` (`flow.ts`) becomes paragraph items with one block identifier and a break item between them; the round 2 note that the split is not built was wrong. Limits, until their stories are built: tables are not paginated (FE-083) and are returned in `unplaced`; a tab and an inline image are measured as one character; after a `continuous` break, paragraphs are broken to the new section's column width although its page width applies from the next page. The line break opportunities in the tests are a stand-in until FE-080.

The open question "the conversion of CDM blocks to pagination items is FE-077, which is still a spike" now has a first answer in item 15; FE-082 criterion 1 still lacks the stored fixtures.

## Round 3 (layout packet, 2026-11-13): footnotes and the engine entry point

`pnpm vitest run packages/layout` passes 17 test files, 173 tests and 6 skipped (the browser-only cases); `tsc --noEmit` passes for `tsconfig.json` and `tsconfig.test.json`. Podman, PostgreSQL and the browsers were not used. Stories: FE-084 (criteria 1 to 3 ticked), FE-076 (criteria 2 to 5 ticked). The reviewer unticked FE-084 criterion 2 and FE-076 criterion 2; both are re-ticked in fix round 3 below, which also replaces item 17 and amends item 20.

16. **Footnote area and the first body line (FE-084).** A page's footnote area takes at most its body height less the first line of its body (`PageFrame.area`), so a page with body text keeps one line of it. A page whose first body item is a box keeps none. Owner question: whether a footnote line should move with its reference line when the area would otherwise leave the body empty.
17. **Reservation between passes (FE-084).** The body pass is repeated with each page's footnote area reserved at the bottom. The reservation only grows between passes (the larger of the earlier reservation and the area the footnotes took). A reservation that shrank let a reference move back and forth between two pages, and the passes did not end: the sweep of `notes.test.ts` showed it. The cost is that a footnote which moves to a later page leaves its earlier reservation empty in that pass set. Owner question: whether a later pass may give back an unneeded reservation with a bound.
18. **Footnotes left after the last page (FE-084).** They take a page of their own, numbered on from the last page, with no headers or footers, because its stories would need their factories. Owner question: whether such a page should repeat the stories of the last page.
19. **Separator and spacing (FE-084).** No separator is drawn above a footnote area; footnotes are spaced by their paragraphs' `spaceBefore` and `spaceAfter`. The spec does not say either. Footnote numbering does not restart: `footnoteRestart` is not read by `flow.ts`, so FE-084 criterion 4 stays open.
20. **The engine entry point (FE-076).** `layoutFlow` (`engine.ts`) takes a flow document, the two injected providers and an optional story resolver, and returns the tree with the unplaced and overflowed block identifiers and the settled flag. The tree's engine name is `@docedit/layout@0.0.0`, the package's own version. The providers in the sweeps are TypeScript stubs; no WebAssembly kernel is built.

## Fix round (group 4 round 3, 2026-11-13)

The reviewer found that the footnote sweep of round 3 had a degenerate generator: with a sound one (mulberry32), about 1.7% of 3000 documents did not settle within `MAX_COUNT_PASSES` (8). The cause was item 17: a page's reservation was raised once per whole pass, and each raise could push a reference, and its footnote, on to the next page, so the unsettled page moved forward about one page per pass. `pnpm vitest run packages/layout` passes 17 test files, 177 tests and 6 skipped; `tsc --noEmit` passes for `tsconfig.json` and `tsconfig.test.json`.

17. **(Replaces round 3 item 17.) Footnote areas settle inside the pass (FE-084).** There is no reservation between passes. While a page fills, each body line or box is taken only when the footnote area that the page would then need fits below it (`noteAreaAccepts`, `notes.ts`); the area is worked out again for each candidate line. The rules: carried footnote text comes first and takes as much of the page as it would on its own (up to item 16's limit); a new footnote is kept whole on the page of its reference; only a footnote taller than item 16's limit is split, and then only its first line has to be on the page of its reference. A refused line moves on with its reference. The first line of an empty page is always taken (termination), so under carried text its footnote may start on the next page. The page-count iteration (item 13) is the only one left, so `pageCountSettled` now speaks of the stories only. Column balancing trials do not see footnotes. Owner questions: whether a short footnote should rather be split, as Word sometimes does, to keep more body text on the page; whether carried text should yield to body text.
20. **(Amends round 3 item 20.) The engine's inputs (FE-076).** `layoutFlow(doc, providers)` takes the flow document and three providers (`ItemProviders`): the measurer, the break opportunities and the line breaker (`LineBreaker`, `lines.ts`; `firstFitBreaker` is the package's own). The optional story resolver is no longer an engine input: the engine lays out the flow's own header and footer stories with the same providers (`flowStoryResolver`, `items.ts`), with the `page` and `pageCount` fields set per page. Stories are broken to the page's text width; tables and breaks inside a story are not laid out. `documentItems` still takes a resolver, for callers that bring their own stories.
21. **A box and the footnote area (FE-084).** A box is placed only when the page's footnote area still fits below it, like a line; on an empty page it is always placed.

Items 13 and 15 were left open by the review before round 3; neither round 3 nor this fix round decides them. (1) The missing-story fallback is still the owner's question (item 13). (2) After a `continuous` break, paragraphs are still broken to the new section's column width on a page that keeps the old width; a fix needs the page context in the breaker (or the widths applied in `paginate`), which is not built. (3) Tables are still not paginated (FE-083) and are still returned in `unplaced`; tab stops and inline images are still measured as one character.

## Round 4 (layout packet, 2026-11-13): justification and incremental line breaking

`pnpm vitest run packages/layout` passes 19 test files, 189 tests and 6 skipped (the browser-only cases); `tsc --noEmit` passes for `tsconfig.json` and `tsconfig.test.json`. Podman, PostgreSQL and the browsers were not used. Stories: FE-091 (criterion 2 ticked), FE-088 (criteria 1 and 4 ticked). The leftover points of the last review (the footnote rules of fix round item 17, and the note on this file's scope) are unchanged in code: item 17 already records them.

22. **Justification (FE-091).** The stretchable spaces are ordinary (U+0020) and no-break (U+00A0) spaces. Tabs never stretch. The trailing run of spaces, no-break spaces and tabs at the end of a line never stretches; the spec does not say how a trailing no-break space is treated, so it is treated like a trailing ordinary space. A line already at or over its target width is not shrunk. Owner question: whether a no-break space at the end of a line should stretch.
23. **Incremental line breaking (FE-088).** The engine is unchanged: `incrementalLayout` wraps the injected line breaker. A paragraph's lines are reused when the block is not marked dirty and its breaker input is the same as before; a changed input is re-measured even when no edit marked it, so a missed mark cannot leave a stale tree. Pagination still runs over the whole document; restart at the first affected page (FE-088 criterion 2) is not built. Owner question: none for this round; the design follows the criterion as written.
24. **Packet-wide limits, unchanged.** Background pagination in time slices (FE-089) is not built: the page pass is one synchronous call, and no resumable form is decided here. Tables (FE-083), line-break opportunities from the Unicode algorithm (FE-080) and the painter (FE-090 to FE-092) remain outside this round; the data for FE-080 is not in the repository.

## Round 5 (layout packet, 2026-11-13): frame coalescing and the unsettled count

Stories: FE-084 (criterion 5 ticked), FE-088 (criterion 3 ticked). Both are in the layout package only.

25. **Frame coalescing (FE-088, criterion 3).** `coalescedLayout` takes the frame request from the host as a parameter (`requestAnimationFrame` in a browser; a queue in the Node.js tests). The first edit of a frame asks for one frame; the edits before it merge into one pending document and one dirty set; the frame runs one `IncrementalLayout.update`. The tests use a fake queue and a fast-check property over batches of edits. No browser animation frame was run. Owner question: none; the design follows the criterion as written.
26. **The unsettled count with footnotes (FE-084, criterion 5).** The footnote areas settle inside each pass (round 3 fix item 17), so the only iteration that can fail to settle is the page-count one (FE-087). The new test builds a footnote on an unsettled count and checks that `paginate` ends with `pageCountSettled` false, its footnote on the first page, and the body above each area. The count bound (`MAX_COUNT_PASSES`) is unchanged.

Not done in this round, with reasons (stories stay unticked):

- **Spacing between paragraphs (FE-077, criterion 3), defect found.** `paginate.ts` adds `spaceBefore + spaceAfter` between two paragraphs (and `items.ts` and `notes.ts` use the same sum), while 03 §7 and FE-077 criterion 3 say the gap is the larger of the first paragraph's `spaceAfter` and the second's `spaceBefore`, and zero with `contextualSpacing`. The fix changes every page that has spacing, so it was not made in this round; it needs its own change and the paginator's fixtures. Owner question: none; the spec is clear, the fix is open work.
- **Tables (FE-083).** The tree types and the flow model carry rows, `cantSplit` and `headerRows`, but `items.ts` returns tables in `unplaced` and `paginate.ts` has no table item. Pagination of rows needs its own item kind and the cell layout, which the paginator's columns and footnote rules depend on. Not built.
- **Position mapping (FE-076, criterion 7).** A block identifier and offset map to a line, but a position back to an offset needs per-character advances, which the tree does not record. Not built; a line-granular mapping would not meet the criterion.
- **Tabs in the breaker (FE-081, criterion 3).** Indents and line spacing are in `lines.ts`; tab stops are not (`items.ts` measures a tab as one character). Criterion 3 stays open.
- **Default canvas measurer and Unicode line breaking (FE-079, FE-080).** Need a browser run and the line-break data; not in the repository.

## Round 6 (layout packet, 2026-11-13): tab stops, caret and movement

27. **Tab stops (FE-081, criterion 3, partly).** `lines.ts` takes left tab stops (`tabStops`, in points from the column's left edge, the origin of `line.x`) and a default spacing (`defaultTabStop`). The spec gives no default spacing, so the default is 0: a tab past the last stop has no width. A trailing tab is left out of the fit, as a trailing space is. Centre, right and decimal stops and leaders are not built, so FE-081 criterion 3 and FE-077 criterion 4 stay open. Proposed default; owner question: none beyond the stop kinds still to build.
28. **Caret and selection conventions (FE-096).** `caret.ts` works from the body fragments only (`page.fragments`); headers, footers and footnotes are edited in panels. An offset at a wrap point belongs to the line that starts there, and the end of a block belongs to its last line. A point beyond a line's end gives the line's last position: its `to` for the last line of a block, and `to - 1` for a line that is not (before the character at the wrap, usually the trailing space), because `to` is the start of the next line. Up and Down with a goal x beyond the target line's end, and End, use the same last position, so the caret stays on the line it was sent to (review of round 6). There is no affinity flag, so the caret cannot stand after the wrap character on the earlier line. The width of text inside a line is an injected `SpanWidth`, because the tree records no glyph advances. Proposed default; owner question: whether the caret needs an affinity, which the spec does not say.
29. **Vertical movement and the line keys (FE-097).** Up and Down move by painted line, across pages, and the caller carries the goal x. Page Up and Page Down need a viewport height that the layout does not hold, so they are not built. Home and End give the line's bounds (`lineBounds`). Shift extension and the clamp at region boundaries belong to the input bridge (FE-098) and FE-038.

## Round 8 (layout packet, 2026-11-13): footnote marks, page movement and the position queries

36. **Page Down and Page Up (FE-097, criterion 3).** `movePage` (`caret.ts`) reads "a page of the layout" as one layout page: the caret moves to the body line on the next page (the previous one for Page Up) whose top edge is nearest its own, passing over pages with no body line. With no such page it goes to the document's first or last body line. The alternative, a screenful, needs the painter's visible height and is not built; it would replace the page step only when the painter gives that height. Owner question: whether a keypress should move one layout page or one screen.
37. **Footnote marks come from the shared algorithm (FE-084, criterion 4).** `toFlow` (`flow.ts`) takes each footnote's mark from `computeLabels` in `packages/model` (CDM-042), which applies `footnoteFormat` and restarts the marks at each section break under `footnoteRestart: perPageSection`, as ADR 0032 reads it. The local count stays only as a fallback for a footnote the algorithm does not number. This replaces the round 3 note that the restart was not read.

## Round 9 (lane layout-3, 2026-11-13): tables, table cells and the tree's immutability

38. **Rows never split (FE-083, criteria 1 and 4).** A table is placed row by row: a row goes on a column or page whole, and a row that does not fit moves on. The spec's split of a row taller than a page at paragraph boundaries (03 §10) is not built. Such a row is placed alone at its full height, and its table is reported in `overflowed`. Proposed default: the whole-row rule until a splitting rule is chosen, since the spec does not say what a split of a row across pages keeps together. Owner question: whether a row may split inside a paragraph when it does not fit.
39. **Repeated header rows (FE-083, criterion 2).** The leading rows with the header flag (`headerRows`) repeat at the top of each continuation piece, marked `repeated` in the tree. They take their height from the piece, and a repeated copy is skipped by coverage and by hit testing. Proposed default, since 03 §4.3 says the rows repeat and does not say whether a repeat counts against the next row's fit.
40. **Table cells hold paragraphs (FE-083, criterion 5 open).** `tableItem` (`items.ts`) places a table whose cells hold paragraphs only. A nested table, a box, a non-paragraph block, a row span, or a footnote reference in a cell leaves the table unplaced, and its id is in `unplaced`. Footnotes in cells are not placed, and `vAlign`, borders and shading are not drawn. Owner question: the scope of the first table release.
41. **Tables in multi-column sections (FE-085, criterion 4 open).** A table in a multi-column section is placed like any other, so it can span pages. The criterion is absolute, and tables taller than a page would still span, so it stays open.
42. **Hit testing of table cells (FE-096, criterion 2).** `paintedLines` takes the paragraphs of table cells in reading order. Lines level with each other (two columns, or two cells of one row) are told apart by the horizontal distance to the line's text. Amended in round 10: the cell boxes are in `PaintedLine.cells`, and a click inside a cell that holds lines only resolves to that cell's lines, so blank cell space does not resolve to a neighbour's text (`caret.ts`, `inCell`).
43. **Immutability of the tree (FE-078, criterion 1).** `freezeTree` freezes table rows, cells and cell fragments as well as pages and paragraph fragments; `tables.test.ts` checks that a mutation throws.

The local counter (`Numbering.next`) is removed; the local class keeps only the level definitions, which give the indents and the run format of a label. The check is `numbering-labels.test.ts`: the 24 valid cases of `numbering-lists.json`, in both directions. Owner question: none.
46. **Odd-page story and page-field values (FE-087, criterion 1, open).** The layout puts the page number and the page count into the header and footer paragraphs of each page (`items.ts`, `flowStoryResolver`), so the values are computed here. The criterion says they are shown when the page is painted, and the painter is not built. Not ticked. Owner question: none.

A restart at the first affected page needs the page pass's state at each page start (open page, carried footnotes, balance run, page count), which `paginate.ts` keeps in closures. Not built in this round. Owner question: none for the design; the work is open.

## Round 11 (layout packet, round 4, 2026-11-13): tab stops in the item adapter

48. **Tabs take the paragraph's stops and the document's default spacing (FE-081, criterion 3).** `paragraphItem` (`items.ts`) passes the paragraph's tab stops (`FlowParagraph.tabs`) and `settings.defaultTabStop` (`FlowDocument.defaultTabStop`, threaded through `pageItems`, `tableItem`, the story resolver and the notes) to the breaker, instead of measuring a tab as one character. A numbering label's tab (`FlowTab.toPt`, the hanging indent) is taken as a left stop at that position. Proposed default: the stop list is paragraph-wide, so a left stop at the hanging indent also serves a later tab in the same paragraph that falls before it. The alternative, a stop that serves only the label's tab, needs a per-tab rule in the breaker, which the spec does not give. Owner question: none for the default; a Word-compatible rule for the hanging indent, if the owner wants one, would replace this. Tested in `items-tabs.test.ts`.

## Round 12 (layout packet, round 5, 2026-11-13): typeset line starts

49. **Typeset line starts are cut into the paragraph (FE-100, criterion 1; status proposed).** `layoutFlow` takes `lines` (the `LinePin`s of `adoptablePins`, line granularity only). `paragraphItem` maps each CDM start to a text position of the paragraph (an exact span gives one position per CDM position; a start on no position, or on the first or end position, is ignored and the editor's break stays). `breakParagraphAt` (`lines.ts`) then cuts the text at those positions and breaks each piece with the injected breaker, so a line starts at each typeset start. Proposed defaults: (a) a piece wider than one line gives more lines, and the start after it is still adopted, so the extra lines are the editor's; (b) only the first piece keeps the first-line indent; (c) the lines of an adopted paragraph are the pieces' lines, not one re-break of the whole paragraph, so justification and tab positions are measured per piece from the line start. Owner question: none for the default; the owner may prefer that an overflowing typeset line is reported instead of extended. The caller that calls `layoutFlow` with the adopted lines on the page view is not built (the element). Tested in `line-starts.test.ts`.
50. **Incremental breaker and cut paragraphs (FE-088, note).** `incrementalLayout` keys its cache by block identifier and checks the whole breaker input, so a cut paragraph is cached per piece, with the last piece kept under the identifier.
