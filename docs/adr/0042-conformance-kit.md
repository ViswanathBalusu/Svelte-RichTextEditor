# ADR 0042: The conformance kit: inputs, profiles, oracles and test mode

**Status:** proposed, 2026-11-06 (packet K). Covers PRO-098, PRO-099, PRO-108 to PRO-117, PRO-131 and FRW-065 to FRW-067. Nothing here changes DEP; where 05 leaves a behaviour open, the kit accepts every reading and records which one a target chose.

## Context

05 §11 asks for a black-box test runner that certifies any DEP backend from a discovery URL, a service credential and a test-mode switch, with profiles that map to announced features, golden fixtures, negative tests for the authorisation matrix and fuzzers. The kit is `packages/tck` (`@docedit/tck`). It has to be a fair test of servers written by others, so it must not lean on the project's own client or server code, and it must not fail a server for a choice the specification leaves open.

## Decision (proposed)

1. **What the kit may use.** It speaks DEP itself: frames through the protocol package's codec (`@docedit/protocol`), shapes from its definition, requests with `fetch`, sockets with `ws`. It may also read the reference semantics it certifies against: the CDM definition, canonical form, validation and schema (`@docedit/model`), and the authority's published fixtures and functions as oracles (`@docedit/authority`: the outcome check, the capability fixtures, the authorisation matrix, the step-semantics fixtures). It imports nothing of the component (`element`, `engine`, `ui`, `painter`, `backend-dep`, `backend-mock`) or of a server, and never reaches a database. A test of the kit enforces the list (PRO-108 criterion 4).
2. **Inputs.** Required: the discovery URL, the service credential (from the environment variable `DEP_TCK_CREDENTIAL` or a file, never the command line), and whether the target's test-mode switch is on. Optional, each widening what is checked and skipping what needs it when absent: an origin registered for the kit's tenant (CORS and the allowed half of the `Origin` check); the history visibility the target applies (default `editors`, ADR 0034, proposed); the feature name of read restrictions (default `read-restrictions`, below); time budgets and seeds. The kit creates its own documents and users; every `sub` carries a run prefix, so runs share a tenant safely.
3. **Profiles.** A profile runs when the target announces what it maps to, and is reported as skipped with the reason otherwise; a failed scenario of a profile that runs fails the run. `core`, `perm-doc`, `semantics` (the golden fixtures replayed), `authz` (every row of 07 §12), `registry` (every rejection code with its surface and retry hint) and `fuzz` apply to every server in authority mode; `core-relay` to relays; `presence`, `perm-region` (`regions`), `exports`, `assets`, `fields` and `perm-fill` to their features; profiles of later phases are listed with the story that fills them. `authz`, `registry`, `fuzz` and `semantics` are the kit's names for the contents of 05 §11 that are not features.
4. **Read restrictions.** DEP has no feature name for them yet (G101; PRO-130). The kit maps `perm-read` to `read-restrictions` until PRO-130 names one; the name is configurable. The leak oracle is S12's: unique canaries in a confidential region's text and title, scanned in every frame and every REST response a reader without access receives.
5. **Open questions are not failures.** Where 05 is open the kit accepts each reading and adds a note: the identity in `user.id` (G11), the reaction to an abandoned chunk reassembly (G14), `re` on `pong` (G17), which scopes `access` lists (G43), which connections receive an `event` (G47), and whether a resume beyond the catch-up limits pages or reloads. A scenario that needs a server hook (held writes for `busy`, a fault for `unavailable`) is skipped with the hook it needs (PRO-126).
6. **Oracles.** Property tests judge every accepted commit with the authority's outcome check (PRM-009) and record their seed. The fill property (FRW-066) runs in process against the authority with an oracle written apart from the outcome check, and shows that a check reasoning about step shapes is caught. Golden hashes are checked by the kit's own RFC 8785 implementation and by the model's Python implementation (CDM-011).
7. **Fuzzing.** Each fuzzer runs for a budget (`--fuzz-ms`, default 20 seconds; a full run uses the one-hour target of PRO-116) from a recorded seed. A crash, a stall, a close code outside 05 §5.7, an error code outside the registry or an invalid document fails the run, and the report keeps the seed, the batch and the input.
8. **Scenarios and artifacts in step (PRO-117).** Every scenario declares the message types, optional members, routes, close codes, error codes and notification types it exercises. A test fails for an artifact entry without a scenario that is not on a pending list with a reason, for a pending entry that has a scenario, and for a definition marked final with anything pending. The kit's runs against its targets check that every passing scenario's traffic contains what it declares.
9. **The test-mode switch (PRO-109).** A switch of the server, set by its operator, never visible or settable through discovery, `welcome` or any route. With it on: token expiry is enforced without the 60 seconds of clock skew, `heartbeatMs` is at most a few seconds (and announced in `welcome`, where the kit reads it), leases expire in seconds, and a token still never lives longer than 15 minutes. How a production deployment keeps it off is for the security review the story asks for (SEC); the kit only checks that discovery and `welcome` reveal nothing of it. The reference service has no such switch yet; the kit's mock target implements the timers above.
10. **Report.** JSON (`KitReport`) and text, each profile and scenario with its identifier, result, reason, and for a failure what is required and what the target did. Exit code 0 when the run passes, 1 when it fails, 2 on a usage error. The container image is built with Podman from `packages/tck/Containerfile`.
11. **Known defects.** The kit's own tests list the defects of each target with what is wrong; a new failure fails CI, a listed defect that passes is reported so that the list shrinks.

## Consequences

- A third party can certify a server with a container, a URL and a credential, and gets a report that names each failing scenario with the expectation and the received value.
- Scenarios that need a test hook, a fault or a feature nobody announces yet are skipped with a reason; the pending list says which artifact entries lack a scenario and why.
- The kit depends on the authority package for its oracles, so it certifies against the project's semantics. That is what 05 §9 asks of a native backend, but it means a bug in the authority is not found by the kit.

## Revisit when

PRO-130 names the read-restrictions feature; the fault-injection profile (PRO-126) defines its hooks; or 05 settles any of the gaps in item 5.
