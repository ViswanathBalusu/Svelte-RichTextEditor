# ADR 0419: What a suspended element holds, and the read view when the element moves

**Status:** proposed, 2026-11-20, lane w1 (story FE-005). Item 1 applies owner decision 181 of [owner-decisions-2026-11-15.md](../owner-decisions-2026-11-15.md). Items 2 to 6 are readings of this lane where 02 §2.1 is silent; they are built and measured, and not reviewed by the project owner.

## Context

02 §2.1 says that an element which is still out of the document one microtask after it left suspends: it removes listeners on `document` and `window`, stops observers and workers and closes the socket, and keeps the editor. The owner accepted on 2026-11-15 that two kinds of listener stay on `document` (decision 181). Since then the editor gained a page view, a layout worker, a watch of the visual viewport and the carets of other people, each with something on the page. `packages/element/e2e/fe-005-suspend-resume.spec.ts` now measures, with the counters of FE-006, what the page holds before the element mounts, while it runs, while it is suspended and after it returns.

## Decisions

1. **Decision 181, as applied.** The `selectionchange` listener that ProseMirror puts on `document` for each view, and the handlers Svelte puts on `document` for the event types the shell delegates, stay until the editor is destroyed. FE-005's third criterion and the lifecycle table of 02 §2.1 say so.
2. **Every listener on a page-global target counts, not only those on `document` and `window`.** A suspended element also takes off its `resize` listener on the visual viewport (the keyboard watch of FE-114) and the `loadingdone` listener on the page's font set (the page view), because both are objects of the page that would keep the editor reachable. The web view's `resize` listener on `window` (the carets of SYN-036) goes too. All three return on resume. The page view lays out again on resume only when the set of loaded faces changed meanwhile.
3. **The editing library's own observer stays.** ProseMirror watches its editing surface with a `MutationObserver` on nodes inside the shadow root. It is part of the view, which is kept with the core, and it observes no node of the host page. It cannot be stopped for the length of a suspension: the library starts it again after every state update. The shell's `ResizeObserver`s and its colour-scheme listener are stopped, as before.
4. **The socket.** A backend the element made from `endpoint` is closed, so its socket closes, and it connects again on resume. A backend the host passed is not closed: the host owns it and may share it between elements, so the element closes only its channel. `destroy()` still closes a host's backend (ADR 0039 §6; PRO-090). This is the reading of the 2026-11-15 round, kept.
5. **The read view is closed on suspension.** It has no editing core to keep. Its viewer frame goes (and with it the PDF.js worker), a backend the element opened for it is closed, and the grace period runs as for an editor. Before this round an element that showed the read view never suspended: its socket stayed open and no grace period ran. When the element returns, the read view is shown again from a new export, because the signed URL may have expired and the document may have changed.
6. **A move in one task re-makes the read view's frame.** A browser unloads a frame that leaves the document and loads its page afresh when it returns, even within one task. The frame's port is then dead and the viewer blank. On each connect that follows no suspension the read view opens the same signed URL in a new frame; no export is made. This holds while the first frame is still opening the PDF too: `PdfViewerFrame.destroy()` now rejects an `open` that waits for its pages, where before it never settled, and the export's outcome follows the new frame, so the view does not stay on "Preparing the typeset PDF" for a frame that is gone. A PDF that could not be drawn is not asked for again by a move.

## Not changed, and known

- A PDF viewer opened inside an editing session (the test hook `openPdfViewer`; no pane of the shell opens one yet) is not re-made after a move. Its frame is unloaded by the browser when the element leaves the document, which is what stops its worker; the pane that will show it has to open it again.
- The frame of a sandboxed extension panel (UX-060) has the same property: after any move its page loads afresh and its port is dead. Not measured and not changed here.
- One-shot timers that were already running when the element left (the 500 ms `de-change` throttle, a 400 ms timer of the core) fire once during the suspension and are not renewed. No interval runs.
- Playwright's WebKit (1.65, on Windows 11) raises `loading` and never `loadingdone` on `document.fonts`, for `FontFace.load()`, for `document.fonts.load()` and for a face a style uses (measured on 2026-11-20 with a probe run through `pnpm exec vitest run --project browser`). The page view's listener therefore hears no arriving face in that engine while it runs; on a return from a suspension it does find the face, because it compares the loaded faces (`packages/element/src/fe-005-page-view-suspend.universal.test.ts`). Hearing a face without the event is FE-064's and was not changed here.
- The DEP client that the element makes for `endpoint` holds a `pagehide` listener on `window` while it is connected (PRO-019). It goes when the client is closed, so a suspension removes it for a backend the element made, and not for one the host passed (item 4). `tests/V-FE-113-128/fe-122-two-tabs.spec.ts` measures it with a real WebSocket on the document service, for the editing session and for the read view.

## Consequences

- An element in the read view that a framework moves between tasks pays for a new export. A move with `Element.moveBefore`, or within one task, does not.
- The integration guide (`packages/element/docs/policies-and-side-effects.md`) lists the three listeners it did not name before (`window` `resize`, the visual viewport, the font set) and the framework's delegated-event handlers, and says which are removed during a suspension.
