# ADR 0206: Lane FE-079 to FE-091 decisions and blockers

**Status:** proposed, 2026-11-13. Written by the developer of lane FE-079-091 (round 1). Nothing here is an owner decision.

## FE-075: where layout runs (02 §9.1, §15)

02 §15 leaves open whether layout runs in a worker from the start or is moved there later. The spec gives no default. The proposed default is:

1. Layout runs on the main thread from the start.
2. The engine (`layoutFlow`, `incrementalLayout`, `paginate`, `pageHeights`) stays free of DOM and Node.js APIs and is tested in Node.js. That keeps the move to a worker open without a change of API.
3. Text measurement stays on the main thread, with the canvas provider (FE-079). `OffscreenCanvas` and the font aliases in workers (FE-063) are not built, so a worker placement is not yet possible for measurement.
4. The move to a worker is reconsidered when spike S5 has reported and when a per-frame cost of the tree crossing to the main thread has been measured in a browser (FE-075 criterion 3). Neither has happened.

Consequences: FE-075 criteria 2 and 3 need a worker and a browser run that were not made in this round. Criterion 1 needs the S5 outcome, which is not in the repository, so it stays open. Criterion 4 (update ADR 0005) is not done here: ADR 0005 is an accepted record that another lane may edit.

## FE-080: Unicode line breaking provider

- `linebreak@1.1.0` is present in the pnpm store (`node_modules/.pnpm/linebreak@1.1.0`) as a transitive dependency. `@docedit/layout` does not declare it, so it cannot be imported from `packages/layout` without a `package.json` change.
- The repository holds no Unicode line-breaking test data (`LineBreakTest.txt`), so criterion 2 cannot be run.
- The Unicode version to bundle is not specified (FE-080 Notes).

Needed from the main session: a decision on whether to declare a dependency on a Unicode line-breaking implementation (through `scripts/pnpm-locked.ps1` only), or to write the algorithm; and the test data for the bundled Unicode version. Until then FE-080 stays open.

## FE-085 criterion 4: a table in a multi-column section does not span pages (03 §10), round 2

03 §10 says tables inside multi-column sections cannot span pages, and FE-085 criterion 4 asks the layout to keep them on one page. The spec gives no mechanism. The proposed default is:

1. A table that fits the body of one page is kept on one page. In a multi-column run, when the rest of the current page (all columns from the current one) cannot hold the whole table, and a page can, the table starts on a new page. Built in `paginate.ts` (`placeTable`) and tested in `packages/layout/src/table-columns.test.ts`.
2. A table taller than a page still spans pages, and is reported as overflowing its page, as a table already does. No default is given for it. Options for the main session: lay it out as today and report it; split it at paragraph boundaries as 03 §10 does for a row taller than a page; or refuse it in a multi-column section at the converter. Until decided, FE-085 criterion 4 stays open.

The rule is a proposed default and not an owner decision.

## FE-083 criterion 4: a row taller than the space is cut at paragraph boundaries (round 3, 2026-11-13)

03 §10 says a row taller than a page splits at paragraph boundaries, as the converter does. The spec gives no default for a row whose cells hold one paragraph each, or for an `exact` row height. The proposed default, not an owner decision:

1. A row that does not fit the space left is cut between paragraphs. One cut index applies to all cells of the row; a cell with fewer paragraphs goes whole into the head. The largest cut whose head fits is used (`packages/layout/src/row-split.ts`, `splitRowAt`).
2. A row with no paragraph boundary to cut at moves whole, as before. A paragraph taller than the body is placed alone and reported in `overflowed`.
3. A cut row takes its content height, not its `exact` height (the row item carries no height rule).

Consequences: FE-083 criterion 4 is ticked. Criterion 1 stays open for rows with one paragraph per cell (a line-level split is not built). Criterion 5 stays open (borders and shading).

## FE-087 criterion 3 and FE-082 criterion 1: still blocked (round 3)

- FE-087 criterion 3 (`page` and `pageCount` painted) needs the DOM painter of FE-090, which is not built: `packages/element` has no painter of layout trees. The layout already gives each story its computed label and count (`items.ts`, `withFields`).
- FE-082 criterion 1 compares with stored fixtures under the priority order. The fixture set for that comparison is not identified in the repository, and the CDM conversion it depends on (FE-077) is a spike. Left open.
