# ADR 0302: Block suggestion marks in the body view (lane V-FE-033-048)

Status: proposed. Owner or engine decision; nothing here is decided.

## Context

FE-045 criterion 1 says a row inserted in suggestion mode carries an `ins` node mark and is drawn as a decoration without a wrapper element. FE-046 criterion 1 asks for the same cue on block marks.

The suggestion marks `ins`, `del` and `fmt` (`packages/engine/src/schema.ts`) are rendered by `prosemirror-view`. In `NodeViewDesc.updateChildren` the view calls `syncToMarks(child.marks)` for every child, block children included. A block child that carries an `ins` mark is therefore wrapped in the mark's element (`<ins>`). A mark's `toDOM` cannot produce no element. The test `packages/engine/src/view/suggestion-rows.universal.test.ts` records this as a known defect (`it.fails`).

The inline kinds are not affected: `packages/engine/src/view/fe-046-suggestion-cues.universal.test.ts` passes in Chromium, Firefox and WebKit.

## Options

1. Keep block suggestions as node marks, and stop the view from drawing their element: a custom mark view for `ins`, `del` and `fmt` that returns no wrapper for a non-inline parent. This depends on `prosemirror-view` allowing that, and must be checked in the three engines.
2. Move the block state to a node attribute (for example `suggest` on `table_row`, `paragraph` and `table`), and draw it with a node decoration. This is a schema change that the CDM and the authority's validator (I1 to I12) must follow, and it changes the stored form of block suggestions.
3. Keep the wrapper and accept it, with the table test changed. This is not compatible with FE-045 criterion 1.

## Default taken

None. The spec (02 §5.2, 13 §3) does not say how block suggestions are stored in the view. Until decided, the block cue is not drawn and FE-045 criterion 1 and FE-046 criterion 1 (block part) stay unticked.

## Decision needed

Owner or engine lead: choose option 1 or 2. Option 2 changes the CDM and needs the authority side too.

## Round 2 defaults (FE-044, FE-035), status: proposed

Taken by the lane, not in the spec (02 §5.2 and 03 §5 leave them open). Each is revisable by the engine lead.

1. Paragraphs added or removed in suggestion mode (`packages/engine/src/suggestion-paragraph.ts`, FE-044 criteria 1 and 2):
   - Enter at the end of a paragraph adds an empty paragraph with one `ins` node mark; a closed slice of whole paragraphs at a block boundary (a paste) gets one `ins` on each.
   - A whole paragraph deleted between block boundaries stays with one `del` node mark. A paragraph the same user inserted is removed outright. A selection mixing the user's own paragraphs with others is refused, and so is a second deletion.
   - Enter in the middle of text, a join (Backspace at a paragraph start) and any change inside a table are refused with the `suggestion` reason.
2. Block changes other than paragraphs, rows and tables (`insertSectionBreak`, `insertToc`, `insertCaption`, `setEquationLatex`, `resizeFigure`, `setFigureLayout`, `markRegion`, `setRegionPolicy`) are unavailable in suggestion mode with the reason `suggestion` in `queryCommand`, and `run` refuses them without changing the document (`packages/engine/src/core.ts`, `BLOCK_ONLY_COMMANDS`; FE-044 criterion 5).
3. The rendering defect above (block node marks wrapped in an element) still applies. FE-044 criterion 4 stays open for it, and nothing here decides option 1 or 2.
4. The trimmed-deletion or Replace-all skip counts (FE-037 criterion 2, FE-047 criterion 6) are not surfaced by any shell here. The shell's notice path (`packages/ui/src/shell/notices.ts`, `NoticeTracker`) reads only the `refusal` and `recovered` views, so the announcement needs a change in ui and a browser run. Not made in this lane.
5. FE-035 criterion 3 is tested in Node with a `REMOTE`-marked insertion, which models a remote rebuild but does not run the sync client (`packages/engine/test/fe-035-rebuild-decorations.test.ts`).

## Round 3 defaults (FE-037 criterion 2), status: proposed

Taken by lane V-FE-033-048 in round 3. The spec does not give the wording or the channel for a trimmed deletion, so these are defaults, revisable by the owner of the shell's copy (UX) and of the messages (PRM).

1. A deletion the core trims (	rimmed view, skipped scopes) gives one notice of kind 	rimmed, with the message key 
otice.trimmed.kept ("Part of that deletion was kept: you cannot change some of the text it covered."). It names no scope (ADR 0019), and the count it carries is the number of scopes kept, which is not shown.
2. The notice is shown in the shell's status bar and announced in the shell's ole="status" live region, as refusals and recovered edits are. It is not fed to the element's own announcer (the reader would hear it twice otherwise).
3. Before the shell starts, a trimmed deletion already in the view is not news (as for refusals).
4. Replace-all and accept-all skip counts (FE-047 criterion 6) are not wired by this lane; the registry has no accept-all or reject-all command in packages/ui, so there is nothing to report from yet.
