Date: 2026-11-13. Lane: U-SEC-033-048. Stories in range: SEC-033 to SEC-048. Handled in earlier rounds and not redone: SEC-034, SEC-035, SEC-036, SEC-045.

## Questions

1. **SEC-037 criterion 3 (commit referencing an asset never uploaded for the document, refused with `invalid_op`).** The content PUT route checks attached assets but refuses with `validation_failed`, not `invalid_op` (services/document-service/src/control-plane/handlers.ts, `replaceContent`). The WebSocket commit path gives a new room an empty `attachedAssets` set, so a commit naming another document's asset is not shown to be refused. Spec default: refuse with `invalid_op` at persist time (BE-044). Not decided here: wiring a per-document asset set into the room is a data-plane change, and the owner should confirm whether a PUT refusal should also use `invalid_op`.

2. **SEC-038 criterion 4 (the sandbox kills a hanging decoder).** The Podman sandbox cannot apply its memory limit on this host. `podman run --memory 256m localhost/docedit-asset-worker:dev` fails in `crun` with "open `memory.max` for writing: No such file or directory". The machine (`podman-machine-default`, WSL) reports cgroups v2 with the systemd manager. The asset worker's readiness probe therefore skips all 12 Podman tests. The export worker's sandbox was not probed. Needed: an infra or owner fix to cgroup delegation in the Podman machine, then `pnpm exec vitest run test/sandbox.podman.test.ts` in services/asset-worker.

3. **SEC-033 criteria 1, 2, 3 and 5.** Criterion 3 relies on the class loading babel with `shorthands=off` (packages/export-latex/src/languages.ts), so no language module rewrites `text`. That is checked at source level only. The oracle needs a compile per language and per emitter in the sandbox (question 2). Whether the context list of criterion 2 must include `.bib` data read by biber (SR-M20) is open and was not decided.

## Round 3 (lane U-SEC-033-048): SEC-048

Status: proposed. Date: 2026-11-13.

- Decision (spec default, SEC-048 criterion 2): the export worker job overlays `/run/secrets` with an empty read-only tmpfs (`--tmpfs=/run/secrets:ro,size=4k,mode=0555`, services/export-worker/src/sandbox.ts). Reason: the Podman machine mounts `/usr/share/rhel/secrets` at `/run/secrets` in every container (`/usr/share/containers/mounts.conf` in the machine). The asset worker already does the same (services/asset-worker/src/sandbox-podman.ts). The change is one line in the job's arguments, with its assertion in services/export-worker/src/sandbox.args.test.ts.
- Open for the owner or infra: the mount itself comes from the Podman machine's configuration. Removing it from the machine is an infra decision; the overlay makes the job independent of it.
- Scope of criterion 2: the export worker image only. Other images and long-running services are not inspected.
- Criterion 6 (recorded rehearsal): the record is written by the test to services/document-service/test/postgres/rehearsals/sec-048-secret-rotation.json. The record is regenerated on each run.
- Not decided here: the length of a webhook or credential overlap (set by the caller, not in this tree); the secret-scan CI step (needs `.github`, a root configuration).

## Round 3 fix (lane U-SEC-033-048): SEC-048 criterion 2 after review

Status: proposed. Date: 2026-11-13. This supersedes the first decision of the round 3 section above.

- Withdrawn: the `/run/secrets` tmpfs overlay in services/export-worker/src/sandbox.ts and its assertion in src/sandbox.args.test.ts. The overlay made `/run/secrets` exist in every job, which the EXP-072 check (`[ -e /run/secrets ]` in src/sandbox.escape.test.ts, criterion 1) treats as a host mount. The export worker already keeps the host's files out through its own route: every `run` names an empty default mounts file (`--default-mounts-file=/dev/null`, src/container.ts), on the machine route and on a local Podman. No change to that route was needed. Whether the export worker should also overlay `/run/secrets` stays with the EXP owner and the main session; this lane does not change it.
- Checked on this host (Windows 11, Podman 6.0.2, WSL machine `podman-machine-default`, machine route with cgroupfs), 2026-11-13: `sandboxReady()` returns ok on the machine route after the revert; the whole of src/sandbox.escape.test.ts passes (23 tests), the EXP-072 "no /run/secrets" case included; src/sec-035-sandbox-env.test.ts and src/exp-072-services.podman.test.ts pass.
- services/export-worker/test/u-sec-033-048-container-env.podman.test.ts now runs every case through `runInSandbox`, so the job's own arguments and route are used and no flag is copied. A control case takes the job's own command line, removes only the empty default mounts file, and shows that the same check then finds the injected files at `/run/secrets` (RHEL subscription data from the machine's `/usr/share/containers/mounts.conf`).
- New: services/asset-worker/test/u-sec-033-048-container-env.podman.test.ts runs a probe through `podmanSandbox` (the asset worker job's own arguments and route; only the entry point is `node` without the permission model). No credential variable, no file under the secret paths, uid and gid 10001, empty effective, permitted and bounding capability sets. The asset worker's own `/run/secrets` overlay (sandbox-podman.ts, not this lane's) shows as an empty directory, also under `/var/run/secrets` because the Debian base links `/var/run` to `/run`.
- Criterion 2 stays unticked. The long-running services do not meet it as defined in this tree: in the demo stack (apps/reference-host/compose.json) the document service, the reference host and the export worker process all mount the same `stack-data` volume, which holds one secrets file (apps/reference-host/scripts/lib/stack.ts, `ensureSecrets`) with the host's signing key, the service's signing key, the API key and the view key. Each of those containers can therefore read secrets it does not need (the reference host can read the service's signing key). This is a source finding, not a run: the demo image `localhost/docedit-demo-node:dev` is not built on this host. The demo is not a production deployment, and no production deployment definition exists in this tree.
- Also seen, not changed: the shared test containers `docedit-test-postgres` and `docedit-test-s3` (started by infra/test-env.ps1) hold `/run/secrets/rhsm` from the machine (public Red Hat CA certificates and `rhsm.conf`, no key). Their environments name only their own credential (PostgreSQL: `POSTGRES_PASSWORD`; S3: `ROOT_ACCESS_KEY`, `ROOT_SECRET_KEY`). An empty default mounts file in infra/test-env.ps1 would remove the injected files; that is the infra owner's file.
- Open for the owner: whether criterion 2 is judged on the demo stack, and if so, splitting the demo secrets file per service (each service mounting only its own file).

## Round 4 (lane U-SEC-033-048): SEC-037 criterion 3 and SEC-047 criteria 4 and 5

Status: proposed. Date: 2026-11-13.

- SEC-047 criteria 4 and 5 ticked. Tests: tests/security/test/sec-047-structural-dump.test.ts and tests/security/test/sec-047-compile-log.test.ts (Node.js, memory storage). The BE-089 dump holds no canary; the compile log's canary is not written to the process output.
- SEC-037 criterion 3 stays unticked. The room is built without an attached-asset set (services/document-service/src/data-plane/room-host.ts, `#load`, the `new HostedRoom` call; `Room` takes `attachedAssets` only when given, packages/authority/src/room/room.ts). Filling it needs a decision the spec leaves open, and it is not made here: the set is loaded from the registry (`readyFor` plus the content's own references, as the content route does in control-plane/handlers.ts) at open time, and then either (a) refreshed when an asset becomes ready, which needs a call from the control plane into the open room, or (b) refreshed before each commit that carries a new asset reference, which needs the commit's asset identifiers found in the steps. Both are data-plane changes beside BE-044, in a file other lanes edit. The proposed default is (a) with a refresh at open; the owner or the BE owner should confirm.
- Not touched in this round: SEC-033 criterion 1 (compiled oracle, needs the sandbox compile), SEC-034 criterion 6 (fuzz through the sandbox), SEC-036 criterion 5 (result served from the asset origin: open decision ADR 0256 item 10), SEC-039 criterion 4 (conflicts with A2, owner reading), SEC-048 criteria 1 and 2 (CI and the demo secrets owner decision, see the Round 3 fix above).
