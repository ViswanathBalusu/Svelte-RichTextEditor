# ADR 0406: Templates and the creation of a document from one (FRW-062)

**Status:** proposed, 2026-11-18. Written by lane w4. Owner decision 184 of 2026-11-15 (`docs/owner-decisions-2026-11-15.md`) accepts the workflow design ADRs as a set, with the proposals in the notes of FRW-062 and FRW-063. The points below are the ones 12 §9 and §10 leave open for this story.

## Context

12 §9: a template is a document with role placeholders, fields and rules and no participants. Instantiating it forks the document at a pinned `seq`, binds participants and optionally prefills values. 12 §10 lists `/templates` and gives no method, member or identifier. 05 §6.2 gives `POST /documents` a `template` member and says it is refused until FRW defines templates.

## Decisions taken

1. **What a template is.** A document that a service credential has marked, by `POST /templates { document, name }`. The mark is a row (`document_templates`, migration 0093): identifier (a UUID version 7), the document, the name, who marked it and when. A document is the template of at most one row (`conflict` otherwise). Unmarking and renaming are not built. The template stays an ordinary document: it is edited, read and exported as any other.
2. **The resource.** `GET /templates` (the tenant's templates, oldest first, all of them, no cursor), `GET /templates/{tid}` and `POST /templates`. All three need a service credential: a template is tenant-wide, and the host decides which documents are templates. The matrix of 07 §12 gets them in the service row.
3. **Instantiation is `POST /documents`.** The body takes `template` (the template identifier, not the document), `templateSeq` (the pinned seq, default the head), `participants` and `values`, with the other members of the call (`title`, `externalId`, `properties`, `classification`). At most one of `content`, `template` and `import` stays the rule. The answer is the document resource with `template: { id, seq }`: the seq the document was forked at, which is also recorded on the document as a fork's is (`forkedFrom`, `forkedAtSeq`).
4. **A fork, with nothing else.** The content of the template at the pinned seq becomes the checkpoint at seq 0 of the new document, as for `POST /documents/{id}/fork`, and is read through the same history gate. Nothing else is copied: no grants (`copyGrants` is false and not offered), no workflow, no lock, no state. The new document is `active`, has no workflow unless the call gave participants, and is not locked. A template that carries participants, or a workflow that is `sent`, `in_progress` or any other state, therefore gives a draft: the workflow of the template is removed from the copy by not being copied, and the call does not refuse it. 12 §9 allows either; this is the "removes".
5. **Participants.** `participants` are checked as the body of `PUT /documents/{id}/workflow` is (`checkWorkflowBody`), and each role must be a `role_def` of the template at the pinned seq. They are stored as the draft workflow of the new document, with the default time zone `UTC` and no other member. The call does not send the workflow: sending is a separate action (`/workflow/send`). Routes, deadline and reminders are set afterwards by the owner with a `PUT`.
6. **Values.** `values` are prefilled in one server-authored commit with origin `prefill`, by the same rules as `PATCH /documents/{id}/field-values` (`prefillSteps`: keys that exist, kinds that can be prefilled, typed values). The call waits for the commit, so it answers with the values in place. A refused key or value is `field_invalid` (422), as for the prefill route.
7. **All or nothing.** The template, the seq, the participants, their roles and the values are all checked before the new document is created. A refused call creates nothing. A failure after the document exists (the prefill commit is not stored in time) leaves the document and answers `unavailable` or `conflict`; it is not rolled back, because a document with a log cannot be removed without a purge. The host can repeat the call with the same `Idempotency-Key`.
8. **Not decided.** Who may read the template list with a user token (service only for now); whether a template can be a document that is itself an instance; a limit on the number of templates; the identifiers of participants (`p1` and the like are the writer's, G59).

## Consequences

`createDocument` answers 404 for an unknown template, where it answered `validation_failed` while templates did not exist; `routes.documents.test.ts` was changed to match. `POST /bulk-sends` (FRW-063) is built on the same instantiation.
