# ADR 0314: Lane U-PRO-086-102 decisions (proposed)

Status: proposed. Owner decisions stay with the owner; the spec default is used and recorded here.

## Context

Lane U-PRO-086-102 closes the protocol and embedding stories PRO-086 to PRO-102 where their blockers
are a database, object storage, a container, a browser or a test server. Round 7 took PRO-090,
PRO-095 and PRO-099 (see the story Notes).

## Decisions

1. PRO-095 criterion 2 stays open. `ClientChannel` reads the `inflight` answer of a resumed
   `ch.opened` only as far as it is used to name the lost commit in a resume. `onOpened` in
   `packages/protocol/src/client/channel.ts` ignores `d.inflight`, and `SyncChannel.opened` is the
   first `ch.opened` only. The unanswered submit fails with `unavailable` (D23), and the caller
   resubmits. The spec default is kept: the caller resubmits after `sync.caughtUp`. The open
   question is how the fate (`accepted` with a sequence, or `unknown`) reaches the caller: a new
   member on `SyncChannel` (for example an `onResume` callback), or a new state field. Proposed for
   the maintainers; not decided here.

2. The browser tests of this lane run the element's Playwright configuration on port 56140
   (`DOCEDIT_DEMO_PORT`), inside the lane's allowed range, and do not change root configuration.

3. PRO-099 criterion 3 stays open. The absence test does not yet have a positive control. A
   single-user session renders no `.de-presence` element, so the test cannot show that presence
   controls appear when the port exists. Proposed: a second session in the same test, or a read of
   the header's feature gate. The decision on which is for the maintainers.

4. The reload catch-up (PRO-095 criterion 1) is read as: the channel closes with `unavailable`, and
   the caller reads the pinned content (`loadContent(docId, seq)`). The channel does not read the
   content itself, as in ADR 0040 (D80). The criterion's wording "pinned content read" is taken to
   mean the caller's read, which is the behaviour the backend already has.

## Consequences

- PRO-090 criterion 4 ticked, with a browser test in four engines.
- PRO-095 criterion 1 ticked, with three Node.js tests over a test server that changes the catch-up
  mode of each resumed open (`packages/backend-dep/test/support/catch-up-server.ts`).
- PRO-099 criterion 1 ticked; criterion 3 stays open.

## Round 2 (2026-11-13)

Round 2 takes PRO-086 criterion 2, PRO-096 criterion 2 and PRO-089 criteria 1 to 3, and makes the
element's per-run build directory (the 404 fix that the earlier review asked for). Status: proposed.

5. Export progress is by polling, not by the `export.*` events. `ExportsPort.request` takes an
   optional `onProgress`, which is called with the job now and at each change of state or progress
   until `completed`, `failed` or `cancelled`, until `close()`, or until the job is `not_found`.
   The criterion (PRO-096 criterion 2) allows either "events or polling". The events would need a
   subscription member on the port, and the port typings are the owner's to widen; this is left for
   them.

6. The poll interval is `EXPORT_POLL_MS = 1000` in `packages/backend-dep/src/files.ts`. It is a lane
   choice, not a spec figure, and it is a target to revisit with a measurement. A read that fails
   with a code other than `not_found` is tried again at the next tick. A throwing listener does not
   stop the poll or fail the request.

7. A cancelled job is reported as `de-export-failed` (with `state: "cancelled"`). The spec (05 §8.1)
   names progress, completion and failure only. The reading that a cancelled job did not complete is
   the lane's; the owner may prefer a fourth event.

8. The `de-export-*` details carry `jobId`, `state` and `progress` only (the job's identifiers and
   state, as 05 §8.1 says). The element raises them only while the session that started the job is
   still current, so a job of an earlier document raises nothing.

9. PRO-089 criterion 2 ("shows no sharing dialog and never lists documents") is checked as the DOM
   stands: no `dialog` or `role="dialog"` in the element's shadow root, and no element with the test
   hooks `document-list` or `documents`. That is a check of the present UI, not of every future one.

10. The element's Playwright run builds into its own directory, `packages/element/dist/runs/<pid>-<ms>`
    (`DOCEDIT_ELEMENT_DIST`, read by `scripts/vite-configs.ts` and `demo/serve.ts`), so parallel runs
    stop rebuilding the directory another run is serving. The directories are not removed by the
    configuration, because a reused server may be serving one of them; they are ignored by git
    (`dist/`), and the owner may prune `dist/runs` when disk space matters.

Not decided here: PRO-096 criterion 1 (the upload resolves the asset identifier, as ADR 0110 reads
it), PRO-096 criterion 5 (fonts have no feature name, G06), PRO-086 criteria 3 and 4 (`print()` and
the `no-export` check need PRO-015 and the printing work).

## Round 3 (2026-11-13)

Round 3 takes PRO-092 criterion 4 (the user interface answers no for a port the backend lacks).
Status: proposed.

11. The check of PRO-092 criterion 4 is made at the command registry, not in a browser. A feature
    the backend does not announce gives `offered: false` with reason `unannounced` for each
    built-in command that carries it (`packages/ui/test/pro-092-feature-controls.test.ts`). The
    header, mode switcher and status bar render only offered commands. The in-memory mock announces
    no optional feature but `presence`, so a browser check of an absent `comments` control needs
    a mock that announces `comments`; that is not built, and the test does not fake one. The
    decision whether the registry check is enough for "the control is not rendered" is for the
    maintainers.

12. PRO-092 criterion 5 stays open. It waits for PRO-098 to be complete, and PRO-098 criterion 2
    waits for `backend-local` (PRO-100, phase 4) and for PUT content (BE-037) on the reference
    service.

13. PRO-097 criterion 2 (round 4). The criterion says the comments port creates, replies, resolves
    and deletes through its routes and that backend-dep "applies thread events from the channel".
    The protocol says thread events arrive through SyncChannel.onEvent (CommentsPort doc in
    packages/protocol/src/ports/optional.ts), and the review pane's store applies them
    (packages/backend-dep/src/review.ts header). Reading taken for the test: backend-dep hands the
    channel's thread and comment events on unchanged, in the order received, and they do not move
    the document (packages/backend-dep/test/u-pro-097-thread-events.test.ts, Node.js, 2 of 2 pass).
    That is a proposed reading, not an owner decision. The criterion stays unticked until the
    maintainers decide whether backend-dep keeps a thread store that applies the events, or the
    criterion moves to the review pane.

14. PRO-098 criterion 2 (round 4) stays open. The reference-service cases of
    packages/tck/test/ports.test.ts (DEP_ON_REFERENCE) need PUT content (BE-037) and two service
    decisions (the ebased flag on a head commit; the control commit of initial grants). The
    criterion also needs ackend-local (PRO-100, phase 4), which is not built. Not started here.
