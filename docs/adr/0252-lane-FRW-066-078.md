# ADR 0252: lane FRW-066-078 (fields, rules and workflow, round 1)

**Status:** proposed. **Date:** 2026-11-13. **Lane:** FRW-066-078, round 1.

## Context

The lane was asked to take three to five stories from FRW-066 to FRW-078 that still have unticked criteria. Each candidate was checked against the code before any change. Most unticked criteria wait on something not yet built, so no criterion was ticked and no code was written in this round. The findings below are the reasons, and two of them are gaps in another package that the owner or the main session should route.

## Findings

1. **Region guard lets a fill participant change any field (engine, FRW-076 criterion 1).** `packages/engine/src/guard.ts`, in `checkChange`, reads `if (access.caps.includes('fill')) continue;` for a changed field value. A participant with the `fill` capability is therefore allowed to change the value of every field locally, whatever the field's `assignee`. The authority's P7 check (FRW-008, proved by FRW-066) refuses the other fields on the server, so the security boundary holds. The local guard does not yet give the "only my fields are editable, every other local transaction is refused" that FRW-076 criterion 1 asks for. Needs the engine owner: the guard must know the participant's roles and each field's `assignee`.

2. **The fill event payload has no field key (FRW-070).** `FillField` in `packages/ui/src/core-api.ts` carries `id`, `label`, `required`, `filled`, `invalid`, `assignee` and `role`. It has no `key`. `de-field-change` needs `{ fieldId, key, valid, empty }`, so the core must supply `key` for each fillable field. Needs the core owner (`FillSummary` extension).

3. **The embedding fill API is not built (FRW-069, FRW-071).** `packages/element/src` has no `mode="fill"` method set: no `nextField`, `focusField(key)`, `getFieldValues`, `setFieldValue`, `validateFields`, `completeFilling` or `decline`. `packages/element/src/events.ts` has no `de-field-change`, `de-fill-progress`, `de-sign-request` or `de-workflow-complete`. The core API (`packages/ui/src/core-api.ts`, around line 605) has an optional `focusField(id)` taking a field identifier, not a key. FRW-069 criterion 2 asks for focus by key.

4. **Role management and the property panel are not built (FRW-073, FRW-074).** `packages/ui/src/shell/field-properties.ts` holds the gate for the properties panel (reasons, patch, read-only). The panel and the roles manager are not built, so the reasons on screen, the legend, the delete refusal in the manager and the keyboard and announcement criteria stay open. The I13 refusal of a delete of a role still in use is tested at the authority (`packages/authority/test/room-scenarios.test.ts`), not in the manager.

5. **Conformance profile `fields` (FRW-067).** The mock backend does not announce `fields` (the reference service does, but has not been run with the corrected fields document). Criterion 2 needs the mock backend to announce the feature or a decision that it is not a fields server. That is `backend-mock`'s and `tck`'s work, not this lane's.

6. **Command search and keyboard operability (FRW-072 criterion 5).** The palette is driven by the command registry and is searchable (`packages/ui/test/field-palette-search.test.ts`). Keyboard operability of the palette was not run in a browser in this round.

## Decisions taken

- No criterion was ticked in this round. Each stays unticked with its reason in the story's Notes.
- No new test was written that pins current behaviour of the gaps above; such a test would encode the bug.

## Open questions for the owner or the main session

- Whether the local guard for fill participants should use the authority's field rule (P7) as the single source, or a copy in the engine.
- The field `key` on `FillField` (finding 2): a new optional attribute, or a separate `FillSummary` map.
- Whether `focusField` should accept a key as well as an identifier (FRW-069 criterion 2).

## Round 3 (2026-11-13)

Stories still open in the range after earlier rounds: FRW-068 and FRW-075 (the others were handled in rounds 1 and 2).

7. **FRW-068 (conformance profiles `workflow`, `sign`, `seal`) is blocked.** The profiles need a server that runs the workflow, the ceremony and the signing service, and the workflow actions that activate a participant are not defined (G95). No profile was written. The story's Notes carry the reason.
8. **FRW-075 (preview as a role) has a model only.** `packages/ui/src/shell/role-preview.ts` holds the preview state: the role's fields only, a value overlay that is never a commit, and the caret kept for the return. It is tested in `packages/ui/test/role-preview.test.ts`. The editor side (fill mode for a role, rules with a role operand, the announcement and the keyboard exit) is not built, so no criterion of FRW-075 is ticked.

Decision taken: the preview's overlay is local to the preview and is dropped on leaving. The spec says "no commit is submitted"; this follows it. Nothing else is decided here.
