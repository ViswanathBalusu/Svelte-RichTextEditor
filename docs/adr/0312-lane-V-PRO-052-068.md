# ADR 0312: Lane V-PRO-052-068 decisions (proposed)

Status: proposed. Owner decisions stay the owner's. The choices below are the spec's defaults or the
smallest reading of it, recorded so that the owner can confirm or change them.

Context: round 1 of the unblock lane for stories PRO-052 to PRO-068, which closes criteria that
earlier lanes left open for want of PostgreSQL, a room or a route. This round closed PRO-053
(criterion 1, control commit of a region state) and PRO-058 (criteria 1, 2 and 4, read marker and
the gate on activity). It did not change stories PRO-054 to PRO-057, PRO-059 to PRO-060, PRO-063 to
PRO-066 or PRO-068 (see the story Notes and the lane report).

## 1. The activity reply shape

`Activity` is a placeholder in `spec/dep` ("not defined by the prose"). `GET /documents/{id}/activity`
answers `{ marker, head, items, nextCursor }`, and each item is `{ seq, time, user, origin, scopes,
kind }`, where `user` is the author's `sub` and `kind` is `steps` or `snapshot`. The list is
paged by an opaque cursor like the commit log. This is a proposal; the owner may name the shape.

## 2. What "since the marker" means

- A missing marker counts as 0, so every change by others is listed.
- A change is listed when its `seq` is above the marker and at or above the caller's history gate
  (`minVisibleSeq`, 07 section 8; ADR 0034). Nothing below the gate is listed, even when the marker
  is lower.
- Control commits (permission changes) are not listed as changes. Snapshot commits are listed.
- The caller's own commits are never listed.
- A reader whose view hides content does not get `unavailable`: the activity list is projected for
  their class, and a change whose scopes touch a hidden region is left out, so no item names it
  (ADR 0019; fixer V-SYN-037-053, 2026-11-13; see the route's header comment and PRO-058 Evidence).

## 3. Comment activity is not listed yet

08 section 10 asks for comment activity as well. Threads (PRO-059) are not built, so the list has no
comment source. PRO-058 criterion 3 therefore stays open until PRO-059 exists.

## 4. Region state commit: the room writes the control commit

The control plane's route answers and raises `dep.region.state_changed`; the room writes the
`control` commit at the new grants revision (07 section 9). The route test uses a stub room, so the
commit is shown on the real data plane (`src/data-plane/pro-053-region-state-control-commit.test.ts`).

## 5. Test ping and replay: no route contract yet (PRO-068 criteria 4 and 5)

`packages/protocol/src/definition/resources.ts` defines no route for a test ping or for a replay of
deliveries; the subscription body is a placeholder (gap G76). `WebhookDispatcher.ping` and
`WebhookDispatcher.replay` exist, but no route calls them, and the dispatcher is not in the control
plane's `HandlerDeps` (`kit.ts` holds only the subscription store). A route contract is a decision
for the owner and for the protocol package: a proposed pair is `POST /webhooks/{id}/test` and
`POST /webhooks/{id}/deliveries/{did}/replay`, both service-credential only. Not built here.

## 6. Packages the lane could not change

`services/document-service/package.json` has no `@docedit/history` dependency, so PRO-054 to
PRO-056 (grouped history, versions, diff and attribution, restore) cannot import the history engine
in this lane. Adding it is a `package.json` change for the main session.

## 8. Thread changes and comments (PRO-060; round 2, 2026-11-13; proposed)

The spec does not give these, so the smallest reading is taken and listed for the owner.

- The ETag of a thread is `"<id>:<state>:<assignee>"` (the assignee percent-encoded), and that of a
  comment is `"<id>:<edit time>"`. A change of state or assignee, or an edit, changes the tag, so
  a `PATCH` with a stale `If-Match` gets 412 and one without gets 428. The published operations
  name `If-Match` as required for `PATCH`, and not the tag's form. The earlier thread tag, the
  identifier alone, is replaced; the PRO-059 test is updated to match.
- A reader whose view hides the thread's region gets `not_found` for read, change, reply and delete
  (ADR 0019): `thread-routes.ts` applies `readerView` to the thread's scope before the rules of
  `authoriseThread` run, and the same check covers the comments of that thread.
- A comment's author is the connection's `sub`, as the thread's first comment is. A service
  credential writes no comment and so cannot edit one; it may delete one, as it may delete a thread.
- A `PATCH` names its rights per change: resolving needs `resolve`, reopening `reopen`, an assignee
  change `assign`, and each is checked by `authoriseThread`. A resolution keeps the first resolver
  while the thread stays resolved; a reopening clears it.
- Notices and webhooks: `resolved` and `reopened` have a webhook (`dep.thread.resolved`,
  `dep.thread.reopened`) and a notice; an assignee change has the `thread.updated` notice only,
  because the webhook vocabulary has no `thread.updated` (gap in `packages/protocol/src/definition/gaps.ts`).
- Comments are soft-deleted: the row keeps its `deleted_at`, and reads leave it out. The thread
  delete (PRO-059) still removes the rows, as migration 0063 allows.
- Mentions (the body of a comment, and `dep.comment.mentioned`) are not read. PRO-060 criterion 4
  stays open for that part.

## 9. Range threads (PRO-059 criterion 2; round 2, 2026-11-13; proposed)

- A range is mapped from its `baseSeq` to the head with `mapRangesThrough` over the commits after
  it, the mapping the room uses (SYN-032). Its scopes are those of the mapped range (`rangeScopes`),
  and `comment` is checked in each of them.
- The rebase window is `DEFAULT_LIMITS.maxRebaseSteps` (the room's own default), measured as a
  difference in seq. The control plane has no other limit to read. A base outside the window, or
  above the head, is `validation_failed`; the spec's word "refused" is read as that problem.
- A range that lost all its text (from below to, and collapsed after mapping) is refused with
  `validation_failed`; a range that starts collapsed is allowed.
- Storage: a range's head seq is `range_seq` (with `range_from` and `range_to`, migration 0050);
  a thread that covers several scopes keeps them joined by a newline in `scope`. The code reads
  them back with `scopesOf` in `thread-routes.ts`.
- Not decided here: `GET /documents/{id}/threads` with `?seq` (PRO-059 criterion 4). The route is
  not built; mapping a stored range back to an earlier seq has no engine function (the mapping runs
  forwards only), so the owner must say what a `?seq` before the stored `range_seq` returns.
