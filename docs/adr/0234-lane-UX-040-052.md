# ADR 0234: lane UX-040-052 decisions (agent identity, extension document API)

**Status:** proposed. **Date:** 2026-11-13. **Lane:** UX-040-052, round 1.

This record holds two decisions and one spike recommendation for the UX epic. Both are proposed. Nothing here is accepted, and the owner has not decided any of it. Where the spec leaves a question open, the proposal below uses the spec default and says so. Security review is required for Part A (README definition of done, UX-044 notes), and no part may be built before it is accepted.

Stories: UX-044 (decision, Part A), UX-049 (spike, Part B) and UX-043 (spike, Part C, round 2). UX-051 is implemented separately and is not decided here.

## Context

- 13 section 6.2 says an assistant's commits carry `origin: "assistant"` and `author.agent`, and that the agent identity is capped at `suggest` because "rule P4 already enforces that on the server". The gap is that P4 applies to a user holding `suggest` without `edit` (07 section 5.2). Nothing derives a cap for an agent acting for an editor (07 section 4 has no agent row). The second review (SR-M23, [second review](../review/2026-11-06-second-review.md)) confirms this.
- 04 section 2 lists `origin` as the client's hint, "recorded and shown as the client's claim; nothing is authorised on its strength". So `origin: "assistant"` from a browser proves nothing.
- 05 section 3.1 has user tokens with `sub`, `tid` and roles, and no agent claim. 05 section 3.2 has `DEP-Actor` for service calls acting for a user, which names the user but no agent.
- 05 section 5.5 already has `author: { user, session, agent }` on `sync.commit`, so the wire field exists. Nothing says who fills `agent`.

## Part A. Decision: how an assistant's agent identity is established and capped (UX-044)

### A1. The server learns that a commit is the assistant's from the credential, never from the client

An agent connection is one whose verified credential is an **agent token**. The client's `origin` hint on `sync.submit` is ignored for this purpose. A commit gets `origin: "assistant"` and `author.agent` only when the authority verifies an agent token on the connection that submitted it. The authority writes both values into the stored commit itself. A client that sends `origin: "assistant"` on a user connection gets an ordinary commit with the hint recorded as a claim (04 section 2), and no agent attribution.

### A2. Where an agent identity comes from

- The **document service** owns the agent registry, per tenant: an agent identifier (`agt`), a display name, the owning host, and the set of documents it may act on.
- An agent is **registered by a service credential** (05 section 3.2) through a new control-plane call, `POST /agents`. A user token can never register an agent or become one (05 section 3.2 already forbids a user token becoming a service credential).
- An **agent token** is a short-lived JWT with type header `dep-agent+jwt`, signed with keys registered separately from user-token keys (the same rule as 05 section 3.2). Its claims are:
  - `sub`: the acting user (the person the assistant acts for), in the tenant's surrogate form;
  - `agt`: the agent identifier;
  - `act`: `{ "sub": "<agent identifier>" }`, the actor claim in the manner of RFC 8693 (the agent is the actor, the user is the subject);
  - `tid`, `doc`, `aud` and `exp` as for user tokens, with `exp` short.
- The **agent token is minted only by the service** (`POST /tokens` with a service credential, or the host's own signing key registered as an agent issuer). The browser never signs one.
- `author.agent` is the `agt` of the verified token. `author.user` is the `sub`. History shows both (08 section 7, UX-046 criterion 2).

### A3. The cap is part of effective capabilities (07 section 4)

Add to 07 section 4 this rule, which applies to every scope:

> For an agent connection, the capabilities in a scope are the intersection of the capabilities the user `sub` would hold in that scope (per the rows above) and `{suggest}`. An agent connection never holds `edit`, `fill`, `structure` or `manage`, and it holds `comment` or `view` only where the user holds them.

Consequences:

- An agent acting for an **editor** has `suggest` at most. It cannot change text except as suggestions, and the authority applies P4 to its commits as to any suggester.
- An agent acting for a **user with only `suggest`** has `suggest`. P4 applies unchanged.
- An agent acting for a **viewer** has `view` only.
- Region grants (07 section 4) are intersected the same way, so an agent never gains a grant the user lacks.

The cap is computed by the authority from the verified token, not from anything the client sends. `rev` (05 section 5.5) changes when the registry entry is disabled, so a disabled agent loses access at once.

### A4. How each assistant case obtains the agent identity

| Case | Agent identity | Notes |
|---|---|---|
| Assistant in the browser (the component calls the model) | The host backend mints an agent token for the user and passes it to the page with the user token. The page presents it on a separate channel for assistant writes. | The page holds an agent token that can only suggest. It cannot turn a user connection into an agent connection. |
| Assistant in the host backend, using a service credential and `DEP-Actor` | The host calls `POST /documents/{id}/...` with its service credential, `DEP-Actor: <user>`, and `DEP-Agent: <agt>`. The service accepts `DEP-Agent` only when that agent is registered to the same service credential and the document is in its list. | `DEP-Agent` is honoured only with a service credential. A user token cannot set it. |
| Third-party service | It registers an agent through `POST /agents` (with its own service credential, granted by the tenant) and then acts as in the row above. | Same rules. The service never holds a user token. |

### A5. What stays open

- Owner: whether a tenant may register agents without an owner's approval. Spec default: registration needs a service credential with `manage` rights in the tenant (the host).
- Owner: retention of agent attribution after an agent is disabled. Spec default: unchanged history, with `agent` still shown.
- Until this ADR is accepted and 05 and 07 are amended, **13 section 6.2 must not claim server enforcement of the cap.** UX-046 does not start.

### A6. Amendments required on acceptance (not made here)

- 05 section 3: a new subsection for agent tokens and `POST /agents`; the `DEP-Agent` header in section 3.2 and in the CORS header list of section 6.
- 07 section 4: the agent rule of A3.
- 13 section 6.2: the sentence "Rule P4 already enforces that on the server" is replaced by a reference to this decision.
- 04 section 2: no change needed; the client `origin` stays a claim.

## Part B. Spike recommendation: the document API for extensions and its versioning (UX-049)

### B1. Operations and events (13 section 7.1)

Read operations (each returns data only for scopes the requester may view, the projection of ADR 0019):

- `blocks(range)`: the blocks in a range, as a read-only block tree with ids.
- `text(range)`: the plain text of a range.
- `selection()`: the current selection as a range.
- `marks(range)`: the marks of a range, with suggestion marks and their authors.
- `comments(range)` and `suggestions(range)`: their identifiers and state.

Write operations (each submitted as an ordinary commit through the same authority guards):

- `insertBlocks(at, blocks)`, `replaceRange(range, content)`, `setMark(range, mark)`, `deleteRange(range)`.
- A write under a tier that cannot write fails with `permission_denied` before it reaches the authority.
- Origin of an extension's commit: spec default `input` is wrong because it hides the extension. Proposed: a client hint `extension` added to the origin list of 04 section 2, with the extension's identifier in `author.extension`. This needs a spec change and the owner's decision (open).

Events, each carrying the document `seq` it refers to and only ids and ranges, with content only for scopes the subscriber may view:

- `blocks.added`, `blocks.changed`, `blocks.deleted`: block ids, and the mapped range where the block is.
- `selection.changed`: anchor and head as ranges.
- `suggestions.changed` and `comments.changed`: the identifiers that changed and their state.

Delivery is in commit order. A subscriber that misses events (a reconnection) gets a catch-up of the changed ids from the `seq` it last saw, or a `reload` signal, as the channel catch-up of 05 section 5.2 does.

### B2. Ranges held across an edit

Recommendation: **ranges are mapped for reads and checked for writes.**

- A range held by an extension is mapped through every local and remote step, with the same mapping used for comment ranges (SYN). A read through a mapped range returns what is there now.
- A write names the `seq` the range was computed against. If the mapped range no longer covers the same content at the authority, the write is refused with `conflict`, and the extension re-reads. Stale writes are never applied to a moved range.

### B3. Manifest fields

- `id` (unique per tenant page; the registry rejects duplicates, as UX-051 criterion 4 does), `name`, `version`.
- `api`: the API version the extension needs, an integer major with a minor (for example `1.0`). The editor lists the versions it supports as a required option (ADR 0136, decision 12). An unsupported version is reported and the extension is not activated (UX-050 criterion 2).
- `tier`: `1` (in page, host trust) or `2` (sandboxed, UX-060).
- `access`: for tier 2, `read` (`view` or higher) and `write` (`none`, `suggest` or `edit`). A tier 1 extension has the host's rights; `access` is still declared so the documentation can state it.
- `contributes`: `commands`, `toolbarGroups`, `contextMenuItems`, `shortcuts`, `panels`, `statusItems`, `customBlocks`, each as a list of identifiers the extension defines.
- `strings`: the extension's string table, which UX-051 criterion 5 checks labels against.
- `entry`: the code, supplied with the manifest through the `extensions` property (05 section 8.1).

### B4. Compatibility promise and deprecation

- Within one major API version, changes are additive only. A new operation, event or optional field may be added; nothing is removed, renamed or given new meaning.
- A removal or an incompatible change needs a new major version. Both majors are supported for the deprecation window.
- A deprecated operation keeps working and reports a non-fatal `de-error` with a `deprecated` code when first called.
- **Open (owner):** the length of the deprecation window. This ADR does not set a number. The spec gives none, and no figure is invented here.

### B5. Tier 2 (UX-060) uses the same API

The tier 2 sandbox wraps the same operations. The `access` declaration decides which operations the wrapper forwards. A tier 1 extension calls the same functions with no wrapper, so code written for tier 1 does not need rewriting to run as tier 2 under a narrower `access`.

### B6. Acceptance

Criterion 5 of UX-049 (this ADR accepted before UX-050 starts) is not met. Until acceptance, UX-050 may build the registration and host logic (already present in `packages/ui/src/extensions/host.ts`), but the document API it exposes to extensions is not a promise.

## Part C. Spike recommendation: a built-in fallback spell checker (UX-043)

### C1. Recommendation: do not ship a built-in fallback in phase 2

Spelling and grammar stay a port (13 section 6.1). The editor ships no dictionary of its own in phase 2. Reasons, from the spec:

- 13 section 6.1 already names the proofing port as the answer to the loss of native spellcheck, in the page view and in the web view (02 section 15).
- The proofing code loads on demand (13 section 9), so a fallback would sit outside the 300 KB initial budget only if it is loaded with the proofing code. The budget is not at risk from a port-only design.
- A fallback adds dictionaries, which carry their own licences and sizes, and a second checker whose results would differ from the host's port. That is a maintenance and support cost the spec does not ask for in phase 2.

Revisit this when a deployment without a proofing port needs spelling. This is a proposal: the owner decides (13 section 13 lists the question as open).

### C2. Candidate dictionaries and their licences (not done)

Not done in this round. No candidate dictionary was listed, its licence read or its size measured. The first locales are not set by the spec, so the list needs the owner's choice of locales first. Each candidate would be checked against the project licence (Apache-2.0, recommended) when it is listed. No licence or size is claimed here.

### C3. Cost of an on-demand fallback (not done)

Not estimated. Without a candidate and a measured compressed size there is no number. The estimate is to be taken from the built bundle with the stated method, after C2.

### C4. Misspellings when there is no proofing port (proposal)

Proposal, using the spec default for an open question (02 section 15; 13 section 13): with no proofing port, the editing surface keeps the browser's own spellcheck on (`spellcheck` enabled on the editable region). The editor's Word-style context menu does not open on a word the browser has marked as misspelt, so the browser's suggestions show there. The editor's menu opens on everything else as it does now. This is not checked in a browser in this round. Owner decision needed (open question in 13 section 13).
