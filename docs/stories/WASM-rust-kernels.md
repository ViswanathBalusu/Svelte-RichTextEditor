# WASM Rust compiled to WebAssembly for compute kernels

The work that follows from [ADR 0016](../adr/0016-rust-wasm-compute-kernels.md) and the [Rust and WebAssembly assessment](../research/2026-11-06-rust-wasm-assessment.md). In short: nothing on the editing, sync, permission, rules, history, protocol or export path is written in Rust. WebAssembly enters the product only as the page view's text kernel, behind the measurement interface that 02 §9.1 already requires, and only if the evidence asks for it. The layout engine, pagination, the layout tree and the painter remain FE's, in TypeScript; this epic owns what runs behind FE's injected interfaces. The spikes that decide all of this (S2, S5, S7 and S10) are in SPK.

Every story here is conditional. Two conditions are used:

| Label | Holds when |
|---|---|
| **C-WASM** | The page-view gate (SPK-013) says yes to the page view or to the read-only painter, and S5 (SPK-018) chooses measurement from the font files. WebAssembly is then needed at all, whichever shaper wins |
| **C-RUST** | C-WASM holds, and S10 (SPK-023) recommends one Rust module for shaping, segmentation, line breaking and hyphenation rather than HarfBuzz's own WebAssembly build alone |

If C-WASM never holds, this epic stays parked and costs nothing.

### WASM-004 A layout worker that hosts the kernel

| Type | Phase | Size | Priority | Persona |
|---|---|---|---|---|
| enabler | cond | M | must | Maintainer |

**Spec:** 02 §2.1, §9.1, §9.5, §15; ADR 0016 · **Requirements:** R1, R12 · **Depends on:** WASM-002, FE-076, FE-004, FE-006

As a maintainer, I want the kernel to run in its own worker with a narrow, batched message interface, so that layout work never blocks typing and the host is asked for nothing it cannot give.

**Acceptance criteria**

- [x] Each editor instance has one worker that owns one kernel instance; no `SharedArrayBuffer` or WebAssembly threads are used, so the host page need not be cross-origin isolated.
- [x] Requests and results cross the boundary in batches of whole paragraphs or blocks, with typed arrays transferred rather than copied, and the measured cost per batch is recorded.
- [x] Given a second editor on the same page, the compiled module is reused rather than compiled again.
- [x] Given the element suspends, the worker stops; given it is destroyed, the worker and its memory are released; given it resumes, the kernel is re-created on first use (02 §2.1).
- [x] Given the kernel traps, the error is caught and logged, the view falls back as in WASM-003, and no document state is lost, because the document lives in the editing core on the main thread.

**Evidence:** Lane w6, 2026-11-18, on owner decisions 26 and 27 of [docs/owner-decisions-2026-11-15.md](../owner-decisions-2026-11-15.md) (the page view and the Rust module are built; C-WASM and C-RUST hold). Code: `packages/element/src/layout-kernel-request.ts` (`ElementKernel`: one for each element, owns at most one worker; `pageModule` is the compiled module of the page), `features/layout-worker-host.ts` (`LayoutWorker`: `start`, `batch`, `terminate` and the cost records `BatchStat`), `features/layout-worker-core.ts` (what the worker does with a message), `features/layout-worker.ts` (the worker script, built as a module worker), `features/layout-worker-create.ts` (the `docedit-worker` Trusted Types policy and the bundler's URL), `features/layout-kernel.ts` (the loader, now run inside the worker: it compiles with `compileStreaming` or `compile` and starts the kernel from the module), `packages/layout-kernel/src/batch.ts` (batch and message types), `doc-editor.ts` (`stop()` on suspend, `destroy()` on destroy), `scripts/vite-configs.ts` (`worker.format: 'es'` and the kernel plugin for the worker). Tests: `test/wasm-004-layout-worker.test.ts` (13 tests, Node.js: the real worker core and the real build of the crate in `worker_threads` workers) and `e2e/wasm-004-layout-worker.spec.ts` (4 tests in each of Chromium, Edge, Firefox and WebKit on the library build; with `wasm-002-kernel-load.spec.ts` and `wasm-003-blocked.spec.ts`, 50 passed and 2 skipped on 2026-11-18, the two skips being the PDF test in Firefox and Edge, as before). Criterion 1: one `Worker` for each editor (a module worker, `/lib/assets/layout-worker-<hash>.js`), and its core holds one kernel; `crossOriginIsolated` is false in the test page and the kernel still loads and answers; no `SharedArrayBuffer` or `Atomics` is used (the answer's buffer is a plain `ArrayBuffer`, checked). Criterion 2: a batch is `packBlocks` (every block's UTF-16 code units in one `Uint16Array` and the block boundaries in one `Uint32Array`); the buffers are transferred (afterwards the caller's buffers have length 0, in the unit test and in all four browsers) and the answer is one `Uint32Array`, transferred back. The only operation today is `checksum`, because the crate has no other call: the shaping and line-breaking operations (WASM-006, WASM-008) add names to `BatchOperation` and nothing to the shape. `LayoutWorker.stats` records for every batch its blocks, units, the worker's time and the round trip. Measured on this machine (Windows 11, Playwright's own browsers, 2026-11-18, `test-results/evidence/wasm-004-batch-cost.<browser>.json`): the median of 25 batches of 200 paragraphs of 630 code units (126,000 code units each) took a round trip of 1.7 ms in Chromium (worker 1.3 ms), 1.6 ms in Edge (1.2 ms), 2 ms in Firefox (1 ms) and 15 ms in WebKit (worker 1 ms; its timers are coarse, so take it as an upper bound only). That is the transport plus a hash, not shaping; it is not the typing budget of S10. Criterion 3: two editors on one page give two workers and one `.wasm` request; the first reports `streaming: true`, the second `streaming: null, bytes: null`, because it was handed the compiled module that the first worker posted back; the page compiled nothing itself (the e2e counts no `WebAssembly` compile call on the page); unit test with two `ElementKernel`s started together. Criterion 4: taking the element out of the page ends its worker (`terminate` called once; the Node worker exits), putting it back creates none, the first `batch` after a stop creates a new one from the page's module, `destroy()` ends it for good (a later `batch` rejects with `kernel_unavailable`), and a start that a suspend overtook is ended without a report. Criterion 5: a trap in a batch is caught in the worker (`kernel_trap`); the page ends that worker, reports `de-diagnostic` `load-failed` with `code: kernel_trap` (`doc-editor.ts` turns every `load-failed` into `degraded`, the fallback and, in Firefox, the notice, as WASM-003 does) and rejects the batch; the text the caller holds is untouched, because the document is in the editing core on the page and the worker only ever gets a packed copy. The trap is shown with a kernel whose `checksum` throws a `WebAssembly.RuntimeError` (the crate's calls cannot trap); it is not run through the element in a browser. Where the policy lives changed: the module is compiled in the worker, so `'wasm-unsafe-eval'` belongs to the worker script's own response policy and the page needs none; `e2e/wasm-003-blocked.spec.ts` now puts the page's policy on the worker script and passes in the four browsers. Docs: the integration guide and `policies-and-side-effects.md` (the worker, `worker-src`, the directive, no cross-origin isolation, the new codes `worker_failed` and `kernel_trap`), and 02 §15 (the open issue is answered for the page view's text kernel).

### WASM-008 First-fit line breaking in the kernel

| Type | Phase | Size | Priority | Persona |
|---|---|---|---|---|
| enabler | cond | M | must | Maintainer |

**Spec:** 02 §9.3, §9.7; 09 §7.1; 03 §4.1 (`defaultTabStop`) · **Requirements:** R1 · **Depends on:** WASM-006, WASM-007, FE-076, FE-081

As a maintainer, I want the kernel to break a whole paragraph into lines in one call, using the spec's first-fit rule and the same offsets the typesetter reports, so that the layout engine can adopt the PDF's breaks where they apply.

**Acceptance criteria**

- [x] Given shaped runs and a line width, the kernel returns line starts and line widths using first-fit breaking at UAX #14 opportunities (02 §9.3).
- [x] Line starts are offsets in UTF-16 code units of the block's text, with each inline atom counting as one and bookmarks as zero, the rule of `layout.json` (09 §7.1), so the engine can adopt reported breaks (02 §9.7).
- [x] Justified lines report the word spacing to apply, which stretches only ordinary and no-break spaces and excludes trailing spaces and tabs (02 §9.3).
- [x] Tabs advance to the paragraph's tab stops or to the document's `defaultTabStop`.
- [x] Re-breaking an edited paragraph reuses cached shaping for runs that did not change.
- [x] Golden tests in Node.js lock the line breaks of the shared corpus.

**Evidence:** Lane w6, 2026-11-18, on owner decisions 26 and 27 of [docs/owner-decisions-2026-11-15.md](../owner-decisions-2026-11-15.md) (C-WASM and C-RUST hold) and on WASM-006 (shaping). Criterion 4: a tab moves to the next custom stop past the position, else to the next multiple of the document's default tab stop, else has no width; left, right, centre and decimal stops place the text after the tab as the engine's do (native tests, Node.js tests, and the corpus comparison); stops may be given in any order. Criterion 5: each text run is shaped through the cache of WASM-006, keyed by the text: breaking the same paragraph again shapes nothing, and after one word of the last line is changed the second break shapes fewer than a third of what the first did (`linebreak.test.ts`, "reuses cached shaping when an edited paragraph is broken again": the counts are the cache's misses). Criterion 6: the golden file holds the line starts of every paragraph of `pages-1`, `form-fields` and `pages-20` as the kernel breaks them (pages-100 and the larger documents are not in it); the test fails on any change, and `DOCEDIT_UPDATE_GOLDEN=1` rewrites it (then run Prettier on it). - The measurement base (S5) and the kernel boundary and language (S10) decide whether any of this epic is built.
- The unit and rounding of the kernel's advances: the CDM's twentieths of a point may be too coarse for glyph advances. WASM-006 documents the choice; it must be made with FE's layout engine.
- Whether layout runs in a worker from the start (02 §15). WASM-004 puts the kernel in one; FE decides for the rest of the engine.
- Whether the house class will select luaotfload's HarfBuzz renderer (S4 reports; EXP decides). It sets how much the shared fonts and shaper can reduce differences between screen and PDF.
- How Unicode upgrades are scheduled across the kernel, the web view (which uses the browser's own data) and LuaLaTeX.
